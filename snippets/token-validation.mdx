Your backend verifies the geolocation token and reads `passed` from it. If `passed` is `false`, your backend rejects the action. The result your app receives is for your UI. A value such as `passed` that arrives from the client outside a verified token can be changed by the user, so never perform a protected action because of it.

Decoding a token isn't validating it. Decoding only reads the payload, and anyone can produce a payload that decodes. Validation means verifying the signature with your secret key and then checking the claims described here.

### Token format and key

| Property | Value |
| --- | --- |
| Format | A JSON Web Token in JWS compact serialization: three base64url segments separated by periods. |
| Algorithm | `HS256` (HMAC with SHA-256). |
| Key | Your project's JWT secret key, shown under **Fraud** on the [Settings](https://dashboard.radar.com/settings#fraud-settings) page. The same key signs and verifies, so it belongs only on your backend. |
| Key identifier | None. The token header has no `kid`. |
| Registered claims | `iat` (issued at) and `exp` (expiry), both in seconds since the Unix epoch. |
| Confidentiality | The token is signed, not encrypted. The signature makes changes detectable. It doesn't hide the payload from someone who holds the token. |

Store the secret key in your secret manager and load it from an environment variable. Don't ship it in a mobile app, a web bundle, or a repository.

### Validation steps

Run every step, in this order, for every token. Reject the request at the first step that fails.

| Step | Check | Performed by |
| --- | --- | --- |
| 1 | The token arrived on an authenticated request, so you know which user is asking. | Your code |
| 2 | The algorithm is `HS256`. Pass an explicit allowlist so that a token with `alg` set to `none` or to another algorithm is rejected. | JWT library, when you pass the allowlist |
| 3 | The signature verifies with your JWT secret key. | JWT library |
| 4 | The token hasn't expired: the current time is before `exp`. | JWT library |
| 5 | `user.userId` equals the ID of the authenticated user on this request. | Your code |
| 6 | `product` equals the product the user is trying to use, when your project uses products. | Your code |
| 7 | `transactionId` equals the action the request performs, when you passed one to the check. | Your code |
| 8 | `user.live` is `true` in production, so that a token from the Test environment isn't accepted. | Your code |
| 9 | `passed` is `true`. | Your code |

A JWT library does steps 2 to 4 and nothing else. It knows nothing about your users, products, or actions, so steps 5 to 9 are code you write. A token that passes steps 2 to 4 is authentic. Steps 5 to 8 confirm it belongs to this request, and step 9 reads the result.

Notes on specific steps:

- **Trusted key selection**: Select the key from your own configuration for the project and environment that the request belongs to. Don't select a key based on anything inside the token.
- **Clock skew**: If you allow a tolerance on `exp`, keep it to a few seconds.
- **Product result**: `passed` is the result for the product in `product`. When your project returns a `products` object, it holds one `passed` value per configured product, and you can read `products.<name>.passed` for the product of the action.
- **Replay**: Radar doesn't track whether a token has already been presented. A token stays valid until `exp`. If an action must be performed only once, pass a `transactionId` to the check, and have your backend mark that identifier as used.
- **Unknown fields**: The payload can gain fields. Ignore fields you don't use instead of rejecting the token.

### Example: Node.js

This example uses the [`jose`](https://github.com/panva/jose) library, which verifies the signature, the algorithm allowlist, and `exp`. The function returns the verified payload, and throws when the token is invalid, expired, or doesn't belong to the request.

```javascript Node.js
import { jwtVerify } from 'jose';

const secret = new TextEncoder().encode(process.env.RADAR_JWT_SECRET_KEY);

/**
 * @param {string} token Geolocation token sent by the client
 * @param {{ userId: string, product?: string, transactionId?: string, requireLive: boolean }} expected
 *   Values from your own session and request, not from the client
 * @returns {Promise<object>} The verified token payload
 */
export async function verifyGeolocationToken(token, expected) {
  // Throws on a bad signature, another algorithm, or a past exp.
  const { payload } = await jwtVerify(token, secret, {
    algorithms: ['HS256'],
    clockTolerance: 5, // seconds
  });

  if (payload.user?.userId !== expected.userId) {
    throw new Error('Token is for a different user');
  }
  if (expected.product && payload.product !== expected.product) {
    throw new Error('Token is for a different product');
  }
  if (expected.transactionId && payload.transactionId !== expected.transactionId) {
    throw new Error('Token is for a different transaction');
  }
  if (expected.requireLive && payload.user.live !== true) {
    throw new Error('Token is from the Test environment');
  }

  return payload;
}
```

Call it from an authenticated route, take the expected values from the session, and read `passed`:

```javascript Node.js
app.post('/api/wagers', requireSession, async (req, res) => {
  let payload;
  try {
    payload = await verifyGeolocationToken(req.body.geolocationToken, {
      userId: req.session.userId,
      product: 'sportsbook',
      requireLive: process.env.NODE_ENV === 'production',
    });
  } catch (err) {
    // No valid token for this request. The client runs a new check.
    return res.status(401).json({ error: 'invalid_geolocation_token' });
  }

  if (payload.passed !== true) {
    return res.status(403).json({ passed: false, failureReasons: payload.failureReasons });
  }

  // Place the wager.
});
```

### Example: Python

This example uses [PyJWT](https://pyjwt.readthedocs.io), which verifies the signature, the algorithm allowlist, and `exp`. The function returns the verified payload, and raises `jwt.InvalidTokenError` when the token is invalid, expired, or doesn't belong to the request.

```python Python
import os

import jwt  # PyJWT

SECRET = os.environ["RADAR_JWT_SECRET_KEY"]


def verify_geolocation_token(token, user_id, product=None, transaction_id=None, require_live=True):
    # Raises on a bad signature, another algorithm, or a past exp.
    payload = jwt.decode(
        token,
        SECRET,
        algorithms=["HS256"],
        leeway=5,
        options={"require": ["exp", "iat"]},
    )

    user = payload.get("user") or {}

    if user.get("userId") != user_id:
        raise jwt.InvalidTokenError("Token is for a different user")
    if product and payload.get("product") != product:
        raise jwt.InvalidTokenError("Token is for a different product")
    if transaction_id and payload.get("transactionId") != transaction_id:
        raise jwt.InvalidTokenError("Token is for a different transaction")
    if require_live and user.get("live") is not True:
        raise jwt.InvalidTokenError("Token is from the Test environment")

    return payload
```

Read `passed` from the returned payload. If it isn't `True`, reject the action and return `payload["failureReasons"]` so that your app can explain why.

### Act on the validation result

| Situation | What your backend does | What your app does |
| --- | --- | --- |
| The token is valid and `passed` is `true` | Performs the action. | Continues. Runs a new check before the token expires. |
| The token is valid and `passed` is `false` | Rejects the action and returns `failureReasons`. | Shows a message based on `failureReasons`. Lets the user fix the cause and run a new check. |
| `passed` is `true` and `warningReasons` isn't empty | Performs the action. Warnings don't fail a check. Record them if your own policy uses them. | Continues. |
| The token has expired | Rejects the request. | Runs a new check and sends the new token. |
| The signature, algorithm, or format is invalid | Rejects the request and logs the event. | Doesn't resend the same token. |
| `user.userId` doesn't match the session user | Rejects the request. | Calls `Radar.setUserId()` with the signed-in user, then runs a new check. |
| `product` or `transactionId` doesn't match | Rejects the request. | Sets the correct product or transaction, then runs a new check. |
| No token on the request | Rejects the request. | Runs a check and sends the token. |
| The client check returned an error status and no token | Receives nothing to validate, so the action isn't performed. | Handles the error and runs a new check. An error isn't a failed check, and it isn't a pass. |

When your backend can't validate a token, including when your own validation code throws, reject the action.

### Change the secret key

The token header has no key identifier, so your backend can't pick a key per token. If your project's JWT secret key is replaced, tokens signed with the previous key stop verifying once your backend loads the new key. To avoid rejecting tokens during the change, configure both keys for a short overlap, try the current key first, then the previous key, and remove the previous key after the longest token lifetime has elapsed.

### Negative tests

Cover each of these in your backend tests. Sign test tokens with a test-only secret.

| Fixture | Expected result |
| --- | --- |
| Valid token, `passed` is `true`, matching user and product | Action performed |
| Valid token, `passed` is `false` with `failureReasons` | Rejected, with the failure reasons in the response |
| Valid token, `passed` is `true` with `warningReasons` | Action performed |
| Token signed with a different secret | Rejected |
| Token with `alg` set to `none`, or with the signature removed | Rejected |
| Token with one payload character changed | Rejected |
| Token with `exp` in the past | Rejected |
| Valid token for `user-456` presented in a `user-123` session | Rejected |
| Valid token for `casino` presented for a `sportsbook` action | Rejected |
| Valid token with `user.live` set to `false` presented in production | Rejected |
| No token | Rejected |
