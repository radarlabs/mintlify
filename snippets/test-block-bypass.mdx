Use a block rule to produce a failed check on demand, and a bypass rule to pass checks from a location or device that would otherwise fail. Both apply to one named test user, so the rest of your traffic is unaffected.

Bypass rules are for internal testing only. Never apply them to real users.

Before you start:

- Use the Test environment and a dedicated test account, for example `test-user-123`. Sign in to your app as that user so that `Radar.setUserId()` sends the same value.
- Your Radar dashboard account needs permission to create block rules. If the **Create** button isn't shown on the **Block rules** page, ask a project admin.

### Block a test user and confirm the rejection

<Steps>
  <Step title="Create the block rule">
    In the dashboard, open the **Block rules** page and click **Create**. Match on the user ID, enter `test-user-123` as the rule value, add a description such as "Integration test, remove after use", and select **Blocked**. For a rule that removes itself, set a temporary duration instead of a permanent one.
  </Step>
  <Step title="Run a check as the test user">
    In your app, signed in as `test-user-123`, trigger a verified location check. The request succeeds and returns a token with `passed` set to `false`, `failureReasons` containing `fraud_blocked_user_id`, and `user.fraud.blocked` set to `true`.
  </Step>
  <Step title="Confirm the UI blocks the action">
    Your app shows its blocked state and doesn't offer the protected action.
  </Step>
  <Step title="Confirm your backend rejects the action">
    Send the protected request directly to your backend with the failed token, bypassing your UI. Your backend must deny it. If the request succeeds, your backend is trusting the client instead of validating the token.
  </Step>
</Steps>

### Bypass checks for a test user

Use a bypass rule when a tester is physically outside your allowed area, or uses a development device that fails integrity checks, and needs to reach the allowed path.

<Steps>
  <Step title="Create the bypass rule">
    On the **Block rules** page, click **Create**. Match on the user ID, enter `test-user-123`, add a description, and select **Bypassed**. To limit the rule, restrict it to specific countries or states, or to specific failure reasons in **Bypassed failure reasons**.
  </Step>
  <Step title="Run a check as the test user">
    The token returns `passed` set to `true` and `user.fraud.bypassed` set to `true`.
  </Step>
  <Step title="Confirm the allowed path">
    Your backend validates the token and allows the action.
  </Step>
</Steps>

Your backend can read `user.fraud.bypassed` to tell a bypassed pass from a regular one. In production, consider denying tokens with `user.fraud.bypassed` set to `true` unless the user is on your internal tester list.

### Override failure reasons or location for a test user

To test how your app handles a specific failure reason or a specific location, set an override on the test user or device. Open the user or device in the dashboard, open its menu, and select **Set override**. Enter a **Failure reasons override**, an **Address or coordinates override**, or both, then save. Later checks for that user or device return the overridden values. Remove the override from the same menu when you finish.

### Use the API instead of the dashboard

If the block endpoints are enabled for your project, you can create and disable block rules from a script with a secret key. Run the script from your backend or a terminal, never from client code. This request blocks the test user:

```bash
curl "https://api.radar.io/v1/fraud/block" \
  -H "Authorization: prj_test_sk_..." \
  -H "Content-Type: application/json" \
  -X POST \
  -d '{"items":[{"userId":"test-user-123","description":"Integration test"}]}'
```

To remove the block, call the unblock endpoint with the same user ID:

```bash
curl "https://api.radar.io/v1/fraud/unblock" \
  -H "Authorization: prj_test_sk_..." \
  -H "Content-Type: application/json" \
  -X POST \
  -d '{"items":[{"userId":"test-user-123"}]}'
```

For the full request and response fields, see [Fraud API](/api/fraud). The API creates block rules only. Create bypass rules in the dashboard.

### Clean up

1. On the **Block rules** page, find each rule you created for the test user and disable or delete it.
2. Remove any override you set on the test user or device.
3. Run one more check as the test user. Confirm that `user.fraud.blocked` and `user.fraud.bypassed` are both `false` and that `passed` reflects the real location and device.
4. Confirm that no bypass rule exists in the Live environment for a real user.

### Test technical errors separately

Block and bypass rules change the result of a check that completes. They don't simulate a check that can't complete. Test those paths on the device: deny location permission, turn on airplane mode, and, on web with the companion app path, quit the Radar Verify app. In each case the client returns an error status and no token, and your backend receives nothing to validate.
