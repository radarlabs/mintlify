A verified location check produces four separate facts. Treat each one as its own question.

| Statement | How you know | What it doesn't tell you |
| --- | --- | --- |
| The request succeeded | The client returned a success status and a token. | Whether the user passed. A successful request can carry `passed` set to `false`. |
| The token is authentic | Your backend verified the signature and expiry with your JWT secret key. | Whether the token belongs to this user, product, or action. |
| The location was verified | `passed` is `true` in the verified payload, so the jurisdiction and fraud checks passed. | Whether the result applies to the user and product on this request. |
| The user is eligible | Your backend confirmed the token is authentic, belongs to the authenticated user and the intended product, isn't expired, and has `passed` set to `true`. | Anything about your other business rules, such as account status or limits. |

Perform a protected action only when the last statement holds.

### Read the client result

The client returns a status and, on success, a token object.

| Field | Type | Description |
| --- | --- | --- |
| `token` | string | The signed geolocation token. Send it to your backend. |
| `passed` | boolean | Whether the user passed all jurisdiction and fraud checks. Use it to update your UI. Your backend reads `passed` from the verified token. |
| `failureReasons` | array of strings | Why the check failed, when `passed` is `false`. |
| `expiresAt` | datetime | When the token expires. |
| `expiresIn` | number | Seconds until the token expires. |
| `_id` | string | Radar's ID for the location check. Use it to find the check in the Radar dashboard. |
| `user` | object | The user, with detail in `user.fraud`, `user.country`, and `user.state`. |
| `events` | array | Events generated by the check, if any. |

Send the token to your backend with the protected request. Your backend verifies the token and reads `passed` itself, so a `passed` value changed on the device has no effect.

### Handle a failed check

A failed check is a successful request with `passed` set to `false` and at least one entry in `failureReasons`. It means Radar reached a conclusion about the user or device.

- Show a message that helps the user fix the cause, such as moving to an allowed area or disconnecting a VPN. For each reason, see [Failure reasons](/api/geolocation-tokens#failure-reasons).
- Let the user run a new check after they change something. Don't loop automatically on a failed check.
- If failure reason messages are enabled for your project, the payload includes `user.failureReasonMessages`, keyed by failure reason, with a `message` to display and a `retry` flag. This is account-specific configuration.

`warningReasons` lists signals that Radar reports without failing the check. A check with warnings can still have `passed` set to `true`. Warnings are in the token payload that your backend reads.

### Handle a technical error

A technical error means the check didn't complete. The client returns a status other than success, and no token. It says nothing about the user's eligibility, so don't treat it as a failed check, and don't treat it as a pass.

| Status | Meaning | What to do |
| --- | --- | --- |
| `ERROR_PERMISSIONS` | Location permission isn't granted. | Explain why location is needed and send the user to grant it. |
| `ERROR_LOCATION` | The device couldn't determine a location. | Ask the user to turn on location services and Wi-Fi, then run a new check. |
| `ERROR_NETWORK` | The request timed out or the host was unreachable. | Ask the user to check their connection, then run a new check. |
| `ERROR_SERVER` | Radar was reachable and returned an internal error. | Run a new check after a short delay. |
| `ERROR_VERIFY_APP` | Web only. The Radar Verify companion app isn't running or isn't installed. | Prompt the user to open or install the app. |
| `ERROR_PLUGIN` | The fraud plugin is missing or incompatible with the Radar SDK. | Fix the installation. See [Fraud plugin setup](/sdk/fraud). |
| `ERROR_UNAUTHORIZED` | The publishable key or auth token is invalid. | Fix the credential. This is an integration error. |
| `ERROR_FORBIDDEN` | The request isn't permitted, for example an auth token constraint doesn't match or device attestation is unavailable. | Check the SDK logs. |
| `ERROR_PUBLISHABLE_KEY` | The SDK isn't initialized. | Initialize the SDK before the check. |
| `ERROR_BAD_REQUEST`, `ERROR_RATE_LIMIT` | The request was invalid or rate limited. | Treat as an integration error and investigate before launch. |

Until a new check succeeds and your backend validates its token, keep the protected action blocked.

### Use the returned expiry

Every token carries its own expiry. Radar sets it for each check based on your configuration and the result, and it is shorter when the user is close to a border. Don't hardcode an interval.

- On the client, schedule the next check from `expiresIn` or `expiresAt` on the token you received. Start the next check shortly before the expiry so that a valid token is always available.
- On your backend, rely on the `exp` claim. Your JWT library rejects a token after that time.
- When the app returns to the foreground, or a page becomes visible again, compare the current time to `expiresAt` before you reuse a stored token.
- Run a new check when the user changes product, when the signed-in user changes, and before an action you bind with a `transactionId`.

### Record a check reason

Pass a `reason` with each check, such as `login`, `wager`, or `withdrawal`. Radar returns it in the token as `reason` and shows it in dashboard filters and reports, so you can tell which step of your flow produced a result. The value is a free-form string. Choose a small, fixed set of values and use them consistently across platforms.
