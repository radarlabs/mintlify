<Info>
  The Salesforce Marketing Cloud integration is available on the [Enterprise plan](https://radar.com/pricing).
</Info>

By the end of this page, Radar sends each location event to a data extension in [Salesforce Marketing Cloud](https://www.salesforce.com/products/marketing-cloud/overview/) as an API event, where it can trigger a journey in Journey Builder, and you have confirmed delivery for one test contact.

Radar sends events only. It doesn't write Radar user attributes to Salesforce contacts.

## Prerequisites

- A Radar project on the Enterprise plan, with the Radar SDK generating events. See [Detect geofence events and place visits](/geofencing/geofences-and-places).
- A Salesforce Marketing Cloud account, with permission to create installed packages and to edit the data model in Contact Builder.
- The Marketing Cloud contact key for each user, available in your app. With the Marketing Cloud mobile SDK, this is the SDK's contact key.

## Configuration

<Steps>
  <Step title="Create an installed package in Salesforce Marketing Cloud">
    In the Marketing Cloud **Setup** menu, open **Installed Packages** and click **New**. Enter `Radar` as the package name. On the package details page, add an **API Integration** component with the **Server-to-Server** integration type, and grant all permissions for the **Automation**, **Contacts**, **Cross Cloud Platform**, and **Data** scopes.

    Copy the **Client ID**, **Client Secret**, **Authentication Base URI**, and **REST Base URI**.
  </Step>
  <Step title="Enter the credentials in Radar">
    In the Radar dashboard, open the [Integrations](https://dashboard.radar.com/integrations) page, find the **Salesforce Marketing Cloud** section, and select **Yes** for **Enabled**. Enter these values:

    | Field | Value |
    | --- | --- |
    | **Client ID**, **Client secret** | From the installed package. |
    | **Auth base URI** | The **Authentication Base URI**, pasted exactly as Salesforce shows it, including the trailing slash. |
    | **REST base URI** | The **REST Base URI**, pasted exactly as Salesforce shows it, including the trailing slash. |
    | **Event definition key** | Optional. The key for the event definition Radar creates. The default is `radar-event`. |

    Click **Save**. Radar authenticates with Salesforce using the credentials. If authentication fails, the save fails with a message that starts with `Error authenticating to Salesforce Marketing Cloud`. If it succeeds, Radar creates an API event definition named **Radar Event** and its data extension, with the event definition key you entered.
  </Step>
  <Step title="Link the data extension to your contacts">
    In **Contact Builder**, open **Data Designer**. Link the **Contact Key** field of your customer data to the `contactKey` field of the Radar data extension, in a one-to-many relationship.
  </Step>
  <Step title="Set the contact key in your app">
    Set the metadata described in [Identity mapping](#identity-mapping).
  </Step>
</Steps>

## Identity mapping

| Radar value | Sent to Salesforce as | Required |
| --- | --- | --- |
| `metadata.salesforceContactKey` | `ContactKey` on the API event, and `contactKey` in the event data | Yes. Without it, Radar skips the event and logs `Identifier missing.` |
| `userId` | `userUserId` in the event data | No |
| `deviceId` | `userDeviceId` in the event data | No |

Radar doesn't use the Radar `userId` as the contact key. Set `salesforceContactKey` in Radar user metadata:

<CodeGroup>

```swift Swift
import RadarSDK

// The Salesforce call depends on your Marketing Cloud SDK version.
let contactKey = SFMCSdk.mp.contactKey()
Radar.setMetadata(["salesforceContactKey": contactKey])
```

```kotlin Kotlin
import io.radar.sdk.Radar
import org.json.JSONObject

// The Salesforce calls depend on your Marketing Cloud SDK version.
SFMCSdk.requestSdk { sdk ->
    sdk.mp {
        val contactKey = it.moduleIdentity.profileId
        Radar.setMetadata(JSONObject().put("salesforceContactKey", contactKey))
    }
}
```

</CodeGroup>

`Radar.setMetadata()` replaces the whole metadata object, so include any other metadata keys you use in the same call. When the user logs out or changes, update the metadata so events stop going to the previous contact.

## Event mapping

Every Radar event becomes one row in the Radar data extension. The Radar event type is stored in the `type` attribute, so one event definition carries all event types. Filter on `type` in Journey Builder to pick the events you want.

Radar sends these event types: `user.entered_geofence`, `user.exited_geofence`, `user.dwelled_in_geofence`, `user.entered_place`, `user.exited_place`, `user.nearby_place_chain`, the `user.entered_region_*` and `user.exited_region_*` events for country, state, DMA, and postal code, `user.started_trip`, `user.updated_trip`, `user.approaching_trip_destination`, `user.arrived_at_trip_destination`, `user.stopped_trip`, `user.entered_beacon`, and `user.exited_beacon`. Other event types that pass your filters are sent with the common attributes only.

The data extension has a fixed schema, created when you first save the integration. Text attributes have a maximum length of 100 characters unless noted. Metadata is sent as one JSON string per object, with a maximum length of 4,000 characters, because Salesforce requires the schema in advance.

## Filtering

On the [Integrations](https://dashboard.radar.com/integrations) page, click **Show advanced** in the **Salesforce Marketing Cloud** section.

| Setting | Effect |
| --- | --- |
| **Event type allowlist** | Radar sends only the selected event types. Check this list first when an event you expect is missing. |
| **Request key blocklist** | Comma-separated keys to remove from each request, for example `userDeviceId`. Don't block `contactKey`, `id`, or `type`. |
| **Geofence tag blocklist** | Comma-separated geofence tags. Radar skips events for geofences with these tags. |

For the filters that every event integration shares, see [Filters](/integrations/integrations#filters). Because every event type arrives in one data extension, also filter by `type` and other attributes in the journey's entry source.

## Delivery behavior

- Radar sends to Salesforce only when it generates an event for a user who has a contact key.
- For each batch of events, Radar first requests an access token from your authentication base URI, then posts each event separately to the `interaction/v1/events` endpoint on your REST base URI.
- Delivery is asynchronous and doesn't block the SDK.
- Radar sends each request once. It doesn't retry a request that Salesforce rejects or that times out. If the token request fails, no events from that batch are sent, and the failed token request is recorded in the integration logs.
- The integration has one set of credentials and one event definition key. Events from the Test and Live environments of the project are sent to the same Salesforce event definition.

## Verify integration data delivery

<Steps>
  <Step title="Prepare a test contact">
    On a test device, set `salesforceContactKey` in Radar metadata to the contact key of a contact that exists in Marketing Cloud.
  </Step>
  <Step title="Generate an event">
    Generate an event for that user. Either open the [Simulator](https://dashboard.radar.com/geofencing/simulate) page, choose the user, and move it into a geofence, or use a test build of your app and enter the geofence.
  </Step>
  <Step title="Check Radar's log">
    On the [Events](https://dashboard.radar.com/geofencing/events) page, click **View** on the new event and find the **Logs** section. Confirm that it shows a Salesforce request to `interaction/v1/events` with a `2xx` response.
  </Step>
  <Step title="Check Salesforce">
    In **Contact Builder**, open the Radar data extension and confirm a new row with your contact key, the event `type`, and the geofence attributes.
  </Step>
</Steps>

## Troubleshoot delivery

Click **View integration logs** in the **Salesforce Marketing Cloud** section of the [Integrations](https://dashboard.radar.com/integrations) page. Each row shows the timestamp, the request URL, and the response code, and expands to the request and response bodies. The client ID and client secret are redacted. New rows can take a few minutes to appear.

| Log response | Meaning |
| --- | --- |
| `skipped`: `Integration key(s) missing.` | The client ID, client secret, auth base URI, or REST base URI is empty. |
| `skipped`: `Identifier missing.` | The user has no `metadata.salesforceContactKey`. |
| `skipped`, "Event type ... isn't allowed." | The event type isn't selected in the allowlist. |
| `skipped`: `Geofence tag '...' is blocklisted.` | The geofence tag is in the blocklist. |
| A failed request to `v2/token` | Salesforce rejected the credentials. Check the client ID and secret, and that the auth base URI ends with a slash. |
| A `4xx` response from `interaction/v1/events` | Salesforce rejected the event. The response body in the log gives the reason. Check the event definition key, the package scopes, and attribute lengths. |
| `2xx`, but the journey doesn't start | The row arrived. Check the journey's entry source filter and the **Data Designer** link between `contactKey` and your contact data. |

## Example use cases

### Send a personalized push notification when a user arrives at a store

1. Create [geofences](/geofencing/geofences-and-places) in Radar with the tag `store`.
2. In Journey Builder, create a journey whose entry source is an API event from the Radar data extension. Filter the entry source on `type` equal to `user.entered_geofence` and `geofenceTag` equal to `store`. Add a push message activity, and use attributes such as `geofenceDescription` to personalize it.

### Message all users who have been nearby a store

1. Create geofences in Radar that cover the area around each store, with the tag `nearby-store`.
2. In Marketing Cloud, create a mobile list filtered on the Radar data extension: `type` equal to `user.entered_geofence`, `geofenceTag` equal to `nearby-store`, and `createdAt` within the last 7 days.
3. Create a MobilePush message whose audience is that list.

## Limitations

- Events only. Radar doesn't sync user attributes, so there is no "current geofences" field on the contact. Build audiences from event rows instead.
- The data extension schema is fixed when the event definition is created. Metadata is one JSON string per object, not one attribute per key.
- Durations are rounded to whole minutes.
- One set of credentials serves both the Test and Live environments.
- A user without `salesforceContactKey` metadata is skipped. The Radar `userId` alone isn't enough.
- There is no automatic retry. A request that fails during a Salesforce outage isn't resent.
