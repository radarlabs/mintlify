<Info>
  The Olo integration is available on the [Enterprise plan](https://radar.com/pricing).
</Info>

An order placed through [Olo](https://www.olo.com) creates a Radar trip, your app starts that trip, and Radar tells Olo to fire the order to the kitchen when the customer is the right number of minutes away. If no location arrives, Radar fires the order at a backup time instead.

For the trip lifecycle in your app, see [Track pickups](/geofencing/trips#track-pickups).

## Prerequisites

- A Radar project on the Enterprise plan with trip tracking enabled, and the Radar SDK in your app with at least [foreground location permission](/fundamentals/location-permissions).
- Access to the Olo Dashboard with two-factor authentication and at least Brand Manager permission, which the **Development Tools** section requires.
- Your Olo brand ID for each environment. Radar matches incoming webhooks to your project and environment by brand ID.
- For order firing: an Olo API client ID and secret key for each environment.

## Configuration

<Steps>
  <Step title="Send Olo order webhooks to Radar">
    In the Olo Dashboard, open **Development Tools** and add a webhook that delivers to `https://api.radar.io/webhooks/olo`. Under **Order Events**, select **Order Placed** and **Order Cancelled**, and **Order Picked Up** if you use [Olo Expo](#expo-notifications). Radar reads the event type (`OrderPlaced`, `OrderCancelled`, or `OrderPickedUp`) from the `X-Olo-Event-Type` header.
  </Step>
  <Step title="Let Radar fire orders in Olo">
    In **Partner Management**, add Radar with a **Partnership Type** of **Customer Arrival** and select the stores where Radar fires orders. Allow manual fire for each of those stores.

    An order that Radar fires must set a `timeWanted` for advance orders, or set the external reference to any value that starts with `radar_`, for example `radar_h87y12rgb`. Radar reads it from the webhook body as `externalReference`.
  </Step>
  <Step title="Configure the Olo settings in Radar">
    On the [Integrations](https://dashboard.radar.com/integrations) page, select **Yes** for **Enabled** in the **Olo** section. Each environment has its own group of settings, and every label starts with the environment name, for example **Live brand ID** and **Test brand ID**. Click **Save**. The page confirms with `Updated integration.`

    | Setting | What to enter |
    | --- | --- |
    | **Live brand ID** | The Olo brand ID for that environment. A webhook whose `brandId` matches the Live brand ID creates trips in the Live environment. Other webhooks for your project create trips in the Test environment. |
    | **Live destination geofence tag** | The tag shared by your store geofences, for example `store`. |
    | **Live trip metadata mapping** | Optional. Pairs of an Olo webhook field path, such as `customer.firstName`, and the Radar trip metadata key to copy it to. Mapped metadata appears in the dashboard, the [Trips API](/api/trips), and trip events, so map only the fields your store team or messaging needs. |
    | **Live handoff modes** | The Olo handoff modes to track, for example `curbside` and `pickup`. If empty, Radar handles every handoff mode. If set, Radar ignores webhooks for other modes and doesn't fire their orders. |
    | **enable order firing**, **client ID**, **secret key** | Turns on order firing, with the Olo API credentials that Radar signs its requests with. Live trips fire against Olo's production ordering API, and Test trips against Olo's sandbox ordering API. |
    | **Live scheduled order earliest fire time (minutes)** | When set, Radar doesn't fire an order on approach or arrival earlier than this many minutes before `scheduledArrivalAt`. |
    | **Live auto-calculate trip scheduled arrival time** | Sets `scheduledArrivalAt` for ASAP orders. See [Order firing](#order-firing). |
    | **Live backup fire delay (minutes)** | Shown when the previous setting is on. The dashboard default is 10. |
    | **Live auto-calculate trip approaching threshold** | Sets `approachingThreshold` for ASAP orders. |
    | **allow multiple orders per trip** | Adds a customer's second order to their existing trip when both go to the same destination and their expected arrival times are within one hour of each other. |
  </Step>
  <Step title="Create store geofences">
    Create one [geofence](/geofencing/geofences-and-places) per store. Set its `tag` to the destination geofence tag, and its `externalId` to the value Olo sends as `storeNumber` for that store. If no geofence matches, Radar still creates the trip, but can't calculate an ETA or detect arrival.
  </Step>
</Steps>

## Identity and field mapping

Radar builds each trip from the Olo **Order Placed** webhook body. The trip has status `pending` until your app starts it. If your app already started a trip with the same `externalId`, Radar adds the Olo fields to that trip.

| Olo webhook field | Radar trip field | Notes |
| --- | --- | --- |
| `orderIdString` | `externalId` | The order ID. Your app must pass the same value to `Radar.startTrip()`. |
| `id` | `metadata.oloOrderGuid` | The order GUID, a different value from the order ID. Radar uses it to fire the order and to update Olo Expo. |
| `deliveryMethod` | `metadata.oloHandoffMode` | The handoff mode, for example `curbside`. Radar sends it back to Olo when it fires the order. |
| `storeNumber` | `destinationGeofenceExternalId` | Matched with the destination geofence tag. |
| `brandId` | Project and environment | Not stored on the trip. |
| `timePlaced`, `timeReady` | `approachingThreshold`, `scheduledArrivalAt` | Only for ASAP orders, when the matching auto-calculate setting is on. |
| `timeWanted` | None | Its presence marks the order as scheduled. |

Olo sends `timePlaced`, `timeReady`, and `timeWanted` as strings in the store's local time, formatted `YYYYMMDD hh:mm`.

## Start the trip in your app

Call `Radar.startTrip()` after the order is placed and you have confirmed location permission. Include `oloOrderGuid` and `oloHandoffMode` in trip metadata, so Radar can still fire the order if the webhook is delayed or missing.

<CodeGroup>

```swift Swift
import RadarSDK

// Initialize the SDK first: /sdk/ios
func startPickupTrip(orderId: String, orderGuid: String, handoffMode: String,
                     storeNumber: String, scheduledPickupTime: Date?) {
    let tripOptions = RadarTripOptions(
        externalId: orderId,
        destinationGeofenceTag: "store",
        destinationGeofenceExternalId: storeNumber,
        scheduledArrivalAt: scheduledPickupTime // nil for ASAP orders with auto-calculation on
    )
    tripOptions.mode = .car
    tripOptions.metadata = [
        "oloOrderGuid": orderGuid,
        "oloHandoffMode": handoffMode
    ]

    Radar.startTrip(options: tripOptions, trackingOptions: RadarTrackingOptions.presetContinuous) { status, trip, events in
        if status == .success {
            // Show the "on the way" state in your UI.
        } else {
            // Retry, or fall back as described under "No-location fallback".
        }
    }
}
```

```kotlin Kotlin
import io.radar.sdk.Radar
import io.radar.sdk.RadarTrackingOptions
import io.radar.sdk.RadarTripOptions
import org.json.JSONObject
import java.util.Date

// Initialize the SDK first: /sdk/android
fun startPickupTrip(orderId: String, orderGuid: String, handoffMode: String,
                    storeNumber: String, scheduledPickupTime: Date?) {
    val tripOptions = RadarTripOptions(
        externalId = orderId,
        metadata = JSONObject()
            .put("oloOrderGuid", orderGuid)
            .put("oloHandoffMode", handoffMode),
        destinationGeofenceTag = "store",
        destinationGeofenceExternalId = storeNumber,
        mode = Radar.RadarRouteMode.CAR,
        scheduledArrivalAt = scheduledPickupTime // null for ASAP orders with auto-calculation on
    )

    Radar.startTrip(tripOptions, RadarTrackingOptions.CONTINUOUS) { status, trip, events ->
        if (status == Radar.RadarStatus.SUCCESS) {
            // Show the "on the way" state in your UI.
        } else {
            // Retry, or fall back as described under "No-location fallback".
        }
    }
}
```

## Order firing

Radar fires an order only when order firing is on for the environment, the trip has `scheduledArrivalAt`, and the order has a GUID and a handoff mode. Each order fires once, on the first of these:

- **Approaching**: a location update puts the trip ETA below the approaching threshold.
- **Arrived**: a location update is inside the destination geofence, including on a trip that starts there.
- **Backup fire time**: the current time passes `scheduledArrivalAt` minus the approaching threshold. This doesn't depend on location. Radar checks on a recurring schedule, so expect the fire shortly after that time.

| | ASAP order | Scheduled order |
| --- | --- | --- |
| How Radar tells them apart | `timeWanted` is absent from the webhook. | `timeWanted` is present. |
| `scheduledArrivalAt` | With auto-calculation on, the current time plus the minutes between `timePlaced` and `timeReady`. Radar then moves it to match the ETA, until the ETA has slipped past the first ETA by the backup fire delay. Otherwise set it yourself. | Never auto-calculated. Set it to the scheduled pickup time with `Radar.startTrip()`, `Radar.updateTrip()`, or the [Trips API](/api/trips). |
| `approachingThreshold` | With auto-calculation on, the minutes between `timePlaced` and `timeReady`. | Never auto-calculated. Radar uses the trip, store, or project value. |
| Main risk | A very late customer. | A customer near the store when ordering. Set the earliest fire time, or start the trip when the customer says they are on the way. |

A `scheduledArrivalAt` you set replaces the auto-calculated one. When the trip has no `approachingThreshold`, Radar uses the destination geofence's `tripApproachingThreshold`, set with the [Geofences API](/api/geofences), then **Approaching threshold (minutes)** in [Trips Settings](https://dashboard.radar.com/settings#trips-settings).

### No-location fallback

If location permission is denied, place the order so that Olo fires it on its own schedule, not as a manual-fire order. If `Radar.startTrip()` keeps failing, set `scheduledArrivalAt` on the pending trip from your backend with the [Trips API](/api/trips), and confirm with your Radar account team that pending trips fire at the backup fire time for your project.

## Cancellation and completion

Olo's `OrderCancelled` webhook cancels a trip that is still pending or in progress and, with Expo updates on, `OrderPickedUp` completes it. `Radar.cancelTrip()` and `Radar.completeTrip()` change the Radar trip only, and don't cancel or close the order in Olo.

## Expo notifications

With **enable Expo updates** on and Radar added as a **Customer Arrival** partner, Radar sends **Approaching** and **Arrival** status updates to Olo Expo for orders whose GUID it knows. The **Picked Up** button in Olo Expo completes the Radar trip.

## Test the integration

In the Test environment, with the Olo sandbox:

1. Place an ASAP order for a store that has a Radar geofence. Click **View integration logs** in the **Olo** section of the Integrations page. A row shows event type `OrderPlaced` and your order ID in **External ID**.
2. On the Trips page, find the trip with that external ID and status `pending`.
3. Start the trip from a test build of your app. The status changes to `started` and the trip shows an ETA.
4. Simulate the route to the store. When the ETA drops below the approaching threshold, the status changes to `approaching`. Confirm in Olo that the order fired.

Then place a second ASAP order, start the trip, turn off location, and confirm that the order fires at the backup fire time.

## Troubleshoot delivery

| Symptom | Likely cause |
| --- | --- |
| No row in the Olo integration logs | The webhook URL or event selection is wrong, or the order's brand ID isn't the one configured in Radar. |
| A log row but no trip | The integration isn't enabled, the handoff mode is filtered out, or the brand ID is assigned to the other environment. |
| The trip has no ETA | No geofence has the destination tag and an `externalId` equal to the order's `storeNumber`. |
| The trip stays `pending` | `Radar.startTrip()` wasn't called, failed, or used an `externalId` that differs from the Olo order ID. |
| The trip is `approaching` or `arrived` but the order didn't fire | `scheduledArrivalAt` isn't set, order firing is off, the order GUID or handoff mode is missing, the earliest fire time hasn't been reached, or Olo rejected the request. The trip log on the trip's page records Olo's response to each fire attempt. |

## Operational edge cases

| Scenario | Guidance |
| --- | --- |
| Restaurant closing time | Olo can't fire an order to a closed restaurant. For ASAP orders placed close to closing time, place a normal order that Olo fires itself. |
| Menu changeover | If an order could fire after the kitchen has switched menus, for example from breakfast to lunch, place a normal order that Olo fires itself. |
| The customer is much later than expected | With auto-calculation on, Radar stops moving `scheduledArrivalAt` once the delay reaches the backup fire delay, and the order fires at the resulting backup fire time. |

## Limitations

- Radar needs `scheduledArrivalAt` to fire an order. A trip without it never fires, even when the customer arrives.
- Auto-calculation of `scheduledArrivalAt` and `approachingThreshold` applies to ASAP orders only.
- If Olo rejects a fire request, Radar tries again on later triggers, up to a limited number of attempts.
