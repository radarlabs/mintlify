<Info>
  The Segment integration is available on the [Enterprise plan](https://radar.com/pricing).
</Info>

By the end of this page, Radar is a source in your Segment workspace: each Radar update that generates events produces an `identify` call with location traits and a `track` call per event, which Segment forwards to your warehouse and destinations.

This is a server-side integration: Radar's servers call Segment. You don't need the Segment SDK in your app for Radar events to reach Segment, but your app and Radar must agree on user IDs for the events to join the right Segment user.

## Prerequisites

- A Radar project on the Enterprise plan that generates events. See [Geofencing overview and quickstart](/geofencing/overview).
- Access to the [Integrations](https://dashboard.radar.com/integrations) page in the Radar dashboard.
- A Segment workspace where you can add a source and read its write key. Use a separate source for testing so that Test events stay out of production destinations.
- A user identifier that is the same in both systems. See [User mapping](#user-mapping).

## Configuration

<Steps>
  <Step title="Add Radar as a source in Segment">
    In Segment, add Radar as a source and copy the source's write key. Repeat for a development source if you want Test events kept separate.
  </Step>
  <Step title="Enable the integration in Radar">
    On the [Integrations](https://dashboard.radar.com/integrations) page, find the **Segment** section and select **Yes** for **Enabled**. Credential fields appear.
  </Step>
  <Step title="Enter your write keys">
    Enter the production source's key in **Live write key** and the development source's key in **Test write key**. Radar uses the Live key for events from the Live environment and the Test key for events from the Test environment. If you leave a field empty, Radar sends nothing for that environment.
  </Step>
  <Step title="Save">
    Click **Save**. From now on, Radar sends each new event to Segment. Events generated before you saved aren't sent.
  </Step>
  <Step title="Connect destinations in Segment">
    In Segment, connect the Radar source to the warehouse and destinations that receive Radar events and traits.
  </Step>
</Steps>

## User mapping

### Identifiers

By default, the Radar `userId` maps to the Segment `userId` for logged-in users, and the Radar `deviceId` maps to the Segment `anonymousId`.

| Segment field | Value Radar sends |
| --- | --- |
| `userId` | `metadata.segmentUserId` when set. Otherwise the Radar `userId`. Omitted when the user has neither. |
| `anonymousId` | `metadata.segmentAnonymousId` when set. Otherwise the Radar `deviceId`. |

The Radar device ID isn't the anonymous ID that the Segment SDK generates in your app. If you want logged-out Radar events to join the same anonymous Segment user that your app tracks, pass the Segment anonymous ID to Radar. If your Segment user ID differs from the Radar `userId`, pass it too.

<CodeGroup>

```swift Swift
import RadarSDK

// Logged-out users: anonymousId is the Segment SDK's anonymous ID.
Radar.setMetadata(["segmentAnonymousId": anonymousId])

// Logged-in users whose Segment userId differs from the Radar userId.
Radar.setMetadata(["segmentUserId": userId])
```

```kotlin Kotlin
import io.radar.sdk.Radar
import org.json.JSONObject

// Logged-out users: anonymousId is the Segment SDK's anonymous ID.
Radar.setMetadata(JSONObject().put("segmentAnonymousId", anonymousId))

// Logged-in users whose Segment userId differs from the Radar userId.
Radar.setMetadata(JSONObject().put("segmentUserId", userId))
```

</CodeGroup>

Neither call is required when the default mapping fits. Call them after you [initialize the SDK](/sdk/sdk).

Radar also fills the Segment `context` of each batch:

| Radar user field | Segment context field | Sent when |
| --- | --- | --- |
| `deviceId` | `context.device.id` | The user has a `deviceId`. |
| `deviceType` | `context.device.type` | The user has a device type. The value is lowercased, for example `ios`. |
| Advertising ID | `context.device.advertisingId`, with `context.device.adTrackingEnabled` set to `true` | The device is iOS or Android, Radar has an advertising ID, and the user hasn't opted out. |
| `location.coordinates` | `context.location.latitude`, `context.location.longitude` | Always. |

## Filtering

On the [Integrations](https://dashboard.radar.com/integrations) page, click **Show advanced** in the **Segment** section.

| Field | Effect |
| --- | --- |
| **Event type allowlist** | When you select one or more event types, Radar sends only those types to Segment. With nothing selected, Radar sends every mapped event type. |
| **Request key blocklist (comma-separated)** | Removes the listed keys from the request at any depth. For example, `radar_geofence_ids,geofence_id` removes `radar_geofence_ids` from the `identify` call and `geofence_id` from the `track` call. |
| **Geofence tag blocklist (comma-separated)** | Skips events for geofences that have one of the listed tags. |

You can also filter after delivery in Segment, per destination.

## Delivery behavior

- **Requests**: For each Radar update that generates events, Radar sends one request to Segment's batch endpoint, `https://api.segment.io/v1/batch`. The batch contains the `identify` call first, then one `track` call per event. If your Segment workspace ingests through a different endpoint, ask your Radar account team whether it is supported before you enable the integration.
- **Events without a location**: Radar doesn't send an event that has no location to Segment, except trip events, which can be generated by a server-side change to a trip.
- **Timing**: Radar sends events from its servers shortly after it generates them. Segment's own processing and destination delivery times apply after that.
- **Attempts**: Radar makes one delivery attempt and waits up to 5 seconds for Segment to respond. It doesn't retry a failed request. Use the [integration logs](#troubleshoot-delivery) to find failures, and the [Events API](/api/events) if you need to backfill.
- **Deduplication**: `messageId` is the Radar event `_id`.
- **Environment**: The event's environment selects the write key. Radar doesn't send a Test event with the Live key or the reverse.

## Test the integration

<Steps>
  <Step title="Use the Test environment">
    Confirm that **Test write key** holds the key of a Segment source that you can inspect, and that the integration is saved with **Enabled** set to **Yes**.
  </Step>
  <Step title="Generate an event">
    Create a geofence in the Test environment, then send a location inside it with your Test publishable key. Replace the coordinates with a point inside your geofence:

    ```bash
    curl "https://api.radar.io/v1/track" \
      -H "Authorization: prj_test_pk_..." \
      -X POST \
      -d "deviceId=test-device-1" \
      -d "userId=user-123" \
      -d "latitude=40.78382" \
      -d "longitude=-73.97536" \
      -d "accuracy=10"
    ```

    The response includes a `user.entered_geofence` event the first time the user enters the geofence. For the parameters, see [Tracking API](/api/tracking).
  </Step>
  <Step title="Check Radar's log">
    In the **Segment** section, click **View integration logs**. Find a row for the event with the batch that Radar sent and a `200` response from Segment.
  </Step>
  <Step title="Check Segment">
    In Segment, open the debugger for the source that owns the Test write key. Confirm that the debugger shows an `identify` call for `user-123` with `radar_geofence_external_ids`, followed by a `Geofence Entered` track call with the `geofence_external_id` of your geofence.
  </Step>
</Steps>

## Troubleshoot delivery

On the [Integrations](https://dashboard.radar.com/integrations) page, click **View integration logs** in the **Segment** section. Each row shows the request and Segment's response.

| What you see | Likely cause | What to do |
| --- | --- | --- |
| No rows | No events were generated in that environment, or the integration isn't saved as enabled. | Check the Events page for the environment and the **Enabled** setting. |
| `skipped`: `Integration key(s) missing.` | The write key for the event's environment is empty. | Enter the **Test write key** or **Live write key**. |
| `skipped`: `Event type ... is not allowed.` | The event type isn't selected in **Event type allowlist**. | Select the type or clear the allowlist. |
| `skipped`: `Geofence tag '...' is blocklisted.` | The geofence's tag is in **Geofence tag blocklist**. | Remove the tag from the blocklist. |
| A `4xx` response | Segment rejected the request. | Read the response body in the log, and check that the write key belongs to the intended source. |
| A `200` response but nothing in a destination | The call reached Segment but the destination isn't connected to the Radar source, or a Segment filter dropped it. | Check the source debugger first, then the destination's settings in Segment. |
| Events on the wrong Segment user | The IDs differ between Radar and your app. | Compare `userId` and `anonymousId` in the logged request with your app's Segment calls, then set `metadata.segmentUserId` or `metadata.segmentAnonymousId`. |

## Limitations

- Radar doesn't retry failed deliveries to Segment.
- Only the event types in the [event mapping](#event-mapping) table are sent.
- You can't rename events, traits, or properties in Radar. Use the request key blocklist to drop fields, or transform them in Segment.
- Events generated before you enabled the integration aren't sent.
- The integration has no setting for the Segment ingestion endpoint.
- Traits reflect the user's state when the event was generated. Radar doesn't call `identify` when a user's state changes without generating an event.
