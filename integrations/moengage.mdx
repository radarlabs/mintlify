---
title: "MoEngage"
description: "Send Radar location events and user attributes to MoEngage to trigger and target location-based messages."
---

<Info>
  The MoEngage integration is available on the [Enterprise plan](https://radar.com/pricing).
</Info>

By the end of this page, Radar sends an event to [MoEngage](https://www.moengage.com/) for each location event it generates and updates the user's Radar attributes, and you have confirmed delivery for one test user.

Radar sends this data from its servers to the MoEngage Data API. Your app sets one metadata value so Radar knows which MoEngage user to update.

## Prerequisites

- A Radar project on the Enterprise plan, with the Radar SDK generating events. See [Detect geofence events and place visits](/geofencing/geofences-and-places).
- A MoEngage workspace, with access to its **APIs** settings page.
- The MoEngage customer ID (the unique ID you use to identify a logged-in user in MoEngage) available in your app.

## Configuration

<Steps>
  <Step title="Copy your MoEngage credentials">
    In MoEngage, open the **APIs** page and copy your Workspace ID and Data API key. If you use a separate MoEngage test environment, copy its Data API key as well.
  </Step>
  <Step title="Enter the settings in Radar">
    In the Radar dashboard, open the [Integrations](https://dashboard.radar.com/integrations) page, find the **MoEngage** section, and select **Yes** for **Enabled**. Enter these values:

    | Field | Value |
    | --- | --- |
    | **API endpoint** | The Data API host for your MoEngage data center. The default is `https://api-01.moengage.com/v1`. Select the endpoint for your MoEngage data center if it is different. |
    | **Test Data API key** | Required. The Data API key used for events from the Test environment. |
    | **Live Data API key** | Required. The Data API key used for events from the Live environment. |
    | **Workspace ID** | Required. Your MoEngage Workspace ID. |
    | **Update existing only** | When **Yes**, Radar asks MoEngage to update only users that already exist. |

    Click **Save**. The form doesn't save while the integration is enabled and any required field is empty.
  </Step>
  <Step title="Set the MoEngage customer ID in your app">
    Set the metadata described in [Identity mapping](#identity-mapping).
  </Step>
</Steps>

For events from the Test environment, Radar appends `_DEBUG` to the Workspace ID in the request, so Test and Live events are addressed to different MoEngage workspaces. Confirm in MoEngage where test data for your workspace appears before you test.

## Identity mapping

| Radar value | Sent to MoEngage as | Required |
| --- | --- | --- |
| `metadata["moengage:customer_id"]` | `customer_id` on the event and customer requests | Yes. Without it, Radar skips the event and logs `Identifier missing.` |
| `deviceId` | `device_id` on the event request | Sent automatically |

Radar doesn't use the Radar `userId` to identify a MoEngage user. Set the metadata to the same unique ID you pass to the MoEngage SDK when the user logs in:

<CodeGroup>

```swift Swift
import RadarSDK

Radar.setMetadata(["moengage:customer_id": "user-123"])
```

```kotlin Kotlin
import io.radar.sdk.Radar
import org.json.JSONObject

Radar.setMetadata(JSONObject().put("moengage:customer_id", "user-123"))
```

</CodeGroup>

`Radar.setMetadata()` replaces the whole metadata object, so include any other metadata keys you use in the same call. When the user logs out or changes, update the metadata so events stop going to the previous user.

## Filtering

The **MoEngage** section of the [Integrations](https://dashboard.radar.com/integrations) page has these filters:

| Setting | Effect |
| --- | --- |
| **Event type allowlist** | Radar sends only the selected event types. Check this list first when an event you expect is missing. |
| **Request key blocklist** | Keys to remove from the requests, for example `radar_geofence_ids`. Applies to user attributes and event attributes. |
| **Geofence tag blocklist** | Geofence tags. Radar skips events for geofences with these tags. |

For the filters that every event integration shares, see [Filters](/integrations/integrations#filters).

## Delivery behavior

- Radar sends to MoEngage only when it generates an event for the user. A location update that produces no event doesn't update user attributes.
- Each batch of Radar events produces two MoEngage requests: an event request that carries all events in the batch, then a customer request that carries the user attributes.
- Delivery is asynchronous and doesn't block the SDK.
- Radar sends each request once. It doesn't retry a request that MoEngage rejects or that times out. Both outcomes are recorded in the integration logs.
- Events from the Test environment use the Test Data API key and the Workspace ID with `_DEBUG` appended. Events from the Live environment use the Live Data API key and the Workspace ID as entered.

## Verify integration data delivery

<Steps>
  <Step title="Prepare a test user">
    On a test device, set `moengage:customer_id` in Radar metadata to the ID of a user that exists in MoEngage.
  </Step>
  <Step title="Generate an event">
    Generate an event for that user. Either open the [Simulator](https://dashboard.radar.com/geofencing/simulate) page, choose the user, and move it into a geofence, or use a test build of your app and enter the geofence.
  </Step>
  <Step title="Check Radar's log">
    On the [Events](https://dashboard.radar.com/geofencing/events) page, click **View** on the new event and find the **Logs** section. Confirm that it shows two MoEngage requests, one to the event endpoint and one to the customer endpoint, each with a `2xx` response.
  </Step>
  <Step title="Check MoEngage">
    In MoEngage, open the user's profile in the environment that matches the Radar environment you tested, and confirm the `[Radar] Geofence Entered` event and the `radar_geofence_tags` attribute.
  </Step>
</Steps>

## Troubleshoot delivery

Click **View integration logs** in the **MoEngage** section of the [Integrations](https://dashboard.radar.com/integrations) page. Each row shows the timestamp, the request URL, and the response code, and expands to the request and response bodies. New rows can take a few minutes to appear.

| Log response | Meaning |
| --- | --- |
| `skipped`: `Integration key(s) missing.` | No Data API key for the event's environment. |
| `skipped`: `Identifier missing.` | The user has no `moengage:customer_id` metadata, or the Workspace ID is empty. |
| `skipped`, "Event type ... isn't allowed." | The event type isn't selected in the allowlist. |
| `skipped`: `Geofence tag '...' is blocklisted.` | The geofence tag is in the blocklist. |
| A `4xx` response | MoEngage rejected the request. The response body in the log gives the reason. Check the Data API key, the Workspace ID, and the API endpoint for your data center. |
| `2xx`, but no data on the user | Check that you are looking at the matching MoEngage environment, that the customer ID matches, and the **Update existing only** setting. |

## Limitations

- A user without `moengage:customer_id` metadata is skipped. The Radar `userId` alone isn't enough.
- User attributes are updated only when an event is generated, so `radar_updated_at` can be older than the user's last location update.
- Empty attributes are sent as the string `"(null)"`.
- Top chain attributes aren't sent to MoEngage.
- There is no automatic retry. A request that fails during a MoEngage outage isn't resent.
