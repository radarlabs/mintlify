<Info>
  The Amplitude integration is available on the [Enterprise plan](https://radar.com/pricing).
</Info>

By the end of this page, each Radar event for your project appears in Amplitude as a `[Radar]` event on the matching user, with Radar's [location context](/fundamentals/context-types) as user properties.

Use the integration to add location context to behavioral analytics, measure location-based features, and build location-based cohorts. It is a server-side integration: Radar's servers call Amplitude, and you add no Amplitude code to your Radar setup.

## Prerequisites

- A Radar project on the Enterprise plan that generates events. See [Geofencing overview and quickstart](/geofencing/overview).
- Access to the [Integrations](https://dashboard.radar.com/integrations) page in the Radar dashboard.
- An Amplitude project and permission to view its API key. Use a separate Amplitude project for testing if you have one.
- A user identifier that is the same in both systems. See [User mapping](#user-mapping).

## Configuration

<Steps>
  <Step title="Copy your Amplitude API key">
    In Amplitude, open the settings for your project and copy its API key. If you have a separate development project, copy that key too.
  </Step>
  <Step title="Enable the integration in Radar">
    On the [Integrations](https://dashboard.radar.com/integrations) page, find the **Amplitude** section and select **Yes** for **Enabled**. Credential fields appear.
  </Step>
  <Step title="Enter your keys">
    Enter the production key in **Live API key** and the development key in **Test API key**. Radar uses the Live key for events from the Live environment and the Test key for events from the Test environment. If you leave a field empty, Radar sends nothing for that environment.
  </Step>
  <Step title="Save">
    Click **Save**. From now on, Radar sends each new event to Amplitude. Events generated before you saved aren't sent.
  </Step>
</Steps>

### Optional settings

Click **Show advanced** in the **Amplitude** section to show these settings:

| Setting | Effect |
| --- | --- |
| **Event type allowlist**, **Request key blocklist**, **Geofence tag blocklist** | See [Filtering](#filtering). |
| **Use identify API** | When set to **Yes**, Radar also calls Amplitude's Identify API on each delivery to update the user's properties, including when every event in the delivery was filtered out. When set to **No**, user properties are sent only as part of each event. |
| **Use cohort API for Segments** | Uses Amplitude's cohort API to apply Radar segments to the user. Additional Amplitude fields appear when you select **Yes**. |

## User mapping

### Identifiers

Radar sets these fields on every event it sends to Amplitude:

| Radar user field | Amplitude field | Sent when |
| --- | --- | --- |
| `userId` | `user_id` | The Radar user has a `userId`. |
| `deviceId` | `device_id` | The Radar user has a `deviceId`. |
| `deviceId` | `idfv` | The device type is iOS. |
| `deviceId` | `android_id` | The device type is Android. |
| `ip` | `ip` | Radar has an IP address for the user. |

For Radar events to attach to the users that your app already tracks in Amplitude, set the Radar `userId` to the same value that you use as the Amplitude user ID. Set it after login with `Radar.setUserId()`. See [SDK overview and compatibility](/sdk/sdk). Events for a user without a `userId` are sent with the device identifiers only.

## Filtering

On the [Integrations](https://dashboard.radar.com/integrations) page, click **Show advanced** in the **Amplitude** section.

| Field | Effect |
| --- | --- |
| **Event type allowlist** | When you select one or more event types, Radar sends only those types to Amplitude. With nothing selected, Radar sends every event type. |
| **Request key blocklist (comma-separated)** | Removes the listed keys from the request at any depth. For example, `ip,[Radar] Place Name` removes the IP address and one user property. |
| **Geofence tag blocklist (comma-separated)** | Skips events for geofences that have one of the listed tags. |

Radar forwards every event type that passes the filters, including types that aren't in the [event mapping](#event-mapping) table. To keep unmapped event types out of Amplitude, select only the types you want in **Event type allowlist**.

## Delivery behavior

- **Endpoint**: Radar sends events to Amplitude's HTTP API at `https://api.amplitude.com/httpapi`, and Identify calls to `https://api2.amplitude.com/identify`. If your Amplitude project ingests through a different endpoint, ask your Radar account team whether it is supported before you enable the integration.
- **Batching**: The events from one Radar update are sent together in one request.
- **Timing**: Radar sends events from its servers shortly after it generates them. Amplitude's own processing time applies after that.
- **Attempts**: Radar makes one delivery attempt and waits up to 5 seconds for Amplitude to respond. It doesn't retry a failed request. Use the [integration logs](#troubleshoot-delivery) to find failures, and the [Events API](/api/events) if you need to backfill.
- **Deduplication**: `insert_id` is the Radar event `_id`, so the same Radar event always carries the same `insert_id`.
- **Environment**: The event's environment selects the key. Radar doesn't send a Test event with the Live key or the reverse.

## Test the integration

<Steps>
  <Step title="Use the Test environment">
    Confirm that **Test API key** holds the key of an Amplitude project that you can inspect, and that the integration is saved with **Enabled** set to **Yes**.
  </Step>
  <Step title="Generate an event">
    Create a geofence in the Test environment, then send a location inside it with your Test publishable key. Replace the coordinates with a point inside your geofence:

    ```bash
    curl "https://api.radar.io/v1/track" \
      -H "Authorization: prj_test_pk_..." \
      -X POST \
      -d "deviceId=test-device-1" \
      -d "userId=user-123" \
      -d "deviceType=iOS" \
      -d "latitude=40.78382" \
      -d "longitude=-73.97536" \
      -d "accuracy=10"
    ```

    The response includes a `user.entered_geofence` event the first time the user enters the geofence. For the parameters, see [Tracking API](/api/tracking).
  </Step>
  <Step title="Check Radar's log">
    In the **Amplitude** section, click **View integration logs**. Find a row for the event with the request that Radar sent and a `200` response from Amplitude.
  </Step>
  <Step title="Check Amplitude">
    In Amplitude, look up the user `user-123` in the project that owns the Test key. Confirm that the user has a `[Radar] Geofence Entered` event with the `Geofence External ID` of your geofence, and `[Radar] Geofence External IDs` in the user's properties.
  </Step>
</Steps>

## Troubleshoot delivery

On the [Integrations](https://dashboard.radar.com/integrations) page, click **View integration logs** in the **Amplitude** section. Each row shows the request and Amplitude's response. Radar redacts the API key in the logged request.

| What you see | Likely cause | What to do |
| --- | --- | --- |
| No rows | No events were generated in that environment, or the integration isn't saved as enabled. | Check the Events page for the environment and the **Enabled** setting. |
| `skipped`: `Integration key(s) missing.` | The key for the event's environment is empty. | Enter the **Test API key** or **Live API key**. |
| `skipped`: `Event type ... is not allowed.` | The event type isn't selected in **Event type allowlist**. | Select the type or clear the allowlist. |
| `skipped`: `Geofence tag '...' is blocklisted.` | The geofence's tag is in **Geofence tag blocklist**. | Remove the tag from the blocklist. |
| A `4xx` response | Amplitude rejected the request. | Read the response body in the log. If it reports an invalid API key, copy the key again from the correct Amplitude project. |
| A `200` response but no event on the expected user | The identifiers differ between Radar and Amplitude. | Compare the `user_id` and `device_id` in the logged request with the Amplitude user. |

## Limitations

- Radar doesn't retry failed deliveries to Amplitude.
- You can't rename events or properties. Use the request key blocklist to drop properties you don't want.
- Events generated before you enabled the integration aren't sent.
- The integration has no setting for the Amplitude ingestion endpoint.
- User properties reflect the user's state when the event was generated. Radar doesn't update Amplitude when a user's state changes without generating an event.
