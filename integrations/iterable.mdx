<Info>
  The Iterable integration is available on the [Enterprise plan](https://radar.com/pricing).
</Info>

By the end of this page, Radar sends a custom event to [Iterable](https://iterable.com) for each location event it generates and updates the user's Radar data fields, and you have confirmed delivery for one test user.

Radar sends this data from its servers to the Iterable API at `https://api.iterable.com/api`. Your app only needs to make sure Radar and Iterable agree on the user ID.

## Prerequisites

- A Radar project on the Enterprise plan, with the Radar SDK generating events. See [Detect geofence events and place visits](/geofencing/geofences-and-places).
- An Iterable project, with permission to create API keys.
- Users identified in Iterable by `userId`. Radar sends a `userId`, not an email address.

## Configuration

<Steps>
  <Step title="Create an Iterable API key">
    In Iterable, open the **API Keys** page, create a Mobile API key, and copy it. Create a second key in your test project if you keep test data separate.
  </Step>
  <Step title="Enter the keys in Radar">
    In the Radar dashboard, open the [Integrations](https://dashboard.radar.com/integrations) page, find the **Iterable** section, and select **Yes** for **Enabled**. Enter the keys in **Live API key** and **Test API key**, then click **Save**.
  </Step>
  <Step title="Align user IDs in your app">
    Make the Radar user ID match the Iterable user ID, or set the Iterable user ID in Radar metadata. See [Identity mapping](#identity-mapping).
  </Step>
</Steps>

## Identity mapping

Radar picks the Iterable `userId` in this order:

| Priority | Radar value | Sent to Iterable as |
| --- | --- | --- |
| 1 | `metadata["iterable:user_id"]` | `userId` |
| 2 | `userId` | `userId` |

If neither is set, Radar skips the event and logs `Identifier missing.` Anonymous Radar users aren't sent to Iterable.

The simplest setup uses the same ID in both SDKs:

<CodeGroup>

```swift Swift
import RadarSDK

// The Iterable call depends on your Iterable SDK version.
IterableAPI.userId = userId
Radar.setUserId(userId)
```

```kotlin Kotlin
import io.radar.sdk.Radar

// The Iterable call depends on your Iterable SDK version.
IterableApi.getInstance().setUserId(userId)
Radar.setUserId(userId)
```

</CodeGroup>

If your Iterable user ID differs from your Radar user ID, set it in Radar metadata. Radar then uses this value as the Iterable `userId`.

<CodeGroup>

```swift Swift
import RadarSDK

Radar.setMetadata(["iterable:user_id": iterableUserId])
```

```kotlin Kotlin
import io.radar.sdk.Radar
import org.json.JSONObject

Radar.setMetadata(JSONObject().put("iterable:user_id", iterableUserId))
```

</CodeGroup>

`Radar.setMetadata()` replaces the whole metadata object, so include any other metadata keys you use in the same call. When the user logs out or changes, update the user ID or metadata so events stop going to the previous user.

## Filtering

On the [Integrations](https://dashboard.radar.com/integrations) page, click **Show advanced** in the **Iterable** section.

| Setting | Effect |
| --- | --- |
| **Event type allowlist** | Radar sends only the selected event types. Check this list first when an event you expect is missing. |
| **Request key blocklist** | Comma-separated keys to remove from the requests, for example `radarGeofenceIds,geofenceId`. Applies to user data fields and event data fields. |
| **Geofence tag blocklist** | Comma-separated geofence tags. Radar skips events for geofences with these tags. |

For the filters that every event integration shares, see [Filters](/integrations/integrations#filters).

## Delivery behavior

- Radar sends to Iterable only when it generates an event for the user. A location update that produces no event doesn't update user data fields.
- Each batch of Radar events produces one `users/update` request and one `events/track` request per event. The requests are sent in parallel, so the event can reach Iterable before the user update does.
- Delivery is asynchronous and doesn't block the SDK.
- Radar sends each request once. It doesn't retry a request that Iterable rejects or that times out. The outcome is recorded in the integration logs.
- Events from the Test environment use the Test API key, and events from the Live environment use the Live API key.

<Steps>
  <Step title="Prepare a test user">
    Choose a Radar user whose `userId`, or `iterable:user_id` metadata, matches a user in your Iterable project.
  </Step>
  <Step title="Generate an event">
    Generate an event for that user. Either open the [Simulator](https://dashboard.radar.com/geofencing/simulate) page, choose the user, and move it into a geofence, or use a test build of your app and enter the geofence.
  </Step>
  <Step title="Check Radar's log">
    On the [Events](https://dashboard.radar.com/geofencing/events) page, click **View** on the new event and find the **Logs** section. Confirm that it shows Iterable requests to `users/update` and `events/track`, each with a `2xx` response.
  </Step>
  <Step title="Check Iterable">
    In Iterable, open the user and confirm the `radarGeofenceEntered` event and the `radarGeofenceTags` data field.
  </Step>
</Steps>

## Troubleshoot delivery

Click **View integration logs** in the **Iterable** section of the [Integrations](https://dashboard.radar.com/integrations) page. Each row shows the timestamp, the request URL, and the response code, and expands to the request and response bodies. New rows can take a few minutes to appear.

| Log response | Meaning |
| --- | --- |
| `skipped`: `Integration key(s) missing.` | No API key for the event's environment. |
| `skipped`: `Identifier missing.` | The user has neither a `userId` nor `iterable:user_id` metadata. |
| `skipped`, "Event type ... isn't allowed." | The event type isn't selected in the allowlist. |
| `skipped`: `Geofence tag '...' is blocklisted.` | The geofence tag is in the blocklist. |
| A `4xx` response | Iterable rejected the request. The response body in the log gives the reason. Check the API key and its project. |
| `2xx`, but the data is on a different user | The Radar and Iterable user IDs don't match. See [Identity mapping](#identity-mapping). |

## Example use cases

Menu names in Iterable can change. If a label in these steps doesn't match what you see, follow Iterable's documentation.

### Send a personalized push notification when user is near a store

This campaign sends a push notification when a user enters a Radar geofence around a store.

#### Configure geofences in Radar

1. Create [geofences](/geofencing/geofences-and-places) around your stores. For a "nearby" campaign, a radius of a few hundred meters is a common starting point. You can also use isochrone geofences, which cover every point within a travel time such as a 10-minute walk.
2. Note the tag you gave those geofences. Tags are listed on the [Geofences](https://dashboard.radar.com/geofencing/geofences) page.

#### Create a new Journey in Iterable

3. In Iterable, open [Journeys](https://app.iterable.com/workflows) and click **New journey**.
4. Open the start node and change the trigger to **Triggered Custom Event**. For the event name, choose `radarGeofenceEntered`.
5. For **Use Filter**, select **Yes**.
6. For the property, choose `radarGeofenceEntered.geofenceTag`, select the **Contains** operator, and enter your geofence tag.
7. Click **Update Node**.
8. Add a **Send Push** node and connect the start node to it.

#### Set up a push notification template in Iterable

9. Under **Content**, open **Templates** and create a new push template.
10. To include the store name, put `{{radarGeofenceEntered.geofenceDescription}}` in the title or body. This is Iterable's Handlebars syntax for event data fields.
11. Save the template.
12. Back in the journey, open the **Send Push** node and select the template.

#### Test your campaign

Enter the geofence on a test device, or open the [Users](https://dashboard.radar.com/geofencing/users) page, select a user who also exists in Iterable with the same user ID, and click **Simulate**. Move the simulated user into a geofence with your tag. The notification arrives on that user's device.

### Filter users in an Iterable Journey whose last known location is X minutes away from a store

This campaign sends a push notification to users who opened a specific email and whose last known location is within a 10-minute drive of a store.

1. In Radar, create isochrone geofences with a 10-minute drive time around your stores, and note their tag.
2. In Iterable, create a journey whose start node is triggered by **Opened An Email** for the campaign you choose.
3. Add a **Fields Match** filter node below the start node. For the property, choose the contact property `radarGeofenceTags`, select the **Contains** operator, and enter your geofence tag. Connect the start node to the filter node.
4. Create a push template, add a **Send Push** node that uses it, and connect the filter node's **Yes** branch to it.
5. Test as in the previous example. The filter uses the user's data fields, which reflect the geofences the user was in at their last Radar event.

## Limitations

- Radar sends to `https://api.iterable.com/api`. There is no setting for another Iterable API host.
- Users are identified by `userId` only. Radar doesn't send an email address.
- User data fields are updated only when an event is generated, so `radarUpdatedAt` can be older than the user's last location update.
- Empty fields are sent as the string `"(null)"`.
- There is no automatic retry. A request that fails during an Iterable outage isn't resent.
