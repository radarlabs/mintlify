---
title: "Webhooks"
description: "Receive Radar events and user state at your own HTTP endpoint, verify the signature, and handle retries and duplicates safely."
---

Your backend receives a `POST` request from Radar each time Radar generates an event, verifies that the request came from Radar, and processes each event once. Use webhooks to store events, trigger backend workflows, or forward Radar data to a platform that has no [native integration](/integrations/integrations).

## Prerequisites

- A Radar project that generates events. See [Geofencing overview and quickstart](/geofencing/overview).
- An HTTP endpoint that accepts `POST` requests with a JSON body and that Radar can reach from the public internet. A webhook for the Live environment needs an `https://` URL.

## Configuration

<Steps>
  <Step title="Create the webhook">
    On the [Integrations](https://dashboard.radar.com/integrations) page, find the **Webhooks** section and click **New**.
  </Step>
  <Step title="Choose the environment and URL">
    For **Environment**, select **Test** or **Live**. A webhook receives events from one environment only, so create one per environment. Enter your endpoint in **URL**.
  </Step>
  <Step title="Choose the event delivery mode">
    For **Event delivery**, select **Single event** to receive one event per request, or **Multiple events** to receive the events from one update together.
  </Step>
  <Step title="Save and copy the security token">
    Click **Create**. The webhook appears in the **Webhooks** table. Copy its **Security token** and store it as a secret on your backend.
  </Step>
</Steps>

Radar sends each event to every enabled webhook for that environment. To limit what a webhook receives, see [Filters](/integrations/integrations#filters). To pause a webhook, select **No** for **Enabled**.

The dialog also has a **Headers** field for up to 10 static headers, and on some accounts a **Type** field with the **Case Events** and **Locations** types. Both are account-specific. Standard HTTP headers such as `Content-Type` and `Host`, and `X-Radar-Signature`, aren't allowed.

## Request format

Radar sends a `POST` request with `Content-Type: application/json` and these headers:

| Header | Value |
| --- | --- |
| `X-Radar-Signing-Id` | The ID that the signature is computed from. |
| `X-Radar-Signature` | A hex-encoded HMAC-SHA1 of the `X-Radar-Signing-Id` value, keyed with the webhook's security token. |

With **Single event**, the body has an `event` object and a `user` object, and Radar sends one request per event:

```json
{
  "event": {
    "_id": "56db1f4613012711002229f6",
    "type": "user.entered_geofence",
    "createdAt": "2026-06-12T13:44:10.535Z",
    "actualCreatedAt": "2026-06-12T13:44:10.535Z",
    "live": false,
    "user": {
      "_id": "56db1f4613012711002229f4",
      "userId": "user-123",
      "deviceId": "C305F2DB-56DC-404F-B6C1-BC52F0B680D8"
    },
    "geofence": {
      "_id": "56db1f4613012711002229fb",
      "tag": "store",
      "externalId": "store-42",
      "description": "Store #42",
      "metadata": {
        "parking": false
      }
    },
    "location": {
      "type": "Point",
      "coordinates": [-73.977797, 40.783826]
    },
    "locationAccuracy": 5,
    "confidence": 3,
    "foreground": true
  },
  "user": {
    "_id": "56db1f4613012711002229f4",
    "live": false,
    "userId": "user-123",
    "deviceId": "C305F2DB-56DC-404F-B6C1-BC52F0B680D8",
    "metadata": {
      "loyaltyTier": "gold"
    },
    "updatedAt": "2026-06-12T13:44:10.535Z",
    "location": {
      "type": "Point",
      "coordinates": [-73.977797, 40.783826]
    },

    "locationAuthorization": "GRANTED_FOREGROUND",

    "geofences": [
      {
        "_id": "56db1f4613012711002229fb",
        "tag": "store",
        "externalId": "store-42",
        "description": "Store #42"
      }

  }

```

With **Multiple events**, the body has the same `user` object and an `events` array in place of `event`. When an update generates more than 5 events, Radar can split them into groups of 5 and send each group in its own request.

- `user` is the user's state after the update that generated the events. It carries more [context](/fundamentals/context-types) when the matching features are enabled, for example `place`, `country`, `state`, `dma`, `postalCode`, `segments`, `topChains`, `trip`, `beacons`, and `fraud`. Ignore fields you don't use, so that new fields don't break your parser.
- Coordinates are GeoJSON, so longitude comes before latitude.
- Geofence geometry isn't included. Look a geofence up with the [Geofences API](/api/geofences) if you need its shape.

For every field, see the [Events API](/api/events) and the [Users API](/api/users).

### Case event payload

A webhook with **Type** set to **Case Events** sends `case.opened`, `case.updated`, and `case.closed` events for Fraud cases, with an `event` object (or an `events` array) and no `user` object:

```json
{
  "event": {
    "_id": "69aee5fc9b08c3f147dc12b0",
    "type": "case.opened",
    "case": {
      "_id": "69aee5fc8581c72e89dfe90e",
      "ruleId": "68deb69ced45959e3208bd94",
      "ruleType": "example_rule_type",
      "associatedUserIds": ["user-123", "user-456"],
      "associatedDeviceIds": ["C305F2DB-56DC-404F-B6C1-BC52F0B680D8"]
    },
    "createdAt": "2026-06-12T13:44:10.535Z"
  }
}
```

`ruleId` and `ruleType` identify the rule that triggered the case. The `ruleType` value above is a placeholder.

## Verify the signature

Each webhook has a security token: a random 40-character hex string that Radar generates when you create the webhook. Radar computes an HMAC-SHA1 of the signing ID, using the security token as the key, and sends the hex digest in `X-Radar-Signature`. The signing ID, sent in `X-Radar-Signing-Id`, depends on the request:

| Request | Signing ID |
| --- | --- |
| **Single event** | The `_id` of the event. |
| **Multiple events** | The `_id` of the first event in the `events` array. |
| **Case Events** | The `_id` of the case (of the first case with **Multiple events**). |
| **Locations** | The `_id` of the user. |

Compute the same HMAC from the `X-Radar-Signing-Id` header and compare it with `X-Radar-Signature`:

```javascript
const crypto = require('crypto');
const express = require('express');

const app = express();
app.use(express.json());

// Load the security token from your secret store. Never hard-code it.
const RADAR_WEBHOOK_TOKEN = process.env.RADAR_WEBHOOK_TOKEN;

function isFromRadar(req) {
  const signingId = req.get('X-Radar-Signing-Id');
  const signature = req.get('X-Radar-Signature');
  if (!signingId || !signature) {
    return false;
  }

  const expected = crypto
    .createHmac('sha1', RADAR_WEBHOOK_TOKEN)
    .update(signingId)
    .digest('hex');

  const a = Buffer.from(signature, 'utf8');
  const b = Buffer.from(expected, 'utf8');
  return a.length === b.length && crypto.timingSafeEqual(a, b);
}

app.post('/webhooks/radar', (req, res) => {
  if (!isFromRadar(req)) {
    return res.sendStatus(401);
  }

  // For Single event and Case Events webhooks, also check that the signed ID
  // matches the body. Use req.body.events[0]._id for Multiple events.
  const signingId = req.get('X-Radar-Signing-Id');
  const event = req.body.event;
  const bodyId = event && (event.case ? event.case._id : event._id);
  if (bodyId !== signingId) {
    return res.sendStatus(400);
  }

  // Acknowledge first, then process asynchronously.
  res.sendStatus(200);
  enqueueForProcessing(req.body);
});

function enqueueForProcessing(body) {
  // Hand the payload to your own queue or worker.
}

app.listen(3000);
```

The signature proves that the sender knows your security token. It is computed from the signing ID only: it doesn't cover the rest of the body and it has no timestamp. So:

- Compare signatures with a constant-time function.
- Check that the signing ID matches the corresponding ID in the body, and serve your endpoint over HTTPS so that the body can't be altered in transit.
- Process each event ID once, because a captured request stays valid if it is sent again.

## Delivery behavior

Return a `2xx` status code to acknowledge a request. Radar waits 5 seconds for a response by default, so acknowledge as soon as you have verified and stored the request, and do slow work afterward.

| Your response | How Radar treats it |
| --- | --- |
| `2xx` | Delivered. |
| `429`, any `5xx`, a connection error, or no response before the timeout | Failed. Eligible for retry when retries are enabled for your project. |
| Any other status, including `3xx` and `4xx` | Not delivered and not retried. Don't use a `4xx` to ask for redelivery. |

### Retries

Retries are off unless your Radar account team enables them for your project. Without them, each request gets one delivery attempt. When retries are enabled:

- Radar queues the failed request again with the same body, so every event keeps its `_id`.
- For **Single event** webhooks, Radar retries only the event whose request failed. For **Multiple events** webhooks, it retries the whole request.
- If your response includes a `Retry-After` header, in seconds or as an HTTP date, Radar waits that long before the next attempt, up to a maximum of 900 seconds.

A failed delivery doesn't remove the event from Radar. Within your project's data retention period, you can backfill from the [Events API](/api/events).

### Ordering and duplicates

Radar doesn't guarantee the order in which requests arrive. Order events by `createdAt`, when the event occurred, or `actualCreatedAt`, when Radar's server created it, which is later when a device replays a location. Compare `user.updatedAt` before you overwrite stored user state.

Radar doesn't deduplicate deliveries and doesn't send a separate idempotency key. You can receive an event more than once when a delivery is retried, when two webhooks point at the same endpoint, or when you rotate a token. Use the event `_id` as the idempotency key: insert it into a store with a unique constraint, process the event only if the insert succeeds, and return `2xx` either way. With **Multiple events**, do this per event, not per request.

## Rotate the security token

Editing a webhook doesn't change its token, and the dashboard can't regenerate it. To rotate a token, replace the webhook:

1. Create a second webhook with the same environment, URL, event delivery mode, and filters. It gets a new security token.
2. Update your endpoint to accept a signature from either token.
3. Confirm in the integration logs that deliveries from the new webhook succeed.
4. Open the old webhook's row menu and select **Delete webhook**, then remove the old token from your endpoint.

While both webhooks exist, your endpoint receives every event twice.

## Test the integration

In the **Webhooks** table, open the row menu for your webhook and select **Test webhook**. Radar sends a signed sample request to your URL, and the dashboard reports `Webhook responded with a status of 200.`, with the status code that your endpoint returned, or `Webhook did not respond.` The sample user has a `userId` of `1`. A **Single event** webhook receives one `user.entered_geofence` event, and a **Multiple events** webhook receives one geofence event and one place event. Sample deliveries reuse the same event IDs each time.

To check that your endpoint rejects a bad signature, sign a request yourself, then change one character of the signature and confirm that the response changes from `200` to `401`:

```bash
SIGNING_ID="56db1f4613012711002229f6"
TOKEN="your-webhook-security-token"
SIGNATURE=$(printf '%s' "$SIGNING_ID" | openssl dgst -sha1 -hmac "$TOKEN" | awk '{print $NF}')

curl -i "https://example.com/webhooks/radar" \
  -X POST \
  -H "Content-Type: application/json" \
  -H "X-Radar-Signing-Id: $SIGNING_ID" \
  -H "X-Radar-Signature: $SIGNATURE" \
  -d '{"event":{"_id":"56db1f4613012711002229f6","type":"user.entered_geofence"},"user":{"userId":"user-123"}}'
```

## Troubleshoot delivery

Click **View integration logs** in the **Webhooks** section, or in a webhook's row menu to see the deliveries for that URL only. Besides the shared [skip reasons](/integrations/integrations#troubleshoot-delivery), webhooks have these:

| What you see | Likely cause | What to do |
| --- | --- | --- |
| `skipped` with `Invalid URL.` | The URL didn't pass Radar's validation, for example because it doesn't resolve to a public address. | Use a publicly reachable URL. |
| A timeout or connection error | Your endpoint didn't respond in time or refused the connection. | Check availability and firewall rules, and acknowledge before doing slow work. |
| A `401` or `403` from your endpoint | Your signature check or another auth layer rejected the request. | Confirm that you use the token of this webhook and compute the HMAC from `X-Radar-Signing-Id`. |

## Limitations

- A webhook delivers only when an event is generated. To receive every location update, you need the account-specific **Locations** webhook type.
- A webhook belongs to one project and one environment.
