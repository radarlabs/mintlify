<Info>
  The Cordial integration is available on the [Enterprise plan](https://radar.com/pricing).
</Info>

By the end of this page, Radar sends contact activities and updated contact attributes to [Cordial](https://cordial.com) each time it generates a location event for a user, and you have confirmed delivery for one test contact.

Radar sends this data from its servers to Cordial's asynchronous API. Your app sets one metadata value so Radar knows which Cordial contact to update.

## Prerequisites

- A Radar project on the Enterprise plan, with the Radar SDK generating events. See [Detect geofence events and place visits](/geofencing/geofences-and-places).
- A Cordial account, with permission to create API keys.
- A contact identifier that your app knows. This is either the Cordial contact ID or a secondary key that the Cordial team has created for your contacts, for example `emailHash`.
- Your Cordial async API endpoint, for example `https://integrations-ingest-svc.usw2.cordial.com`.

## Configuration

<Steps>
  <Step title="Create a Cordial API key">
    In Cordial, open the **API Keys** page and create an API key with **Contact Activities** permissions. Copy it.
  </Step>
  <Step title="Agree on a contact identifier">
    If your app doesn't have the Cordial contact ID, ask the Cordial team to create a secondary key for contacts, such as `emailHash`, that your app can pass to Radar.
  </Step>
  <Step title="Enter the settings in Radar">
    In the Radar dashboard, open the [Integrations](https://dashboard.radar.com/integrations) page, find the **Cordial** section, and select **Yes** for **Enabled**. Enter these values:

    | Field | Value |
    | --- | --- |
    | **Async API endpoint** | Required. Your Cordial async API endpoint, without a trailing path. Radar posts to `/api/createContactactivities` on this host. |
    | **Live API key** | The API key for events from the Live environment. |
    | **Test API key** | The API key for events from the Test environment. |
    | **Cordial secondary key** | The name of the secondary key, for example `emailHash`. Leave empty if you identify contacts by Cordial contact ID only. |

    Click **Save**.
  </Step>
  <Step title="Set the contact identifier in your app">
    Set the metadata described in [Identity mapping](#identity-mapping).
  </Step>
</Steps>

## Identity mapping

Radar doesn't use the Radar `userId` to identify a Cordial contact. It picks the identifier in this order:

| Priority | Radar value | Sent to Cordial as |
| --- | --- | --- |
| 1 | `metadata.cordialId` | The `cID` contact identifier |
| 2 | `metadata["cordial:{secondaryKey}"]`, where `{secondaryKey}` is the **Cordial secondary key** setting | The secondary key identifier, for example `emailHash` |

If neither is set, Radar skips the event and logs `Identifier missing.`

For example, if your secondary key is `emailHash`:

<CodeGroup>

```swift Swift
import RadarSDK

Radar.setMetadata(["cordial:emailHash": emailHash])
```

```kotlin Kotlin
import io.radar.sdk.Radar
import org.json.JSONObject

Radar.setMetadata(JSONObject().put("cordial:emailHash", emailHash))
```

</CodeGroup>

The metadata key must match the setting exactly, including case. `Radar.setMetadata()` replaces the whole metadata object, so include any other metadata keys you use in the same call. When the user logs out or changes, update the metadata so events stop going to the previous contact.

Radar marks the contact as updatable in each request, so attributes are written to a contact that already exists.

## Filtering

On the [Integrations](https://dashboard.radar.com/integrations) page, click **Show advanced** in the **Cordial** section.

| Setting | Effect |
| --- | --- |
| **Event type allowlist** | Radar sends only the selected event types. Check this list first when an activity you expect is missing. |
| **Request key blocklist** | Comma-separated keys to remove from the request, for example `radar_geofence_ids,geofence_id`. Applies to contact attributes and activity properties. |
| **Geofence tag blocklist** | Comma-separated geofence tags. Radar skips events for geofences with these tags. |

For the filters that every event integration shares, see [Filters](/integrations/integrations#filters).

## Delivery behavior

- Radar sends to Cordial only when it generates an event for the user. A location update that produces no event doesn't update contact attributes.
- Events generated by one location update are sent together in one request, with the contact attributes.
- Delivery is asynchronous and doesn't block the SDK. Radar posts to Cordial's asynchronous API, so a `2xx` response in the Radar logs means Cordial accepted the request.
- Radar sends each request once. It doesn't retry a request that Cordial rejects or that times out. The outcome is recorded in the integration logs.
- Events without a location aren't sent.
- Events from the Test environment use the Test API key, and events from the Live environment use the Live API key. Both use the same endpoint and secondary key.

## Verify integration data delivery

<Steps>
  <Step title="Prepare a test contact">
    On a test device, set the contact identifier in Radar metadata for a contact that exists in Cordial.
  </Step>
  <Step title="Generate an event">
    Generate an event for that user. Either open the [Simulator](https://dashboard.radar.com/geofencing/simulate) page, choose the user, and move it into a geofence, or use a test build of your app and enter the geofence.
  </Step>
  <Step title="Check Radar's log">
    On the [Events](https://dashboard.radar.com/geofencing/events) page, click **View** on the new event and find the **Logs** section. Confirm that it shows a Cordial request to `/api/createContactactivities` with a `2xx` response.
  </Step>
  <Step title="Check Cordial">
    In Cordial, open the contact and confirm the `entered_geofence` activity and the `radar_geofence_tags` attribute.
  </Step>
</Steps>

## Troubleshoot delivery

Click **View integration logs** in the **Cordial** section of the [Integrations](https://dashboard.radar.com/integrations) page. Each row shows the timestamp, the request URL, and the response code, and expands to the request and response bodies. New rows can take a few minutes to appear.

| Log response | Meaning |
| --- | --- |
| `skipped`: `Integration key(s) missing.` | No API key for the event's environment. |
| `skipped`: `Identifier missing.` | The user has neither `metadata.cordialId` nor the `cordial:{secondaryKey}` metadata key that matches the setting. |
| `skipped`, "Event type ... isn't allowed." | The event type isn't selected in the allowlist. |
| `skipped`: `Geofence tag '...' is blocklisted.` | The geofence tag is in the blocklist. |
| A `4xx` response | Cordial rejected the request. The response body in the log gives the reason. Check the API key, its permissions, and the async API endpoint. |
| `2xx`, but no data on the contact | Check that the identifier value matches the Cordial contact you are looking at, then ask the Cordial team how the request was processed. |

## Limitations

- A user without a Cordial identifier in metadata is skipped. The Radar `userId` alone isn't enough.
- Contact attributes are updated only when an event is generated.
- There is one async API endpoint and one secondary key setting for both environments.
- There is no automatic retry. A request that fails during a Cordial outage isn't resent.
- Events without a location, and event types not listed under [Event mapping](#event-mapping), aren't sent.
