<Info>
  The Mixpanel integration is available on the [Enterprise plan](https://radar.com/pricing).
</Info>

By the end of this page, each Radar event for an identified user appears in Mixpanel as a `Radar` event on that user's profile, with Radar's location context as profile properties.

Use the integration to add location context to behavioral analytics, measure location-based features, and build location-based cohorts. It is a server-side integration: Radar's servers call Mixpanel.

## Prerequisites

- A Radar project on the Enterprise plan that generates events. See [Geofencing overview and quickstart](/geofencing/overview).
- Access to the [Integrations](https://dashboard.radar.com/integrations) page in the Radar dashboard.
- A Mixpanel project and permission to view its project token. Use a separate Mixpanel project for testing if you have one.
- A Mixpanel distinct ID for each user that Radar can use. Radar skips events for users that have none. See [User mapping](#user-mapping).

## Configuration

<Steps>
  <Step title="Copy your Mixpanel project token">
    In Mixpanel, open **Project Settings** and copy the project token from the access keys section. If you have a separate development project, copy that token too.
  </Step>
  <Step title="Enable the integration in Radar">
    On the [Integrations](https://dashboard.radar.com/integrations) page, find the **Mixpanel** section and select **Yes** for **Enabled**. Credential fields appear.
  </Step>
  <Step title="Enter your tokens">
    Enter the production token in **Live token** and the development token in **Test token**. Radar uses the Live token for events from the Live environment and the Test token for events from the Test environment. If you leave a field empty, Radar sends nothing for that environment.
  </Step>
  <Step title="Save">
    Click **Save**. From now on, Radar sends each new event to Mixpanel. Events generated before you saved aren't sent.
  </Step>
  <Step title="Make sure users have a distinct ID">
    Set the Radar `userId`, or set `metadata.mixpanelDistinctId`, as described in the next section.
  </Step>
</Steps>

## User mapping

### Identifiers

Radar chooses the Mixpanel distinct ID in this order:

1. `metadata.mixpanelDistinctId`, when it is set on the Radar user.
2. Otherwise, the Radar `userId`.

If the user has neither, Radar skips that user's events for Mixpanel and logs `Identifier missing.` Radar doesn't fall back to the device ID.

If your app's Mixpanel distinct ID is the same value as the Radar `userId`, you need no extra code. If it differs, pass the Mixpanel value in the user's metadata.

<CodeGroup>

```swift Swift
import RadarSDK

// distinctId is the value your app uses as the Mixpanel distinct ID.
Radar.setMetadata(["mixpanelDistinctId": distinctId])
```

```kotlin Kotlin
import io.radar.sdk.Radar
import org.json.JSONObject

// distinctId is the value your app uses as the Mixpanel distinct ID.
Radar.setMetadata(JSONObject().put("mixpanelDistinctId", distinctId))
```

</CodeGroup>

Call `Radar.setMetadata()` after you [initialize the SDK](/sdk/sdk) and whenever the distinct ID changes.

## Filtering

On the [Integrations](https://dashboard.radar.com/integrations) page, click **Show advanced** in the **Mixpanel** section.

| Field | Effect |
| --- | --- |
| **Event type allowlist** | When you select one or more event types, Radar sends only those types to Mixpanel. With nothing selected, Radar sends every event type. |
| **Request key blocklist (comma-separated)** | Removes the listed keys from the request at any depth. For example, `Radar Place Name,Latitude,Longitude` removes one profile property and two event properties. |
| **Geofence tag blocklist (comma-separated)** | Skips events for geofences that have one of the listed tags. |

Radar forwards every event type that passes the filters, including types that aren't in the [event mapping](#event-mapping) table. To keep unmapped event types out of Mixpanel, select only the types you want in **Event type allowlist**.

## Delivery behavior

- **Requests**: For each Radar update that generates events, Radar sends one profile update to `https://api.mixpanel.com/engage/` and one request with the events to `https://api.mixpanel.com/track/`. If your Mixpanel project ingests through a different endpoint, ask your Radar account team whether it is supported before you enable the integration.
- **Events without a location**: Radar doesn't send an event that has no location to Mixpanel.
- **Timing**: Radar sends events from its servers shortly after it generates them.
- **Attempts**: Radar makes one delivery attempt per request and waits up to 5 seconds for Mixpanel to respond. It doesn't retry a failed request. Use the [integration logs](#troubleshoot-delivery) to find failures, and the [Events API](/api/events) if you need to backfill.
- **Environment**: The event's environment selects the token. Radar doesn't send a Test event with the Live token or the reverse.

## Test the integration

<Steps>
  <Step title="Use the Test environment">
    Confirm that **Test token** holds the token of a Mixpanel project that you can inspect, and that the integration is saved with **Enabled** set to **Yes**.
  </Step>
  <Step title="Generate an event for an identified user">
    Create a geofence in the Test environment, then send a location inside it with your Test publishable key. Include a `userId`, because Mixpanel delivery requires a distinct ID. Replace the coordinates with a point inside your geofence:

    ```bash
    curl "https://api.radar.io/v1/track" \
      -H "Authorization: prj_test_pk_..." \
      -X POST \
      -d "deviceId=test-device-1" \
      -d "userId=user-123" \
      -d "latitude=40.78382" \
      -d "longitude=-73.97536" \
      -d "accuracy=10"
    ```

    The response includes a `user.entered_geofence` event the first time the user enters the geofence. For the parameters, see [Tracking API](/api/tracking).
  </Step>
  <Step title="Check Radar's log">
    In the **Mixpanel** section, click **View integration logs**. Find two rows for the event: one for the `/engage/` request and one for the `/track/` request, each with a `200` response.
  </Step>
  <Step title="Check Mixpanel">
    In the Mixpanel project that owns the Test token, open the profile with distinct ID `user-123`. Confirm that the profile has a `Radar Geofence Entered` event with the `Geofence External ID` of your geofence, and `Radar Geofence External IDs` among the profile properties.
  </Step>
</Steps>

## Troubleshoot delivery

On the [Integrations](https://dashboard.radar.com/integrations) page, click **View integration logs** in the **Mixpanel** section. Each row shows the request and Mixpanel's response. Radar redacts the token in the logged request.

| What you see | Likely cause | What to do |
| --- | --- | --- |
| No rows | No events were generated in that environment, or the integration isn't saved as enabled. | Check the Events page for the environment and the **Enabled** setting. |
| `skipped`: `Integration key(s) missing.` | The token for the event's environment is empty. | Enter the **Test token** or **Live token**. |
| `skipped`: `Identifier missing.` | The user has no `userId` and no `metadata.mixpanelDistinctId`. | Set one of them. Anonymous users aren't sent to Mixpanel. |
| `skipped`: `Event type ... is not allowed.` | The event type isn't selected in **Event type allowlist**. | Select the type or clear the allowlist. |
| `skipped`: `Geofence tag '...' is blocklisted.` | The geofence's tag is in **Geofence tag blocklist**. | Remove the tag from the blocklist. |
| A success response but no event on the expected profile | The distinct ID differs between Radar and your app, or the token belongs to another project. | Compare `distinct_id` in the logged request with the profile, and check the token. |

## Limitations

- Radar sends events only for users that have a `userId` or `metadata.mixpanelDistinctId`.
- Radar doesn't retry failed deliveries to Mixpanel, and doesn't send a deduplication ID with events.
- Events without a location aren't sent.
- You can't rename events or properties. Use the request key blocklist to drop properties you don't want.
- Events generated before you enabled the integration aren't sent.
- The integration has no setting for the Mixpanel ingestion endpoint.
