By the end of this guide, your app assesses risk when someone registers and when an account redeems a promotion. Your backend verifies each signed result and reads Radar's risk level, fraud flags, and account-to-device counts. Your analysts can investigate a suspicious account, and your backend sends confirmed outcomes back to Radar as labels.

The verified location check for a promotion redemption on a device that several accounts have used:

```json
{
  "_id": "6740a1f2c3d4e5f6a7b8c9d1",
  "passed": true,
  "failureReasons": [],
  "reason": "promo_redemption",
  "transactionId": "redeem-555",
  "user": {
    "userId": "user-123",
    "deviceId": "device-456",
    "fraud": {
      "usersForThisDevice": 4,
      "devicesForThisUser": 1
    }
  }
}
```

## Complete example

This is the client side of registration, and the sections below explain each part and add the redemption check. `api.register` is your own call to your backend, which returns the new account ID.

<CodeGroup>

```swift Swift
import RadarSDK

// At app launch
Radar.initialize(publishableKey: "prj_test_pk_...")

// When the user submits the registration form
func register(email: String) {
  Radar.revealRisk { status, risk in
    // A nil token tells your backend that the risk is unknown.
    let riskToken = status == .success ? risk?.token : nil

    api.register(email: email, riskToken: riskToken) { userId in
      // The account exists now. Later checks carry its ID.
      Radar.setUserId(userId)
    }
  }
}
```

Your backend verifies the token with your project's JWT secret key and stores the result with the new account. `registrations` and `accounts` are your own stores.

<CodeGroup>

```javascript Node.js
import express from 'express';
import { jwtVerify } from 'jose';

const app = express();
app.use(express.json());

const secret = new TextEncoder().encode(process.env.RADAR_JWT_SECRET_KEY);

app.post('/api/registrations', async (req, res) => {
  let assessment = null;
  try {
    // Checks the signature and the expiry, and accepts HS256 only.
    ({ payload: assessment } = await jwtVerify(req.body.riskToken ?? '', secret, {
      algorithms: ['HS256'],
    }));
  } catch (err) {
    // Missing, changed, or expired. The risk is unknown, not low.
  }

  // No account exists yet. Tie the assessment to this registration, and accept it once.
  if (assessment && !(await registrations.claimAssessment(assessment.jti))) {
    return res.status(409).json({ error: 'risk_token_reused' });
  }

  const account = await accounts.create({
    email: req.body.email,
    radarAssessmentId: assessment?.jti ?? null,
    radarDeviceId: assessment?.device?.deviceId ?? null,
    riskLevel: assessment?.risk.level ?? null,
    riskReasons: assessment?.risk.reasons ?? [],
  });

  res.status(201).json({ userId: account.id });
});
```

## Prerequisites

- **Access**: A Radar project with Fraud enabled. The device and network risk assessment must be enabled for your project. Contact your Radar account team. Fraud rules, cases, and the Labels API are also enabled for each project.
- **SDK and plugin**: The Radar SDK and fraud plugin for your platform. See [Fraud plugin setup](/sdk/fraud). The examples use iOS SDK 3.46.0, Android SDK 4.3.0, and Web SDK 5.3.0 with `@radarlabs/plugin-fraud` 1.6.1. `Radar.revealRisk()` requires iOS SDK 3.38.0 or later, Android SDK 3.35.0 or later, `@radarlabs/plugin-fraud` 1.4.0 or later, or React Native SDK 4.36.0 or later.
- **Keys**: A publishable key in your app. On your backend only: the project's JWT secret key, and a secret key (`prj_test_sk_...` or `prj_live_sk_...`) for the Labels API.
- **Identity**: An opaque account ID that your backend creates at registration and never reuses.
- **Permission**: None for the risk assessment. A verified location check needs foreground location permission. See [Understand foreground and background location permissions](/fundamentals/location-permissions).
- **Environment**: Build and test with Test keys. Labels sent with a Test key are recorded for the Test environment.

## How it works

| Party | Responsibility |
| --- | --- |
| Your app | Runs the risk assessment during registration. Sets the user ID once the account exists. Runs verified location checks at registration and redemption when permission allows. Sends signed tokens to your backend. |
| Radar | Returns signed results. Records which devices each user ID is seen on and which user IDs each device is seen with. Evaluates fraud rules on location checks and opens cases. |
| Your backend | Verifies tokens, links the pre-account assessment to the new account in its own records, grants promotions, and sends confirmed outcomes to the Labels API. |
| Your analysts | Investigate cases, record outcomes, and tune rules in the Radar dashboard. |

### What is available before an account exists

A registration starts before you have an account ID, so the first assessment can't carry one. Plan your identifiers around that:

| Moment | Identifiers available | Call |
| --- | --- | --- |
| Registration form, before submit | Radar's assessment `_id`, and the `device.deviceId` and `device.installId` in the assessment. No user ID. | `Radar.revealRisk()` |
| Account created | Your new account ID | `Radar.setUserId()` with the new ID |
| First verified location check | `user.userId`, `user.deviceId`, `user.installId`, and `user.fraud.usersForThisDevice` | `Radar.trackVerified()` with `reason` set to `registration` |
| Later activity | The same user ID on every check, from any device | `Radar.trackVerified()` with a `reason` for the action |

There is no API call to merge the pre-account assessment into the account, and you don't need one:

- **In your own records**: Store the assessment `_id` and `device.deviceId` with the account when you create it, as the complete example does. That is the link between the anonymous assessment and the account.
- **In Radar**: Calling `Radar.setUserId()` on the same app install assigns the user ID to that install's existing record, so earlier activity from the install stays with it. Every later check carries the user ID, and Radar builds the user-to-device relationships from those checks.

Don't use an email address or a phone number as the user ID to make accounts "match". Use the account ID.

## Identify the account once it exists

Call `Radar.setUserId()` with the new account ID as soon as your backend returns it, as the complete example does. The SDK stores the ID on the device and keeps using it across app sessions.

The `userId` is nullable, so you can set it to `nil` or `null` when the user logs out. See [Handle login, logout, and user switching](/fundamentals/authentication-and-access#handle-login-logout-and-user-switching).

## Choose your checkpoints

| Checkpoint | Calls | `reason` | `transactionId` |
| --- | --- | --- | --- |
| Registration submit | Risk assessment | Not applicable | Not applicable |
| Account created | Verified location check, when location permission is granted | `registration` | Not needed |
| Promotion redemption | Verified location check when permission is granted. Otherwise the risk assessment. | `promo_redemption` | The redemption ID from your backend |

## Assess risk at registration

In your app, call `Radar.revealRisk()` when the user submits the form and send the token with the registration request. If the call fails, submit the registration without a token, so your backend records the risk as unknown.

On your backend, verify the token before you read it, and store the assessment ID, the device ID, and the risk level and reasons with the account. For how the token is signed and why your backend records `jti`, see [Validate the token on your backend](/fraud/overview#validate-the-token-on-your-backend).

Radar reports what it observed. What your product does at registration is your choice. A risk level isn't a probability of fraud, and there is no universal level at which to refuse a registration.

| What your backend reads | What it tells you | What an app typically does |
| --- | --- | --- |
| `risk.level` is `none` or `low` | Radar found no signals, or weak ones, on this device and network. | Creates the account. |
| `risk.level` is `medium` or `high` | Radar found more, or stronger, signals. `risk.reasons` and `network.privacy` say which. | Asks for phone or document verification before or after creating the account, or holds promotions and payouts until an analyst has looked. |
| No valid risk token | The risk is unknown. | Creates the account and records that no assessment was available. Doesn't refuse a registration only because the assessment failed. |
| `device.deviceId` | The device the registration came from. | Stores it, so later registrations from the same device can be found in your own records. Several accounts on one device is context, not proof. |

Compare `device.deviceId` values only with other values from risk assessments, and `user.deviceId` values only with other values from verified location checks, unless you have confirmed in your own integration that the two match.

## Run the first verified location check for the new account

After you set the new account ID on the SDK, run a verified location check with the reason `registration` if the user has granted location permission, so that Radar records the account against the device and returns the relationship counts. If the user hasn't granted permission, skip the check. The account is still identified for every later check.

In these examples, `hasLocationPermission` and `sendRegistrationCheck` are functions you write.

<CodeGroup>

```swift Swift
func onAccountCreated(userId: String) {
  Radar.setUserId(userId)

  guard hasLocationPermission() else { return }

  Radar.trackVerified(
    beacons: false,
    desiredAccuracy: .medium,
    reason: "registration",
    transactionId: nil
  ) { status, token in
    guard status == .success, let jwt = token?.token else { return }
    // Send the token whether or not the check passed.
    sendRegistrationCheck(jwt)
  }
}
```

```kotlin Kotlin
import io.radar.sdk.RadarTrackingOptions

fun onAccountCreated(userId: String) {
  Radar.setUserId(userId)

  if (!hasLocationPermission()) return

  Radar.trackVerified(
    beacons = false,
    desiredAccuracy = RadarTrackingOptions.RadarTrackingOptionsDesiredAccuracy.MEDIUM,
    reason = "registration",
    transactionId = null
  ) { status, token ->
    if (status != Radar.RadarStatus.SUCCESS || token == null) return@trackVerified
    // Send the token whether or not the check passed.
    sendRegistrationCheck(token.token)
  }
}
```


## Decide at promotion redemption

Create the redemption on your backend first, so the redemption ID comes from your backend. In your app, run a verified location check with `reason` set to `promo_redemption` and `transactionId` set to the redemption ID, then send the token. The pattern is the same as [Tie a check to one action](/fraud/risky-transactions#tie-a-check-to-one-action).

On your backend, verify the token, confirm that it belongs to the session user and the redemption, and read the result. This route follows the signature, algorithm, expiry, user, transaction, and environment steps of the [shared validation procedure](/fraud/risky-transactions#validation-steps). It reuses `app` and `secret` from the complete example, and `requireSession` and `redemptions` are your own session middleware and store.

```javascript Node.js
app.post('/api/redemptions/:id/confirm', requireSession, async (req, res) => {
  const redemption = await redemptions.getPending(req.params.id, req.session.userId);
  if (!redemption) return res.status(409).json({ granted: false });

  let check;
  try {
    ({ payload: check } = await jwtVerify(req.body.geolocationToken ?? '', secret, {
      algorithms: ['HS256'],
    }));
  } catch (err) {
    // No token, or a changed or expired one. Nothing was verified.
    return res.status(400).json({ granted: false, error: 'token_invalid' });
  }

  // The check must be for this user, this redemption, and this environment.
  const live = process.env.NODE_ENV !== 'production' || check.user?.live === true;
  if (check.user?.userId !== req.session.userId || check.transactionId !== redemption.id || !live) {
    return res.status(400).json({ granted: false, error: 'token_mismatch' });
  }

  await redemptions.recordCheck(redemption.id, {
    radarCheckId: check._id,
    radarDeviceId: check.user.deviceId,
    passed: check.passed,
    failureReasons: check.failureReasons ?? [],
    usersForThisDevice: check.user.fraud?.usersForThisDevice ?? null,
  });

  if (check.passed !== true) {
    return res.status(403).json({
      granted: false,
      passed: false,
      failureReasons: check.failureReasons ?? [],
    });
  }

  // Compare-and-set, so two concurrent requests can't both grant.
  const granted = await redemptions.transition(redemption.id, 'pending', 'granted');
  res.json({ granted });
});
```

The route grants the promotion when the check passed. What else your product looks at before it grants is your choice:

| What your backend reads | What it tells you | What an app typically does |
| --- | --- | --- |
| `passed` is `false` | The check failed according to your project configuration. `failureReasons` says why, for example a spoofed location, a compromised device, or a blocked user. | Doesn't grant. Shows a message the user can act on, and lets them run a new check with the same redemption ID. |
| `user.fraud.usersForThisDevice` | How many user IDs this device has been seen with. | Records it with the redemption. Holds the redemption for an analyst when it comes with a second signal, such as an earlier redemption of the same promotion on the same device. |
| `user.fraud.proxy` | The check came through a VPN or proxy. | Records it. Combines it with other signals before acting, because many people use a VPN for privacy or work. |
| `user.deviceId` | The device the redemption came from. | Compares it with the device IDs on earlier redemptions of the same promotion in its own records. |

A limit such as one redemption per device is a rule from your promotion's terms, applied from your own redemption records. It isn't a Radar result. A second account on a shared device can be a different, legitimate person, so consider holding that case for review instead of refusing it.

When location permission isn't granted, run the risk assessment instead, verify it as at registration, and read the device and network signals together with your own redemption records. User-to-device counts from Radar aren't available on that path.

## Detect new account fraud

The hypothesis is that the account was created to commit fraud and doesn't represent a real, single customer.

| Observation | Where it comes from |
| --- | --- |
| A VPN, proxy, or hosting network at registration | `risk.reasons` and `network.privacy` on the risk assessment |
| A rooted or jailbroken device, or failed attestation | `risk.reasons` on the assessment, or `user.fraud.compromised` on a verified location check |
| A spoofed location on the first verified location check | `user.fraud.mocked` and its failure reasons |
| Many registrations from one device in a short time | Your own count by device ID |
| The account's first actions go straight to a payout or a promotion | Your own event sequence |

Respond before value leaves: ask for stronger verification at registration, hold promotions and payouts for accounts in review, and let legitimate users through the same step.

## Detect multi-accounting

The hypothesis is that one person controls several accounts.

| Observation | Where it comes from |
| --- | --- |
| Several user IDs on one device | `user.fraud.usersForThisDevice`, and the device's detail page in the dashboard |
| One user ID across many devices | `user.fraud.devicesForThisUser`, and the user's detail page |
| A cluster of accounts linked through shared devices | The network view on a user or device detail page |
| Accounts that check from exactly the same coordinates repeatedly | Location history, and the **Consecutive repeat coordinates** rule criterion |
| Accounts created close together in time | **User first seen** in the dashboard, and your own records |

Shared households, workplaces, schools, and public networks produce the first three observations for unrelated, legitimate people. Look for more than one kind of link, and for coordinated behavior: accounts that register together, redeem together, and move value between each other.

A fraud rule on **Users for this device** with a time window surfaces candidates as cases. Keep its action to **Open case** until you know what it matches in your traffic.

## Detect promo abuse

The hypothesis is that a promotion meant for one person, or for people in a particular place, is being claimed repeatedly or from somewhere else.

| Observation | Where it comes from |
| --- | --- |
| The promotion already redeemed on this device by another account | Your own redemption records, keyed by the device ID from validated tokens |
| Several user IDs on the redeeming device | `user.fraud.usersForThisDevice` |
| A location-restricted promotion redeemed with a spoofed location | `user.fraud.mocked`, `user.fraud.jumped`, and their failure reasons |
| A location-restricted promotion redeemed from outside the place | The verified location and geofences in the token. See [Verify location for non-gaming use cases](/geo-compliance/non-gaming). |
| Redemptions concentrated at one place or one set of coordinates | [Location hotspots](#look-for-location-hotspots) |

Bind every redemption check to its redemption with `transactionId`, validate on your backend, and grant the promotion only from your backend. A redemption that your app reports as successful without a validated token isn't a redemption.

### Look for location hotspots

A hotspot is a place where an unusual number of accounts or devices check from, such as one address that produces dozens of registrations.

- On the [Locations](https://dashboard.radar.com/geofencing/locations) page, select **Map and feed**, search for an address, and filter the list to the map area. Add filters such as the check reason `registration` or `promo_redemption` to see who checked there and when.
- Use the **Analysis** view on the same page to count checks, unique users, or unique devices over time for the filters you set.
- To watch a known place, create a geofence around it with a tag such as `review-zone`, and create a fraud rule with the **Geofence tags** criterion and the **Open case** action.

A busy place isn't a fraudulent place. An apartment building, a campus, a stadium, or a store running your promotion at the counter is a hotspot of legitimate users. Combine the place with device links and behavior before you act.

### Prevent SMS verification abuse

If your registration sends an SMS code, automated sign-ups can run up messaging costs by requesting codes at volume. The registration checkpoint in this guide applies unchanged: run the risk assessment and validate it on your backend before you send the SMS, not after. When `risk.level` is `medium` or `high`, or the risk token is missing, consider delaying or withholding the message, and rate limit further requests from that `device.deviceId` in your own records. Radar doesn't send or inspect SMS messages. Your backend chooses whether to send.

## Investigate a suspicious new account

When an account needs a closer look or a fraud rule opens a case, an analyst works from the new account outward: to the device it registered on, to the other accounts on that device, and to where those accounts check from.

<FraudInvestigation />

### Configure rules for new accounts and promotions

Rules that suit this use case, each starting with **Open case** as the only action:

| Goal | Criteria |
| --- | --- |
| Surface possible multi-accounting | **Users for this device** above a number you choose, within a time window |
| Surface repeated redemptions from one spot | **Location check reason** is `promo_redemption`, and **Consecutive repeat coordinates** above a number you choose |
| Surface spoofed redemptions | **Location check reason** is `promo_redemption`, and **Failure reasons** includes the location spoofing reasons you select |
| Watch a known hotspot | **Geofence tags** includes the tag of a geofence you drew around the place |
| Focus on new accounts | Add **User first seen** to any of the above |

A rule with **Block associated users** or **Block associated devices** blocks everyone linked to the matching check, which on a shared device includes legitimate users. If block durations are available for your project, prefer a temporary block while an analyst reviews. See [Configure rules and actions](/fraud/overview#configure-rules-and-actions).

### Submit an outcome as a label

When an outcome is confirmed outside the dashboard, for example a chargeback, a failed identity check, or a support review that clears the account, send it to Radar from your backend. Closing a case in the dashboard as fraud or not fraud records a label for you, so send API labels only for outcomes decided elsewhere.

<Info>
  The Labels API must be enabled for your project. Contact your Radar account team.
</Info>

This request records a `fraud` label for `user-123`:

```bash
curl "https://api.radar.io/v1/fraud/labels" \
  -H "Authorization: prj_test_sk_..." \
  -H "Content-Type: application/json" \
  -X POST \
  -d '{"userId": "user-123", "label": "fraud", "fraudType": "promo_abuse", "incidentTime": "2026-11-10T14:30:00Z"}'
```

| Parameter | Required | Description |
| --- | --- | --- |
| `userId` | Yes | The same ID your app sets with `Radar.setUserId()`. Labels apply to users, not devices. |
| `label` | Yes | `fraud` or `not_fraud`. |
| `fraudType` | No | A category you define, such as `promo_abuse` or `multi_accounting`. Up to 100 characters: letters, numbers, dashes, underscores, spaces, periods, and commas. |
| `incidentTime` | No | When the incident happened, as an ISO 8601 datetime. If omitted, Radar uses the time it received the label. |

If the Labels API isn't enabled for your project, the request returns `404`. A `202` response means the label was accepted for processing:

```json
{
  "meta": {
    "code": 202
  }
}
```

Send the label from your backend, and treat any status other than `202` as a failure:

```javascript Node.js
/**
 * @param {{ userId: string, label: 'fraud' | 'not_fraud', fraudType?: string, incidentTime?: string }} outcome
 */
export async function sendFraudLabel(outcome) {
  const response = await fetch('https://api.radar.io/v1/fraud/labels', {
    method: 'POST',
    headers: {
      Authorization: process.env.RADAR_SECRET_KEY, // prj_live_sk_... in production
      'Content-Type': 'application/json',
    },
    body: JSON.stringify(outcome),
  });

  if (response.status !== 202) {
    // 400: invalid field. 401: bad key. 404: labels not enabled. 429: rate limited.
    throw new Error(`Radar label request failed with status ${response.status}`);
  }
}

// A cleared account is as useful as a confirmed one.
await sendFraudLabel({ userId: 'user-124', label: 'not_fraud' });
```

The response doesn't confirm that a user with that ID exists, and the label is processed asynchronously. Send the user ID exactly as your app sets it. For the full contract, see [Labels API](/api/labels).

### Evaluate false positives

Every rule in this guide, and every choice you make about a risk level or a count, matches some legitimate users. Measure that before you automate anything.

1. **Run in observe mode first**: For the first weeks, store Radar's results with each registration and redemption without acting on them. Give new fraud rules the **Open case** action only.
2. **Review a sample of matches**: For each rule, and for each result you plan to act on, have an analyst investigate a sample and close each case as fraud or not fraud.
3. **Compute the false positive share**: For each rule, divide the cases closed as not fraud by all closed cases. Do the same for the results you plan to act on, using your own outcome records.
4. **Find what the false positives have in common**: Typical causes are households and roommates on one device, workplaces and campuses on one network, a store running a promotion on its own tablet, and travelers on hotel or airline Wi-Fi.
5. **Adjust**: Raise a count, add a second criterion, narrow a time window, or exclude a place. Then measure again.
6. **Label both ways**: Send `not_fraud` for cleared accounts as well as `fraud` for confirmed ones.
7. **Add automatic blocking last**: Add it only to rules whose matches are consistently confirmed. Give blocked users a way to reach support.

## Handle results and errors

Your backend reads these fields from each result:

| Result | Fields your backend reads | Use |
| --- | --- | --- |
| Risk assessment | `_id`, `risk.level`, `risk.reasons`, `network.privacy`, `device.deviceId`, `device.installId` | The only Radar signal before an account exists. See [Read the result](/fraud/overview#read-the-result). |
| Verified location check | `user.userId`, `user.deviceId`, `transactionId`, `reason`, `passed`, `failureReasons`, `warningReasons`, `user.fraud`, `_id` | Account-to-device relationships and location integrity. See the [Geolocation token schema](/api/geolocation-tokens). |

- `user.fraud.usersForThisDevice` and `user.fraud.devicesForThisUser` are counts. To see which users and devices, open the dashboard.
- `user.fraud.risk` is present when risk scores are enabled for your project. Record it for analysts, and don't build logic on specific values. See [Understand risk scores and decisions](/fraud/overview#understand-risk-scores-and-decisions).
- `passed` set to `false` means a check failed according to your project configuration. Read `failureReasons` to see which one.
- A risk score isn't a probability of fraud, and no count is a universal limit.

### Recover from errors and degraded paths

Each situation in this table ends in a defined result:

| Situation | What your backend receives | Result |
| --- | --- | --- |
| Risk assessment failed during registration | No risk token | The risk is unknown. The example creates the account with a `riskLevel` of `null`. Don't refuse a registration only because the assessment was unavailable. |
| Risk token invalid or expired | A token that fails verification | Same as no risk token. Don't store its contents. |
| Location permission not granted | No geolocation token | No verified location check. The account is identified for later checks. Redemption falls back to the risk assessment. |
| Verified check returned a technical error | No geolocation token | Not a failed check and not a pass. At redemption, don't grant, and let the user try again with the same redemption ID. |
| Geolocation token expired | A token that fails verification | `400` with `token_invalid`. Run a new check with the same redemption ID. |
| Token for another user or redemption | A valid token that doesn't match the session or the redemption | `400` with `token_mismatch`. Set the correct user ID or redemption ID in your app and check again. |
| Risk token sent twice | A `jti` your backend already recorded | `409` with `risk_token_reused`. Your app runs a new assessment. |
| Another person registers on the same device | Two accounts with the same device ID | Two separate accounts and two separate records. `usersForThisDevice` becomes 2, which is context. |

For the client status values for technical errors, see [Handle a technical error](/fraud/risky-transactions#handle-a-technical-error).

## Test the integration

Use the Test environment and dedicated test accounts. Test your backend with tokens signed by a test-only secret.

| Test | How | Expected result |
| --- | --- | --- |
| Clean registration | Register on a normal network | The account record has the assessment ID, the device ID, and the risk level |
| Risk unavailable | Submit the registration with no risk token, and with a token that has one character changed | The account is created with a `riskLevel` of `null` |
| Flagged network | Register while connected to a commercial VPN | `network.privacy.vpn` is `true` or `risk.reasons` isn't empty. Note the level and reasons you get. |
| Identity after registration | Register, grant location permission, and let the first check run | The check appears on the [Locations](https://dashboard.radar.com/geofencing/locations) page with the new user ID and the reason `registration` |
| Second account on one device | Register `test-user-123`, then register `test-user-456` on the same device, and run a check | The second account's token has `user.fraud.usersForThisDevice` of at least 2 |
| Redemption | Redeem a promotion with location permission granted | The redemption is granted once, and its record has the check ID, the device ID, and `usersForThisDevice` |
| Token for another redemption | Send a valid token whose `transactionId` is a different redemption ID | `400` with `token_mismatch`. The redemption stays `pending`. |
| Token for another user | Send `test-user-123`'s token in `test-user-456`'s session | `400` with `token_mismatch` |
| Blocked user | Create a block rule for the test user, then redeem | `403` with `passed` set to `false` and `fraud_blocked_user_id` in `failureReasons` |
| Rule and case | Create a fraud rule on **Users for this device** with a low number and **Open case**, then repeat the second-account test | A case opens on the **Cases** page listing both test users and the device |
| Label | Send a `not_fraud` label for a test user with a Test secret key | `202` |
| Client-only redemption | Call your grant route without a validated token | Refused |

To create and remove the block rule, see [Produce a failed check on demand](/fraud/risky-transactions#produce-a-failed-check-on-demand). Disable or delete test rules, and close test cases, when you finish.

## Production checklist

- [ ] The user ID is an opaque account ID, set after account creation.
- [ ] The account record stores the Radar assessment ID and device ID from registration.
- [ ] Both tokens are verified on your backend with the JWT secret key and an explicit `HS256` allowlist, and each risk token `jti` is recorded once.
- [ ] Redemption tokens are bound to the session user and to the redemption ID, and each redemption is granted at most once, from your backend.
- [ ] No rule or code path refuses on a user count, a device count, or a shared network alone.
- [ ] What your product does at each risk level, and any count you act on, has an owner who reviews it against recorded outcomes.
- [ ] A missing or invalid risk token is recorded as unknown risk, not as no risk.
- [ ] New fraud rules start with **Open case** only, and their false positive share is measured before any blocking action is added.
- [ ] Analysts have dashboard access and close cases with an outcome.
- [ ] Outcomes decided outside the dashboard are sent to the Labels API with a Live secret key that is stored only on your backend.
- [ ] Production builds use a Live publishable key, and tokens aren't written to logs.
- [ ] No bypass rule exists in the Live environment for a real user.
