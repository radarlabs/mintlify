By the end of this guide, your app assesses risk at login, when a session continues, and before sensitive account actions. Your backend verifies each signed result and reads Radar's risk level, the signals behind it, and, when a verified location check is available, the user's devices and fraud flags.

The assessment for a login on a network that Radar flags:

```json
{
  "_id": "6740a1f2c3d4e5f6a7b8c9d0",
  "risk": {
    "level": "medium",
    "reasons": ["fraud_proxy_known_proxy_ip"]
  },
  "network": {
    "privacy": {
      "vpn": true,
      "hosting": true
    }
  },
  "device": {
    "deviceId": "device-456"
  }
}
```

Account takeover and account sharing produce similar signals and call for different responses. This guide implements the shared collection once, then treats the two separately.

## Complete example

This is the client side of every checkpoint, and the sections below explain each part. `sendRiskToken` is the function you write that posts the token and the checkpoint name to your backend.

<CodeGroup>

```swift Swift
import RadarSDK

// At app launch
Radar.initialize(publishableKey: "prj_test_pk_...")

// After you authenticate the user
Radar.setUserId("user-123")

// At each checkpoint: "login", "session", or "account_change"
func assessRisk(at checkpoint: String) {
  Radar.revealRisk { status, risk in
    // A nil token tells your backend that the risk is unknown.
    let riskToken = status == .success ? risk?.token : nil
    sendRiskToken(riskToken, checkpoint: checkpoint)
  }
}
```

Your backend verifies the token with your project's JWT secret key, ties it to the session, and reads the result. `requireSession` and `sessions` are your own session middleware and store.

<CodeGroup>

```javascript Node.js
import express from 'express';
import { jwtVerify } from 'jose';

const app = express();
app.use(express.json());

const secret = new TextEncoder().encode(process.env.RADAR_JWT_SECRET_KEY);

app.post('/api/risk', requireSession, async (req, res) => {
  const { checkpoint, riskToken } = req.body;

  let assessment;
  try {
    // Checks the signature and the expiry, and accepts HS256 only.
    ({ payload: assessment } = await jwtVerify(riskToken ?? '', secret, {
      algorithms: ['HS256'],
    }));
  } catch (err) {
    // Missing, changed, or expired. The risk is unknown, not low.
    await sessions.recordRisk(req.session.id, { checkpoint, level: null });
    return res.json({ riskLevel: null, riskReasons: [] });
  }

  // The token has no user ID. Tie it to this session, and accept each assessment once.
  const firstUse = await sessions.recordRisk(req.session.id, {
    checkpoint,
    assessmentId: assessment.jti,
    level: assessment.risk.level,
    reasons: assessment.risk.reasons,
    privacy: assessment.network?.privacy,
    deviceId: assessment.device?.deviceId,
  });
  if (!firstUse) {
    return res.status(409).json({ error: 'risk_token_reused' });
  }

  res.json({ riskLevel: assessment.risk.level, riskReasons: assessment.risk.reasons });
});
```

## Prerequisites

- **Access**: A Radar project with Fraud enabled. The device and network risk assessment must be enabled for your project. Contact your Radar account team. Risk scores, fraud rules, and cases are also enabled for each project.
- **SDK and plugin**: The Radar SDK and fraud plugin for your platform. See [Fraud plugin setup](/sdk/fraud). The examples use iOS SDK 3.46.0, Android SDK 4.3.0, and Web SDK 5.3.0 with `@radarlabs/plugin-fraud` 1.6.1. `Radar.revealRisk()` requires iOS SDK 3.38.0 or later, Android SDK 3.35.0 or later, `@radarlabs/plugin-fraud` 1.4.0 or later, or React Native SDK 4.36.0 or later.
- **Keys**: A publishable key in your app. The project's JWT secret key on your backend only.
- **Identity**: A stable, opaque ID for each account in your own system.
- **Permission**: None for the risk assessment. A verified location check needs foreground location permission. This guide runs it only when permission is already granted. To ask for it, see [Detect risky transactions and verify precise location](/fraud/risky-transactions).
- **Environment**: Build and test with Test keys. Users and history in the Test environment are separate from the Live environment.

## How it works

| Party | Responsibility |
| --- | --- |
| Your app | Identifies the signed-in user to the SDK, runs the assessment and, where possible, a verified location check at each checkpoint, and sends the signed tokens to your backend. |
| Radar | Returns a signed device and network risk assessment. For a verified location check, returns a signed geolocation token with the user's fraud flags, failure reasons, and device and user counts. Keeps the history that the Radar dashboard and fraud rules use. |
| Your backend | Verifies the tokens, ties the risk assessment to the session, checks that the geolocation token belongs to the session user, and applies your follow-up, such as requiring another factor or revoking sessions. |
| Your analysts | Investigate cases in the dashboard, record outcomes, and tune rules. |

The two calls answer different questions:

| Question | Call | Why |
| --- | --- | --- |
| Is this device or network risky right now? | `Radar.revealRisk()` | Works without location permission and without a user ID, so it runs on every checkpoint. |
| Is this the same user, on a consistent set of devices, in a plausible place? | `Radar.trackVerified()` | Carries the `userId`, the location, and signals that depend on them, such as `fraud_jumped_multiple_devices`. Needs location permission. |

## Identify the authenticated user

Every user-level signal depends on the SDK knowing which account is signed in. Call `Radar.setUserId()` with your own stable, opaque account ID after you authenticate the user and before the first verified location check. The SDK stores the ID on the device and keeps using it across app sessions.

The `userId` is nullable, so you can set it to `nil` or `null` when the user logs out. See [Handle login, logout, and user switching](/fundamentals/authentication-and-access#handle-login-logout-and-user-switching).

The risk assessment doesn't carry the user ID. Your backend knows whose assessment it is from the authenticated request that delivered it.

## Choose your checkpoints

| Checkpoint | When to run it | Calls | `reason` |
| --- | --- | --- | --- |
| Login | After you verify credentials and before you treat the session as fully trusted | Risk assessment always. Verified location check when location permission is already granted. | `login` |
| Session continuation | When the app returns to the foreground after a long gap, or on a schedule you choose for long sessions | Risk assessment. Verified location check when permission is granted. | `session` |
| Sensitive account action | Before a change of email, password, phone number, or payout details | Risk assessment, then a verified location check when the risk level is elevated | `account_change` |

Use the same small set of `reason` values on every platform. Radar shows the reason in the dashboard and reports, and fraud rules can match on it.

For a sensitive account action that requires the user's verified location when risk is raised, implement the full flow in [Detect risky transactions and verify precise location](/fraud/risky-transactions). This guide doesn't repeat it.

## Collect the signals on the client

At every checkpoint, run the risk assessment as in the [complete example](#complete-example). It needs no permission, so it always runs.

When the user has already granted location permission, also run a verified location check with the checkpoint as its `reason`, and send its token to your backend. The check adds the signals that depend on the user ID and the location. Don't prompt for location permission at login only for this purpose unless your product already explains why.

In these examples, `hasLocationPermission` and `sendGeolocationToken` are functions you write. Check permission with the platform API described in [Understand foreground and background location permissions](/fundamentals/location-permissions).

<CodeGroup>

```swift Swift
func verifyLocation(at checkpoint: String) {
  guard hasLocationPermission() else { return }

  Radar.trackVerified(
    beacons: false,
    desiredAccuracy: .medium,
    reason: checkpoint,
    transactionId: nil
  ) { status, token in
    // No token means the check didn't complete. It isn't a failed check.
    guard status == .success, let jwt = token?.token else { return }
    // Send the token whether or not the check passed.
    sendGeolocationToken(jwt, checkpoint: checkpoint)
  }
}
```

```kotlin Kotlin
import io.radar.sdk.RadarTrackingOptions

fun verifyLocation(checkpoint: String) {
  if (!hasLocationPermission()) return

  Radar.trackVerified(
    beacons = false,
    desiredAccuracy = RadarTrackingOptions.RadarTrackingOptionsDesiredAccuracy.MEDIUM,
    reason = checkpoint,
    transactionId = null
  ) { status, token ->
    // No token means the check didn't complete. It isn't a failed check.
    if (status != Radar.RadarStatus.SUCCESS || token == null) return@trackVerified
    // Send the token whether or not the check passed.
    sendGeolocationToken(token.token, checkpoint)
  }
}
```

```javascript JavaScript
async function verifyLocation(checkpoint) {
  if (!(await hasLocationPermission())) return;

  try {
    const check = await Radar.fraud.trackVerified({ skipVerifyApp: true, reason: checkpoint });
    // Send the token whether or not the check passed.
    await sendGeolocationToken(check.token, checkpoint);
  } catch (err) {
    // The check didn't complete. No token was issued. It isn't a failed check.
  }
}
```

```javascript React Native
async function verifyLocation(checkpoint) {
  if (!(await hasLocationPermission())) return;

  try {
    const check = await Radar.trackVerified({ reason: checkpoint });
    if (check.token) {
      // Send the token whether or not the check passed.
      await sendGeolocationToken(check.token.token, checkpoint);
    }
  } catch (err) {
    // The check didn't complete. No token was issued. It isn't a failed check.
  }
}
```

</CodeGroup>

The JavaScript example passes `skipVerifyApp: true`, which runs the check in the browser without the Radar Verify companion app. For the verified location check and its parameters, see [Request the verified location check](/fraud/risky-transactions#request-the-verified-location-check).

## Validate and read the results on your backend

The risk token is verified in the [complete example](#complete-example). For how the token is signed and why your backend records `jti`, see [Validate the token on your backend](/fraud/overview#validate-the-token-on-your-backend).

The geolocation token is signed with the same key. Verify it the same way, then confirm that it belongs to the user who is signed in on this request before you read anything else. This route follows the signature, algorithm, expiry, user, and environment steps of the [shared validation procedure](/fraud/risky-transactions#validation-steps), and reuses `app` and `secret` from the complete example.

```javascript Node.js
app.post('/api/location', requireSession, async (req, res) => {
  let check;
  try {
    ({ payload: check } = await jwtVerify(req.body.geolocationToken ?? '', secret, {
      algorithms: ['HS256'],
    }));
  } catch (err) {
    return res.status(400).json({ error: 'token_invalid' });
  }

  // The check must be for the user who is signed in, in this environment.
  const live = process.env.NODE_ENV !== 'production' || check.user?.live === true;
  if (check.user?.userId !== req.session.userId || !live) {
    return res.status(400).json({ error: 'token_mismatch' });
  }

  await sessions.recordCheck(req.session.id, {
    checkpoint: req.body.checkpoint,
    checkId: check._id,
    deviceId: check.user.deviceId,
    passed: check.passed,
    failureReasons: check.failureReasons ?? [],
    fraud: check.user.fraud,
  });

  res.json({ passed: check.passed, failureReasons: check.failureReasons ?? [] });
});
```

## Use the results at each checkpoint

Radar reports what it observed. What your product does at each checkpoint is your choice, and it depends on the action and on what a false positive costs you. A risk level isn't a probability of fraud, and there is no universal level at which to block.

| What your backend reads | What it tells you | What an app typically does |
| --- | --- | --- |
| `risk.level` is `none` or `low` | Radar found no signals, or weak ones, on this device and network. | Continues the session. |
| `risk.level` is `medium` or `high` | Radar found more, or stronger, signals. `risk.reasons` and `network.privacy` say which. | At login or before a sensitive change, asks for another authentication factor or a [verified location check](/fraud/risky-transactions). During a session, records it for review. |
| No valid risk token | The risk is unknown. | Handles a sensitive change as it would a raised risk level. |
| `passed` is `false` | The verified location check failed according to your project configuration. `failureReasons` says why. | Shows a message the user can act on, and holds the sensitive action until a new check passes. |
| `user.fraud.blocked` is `true` | A block rule in Radar matched this user or device, so an analyst or a rule already decided. | Refuses the action. |
| `fraud_jumped_multiple_devices` in `failureReasons` | This device's location is inconsistent with another device that uses the same user ID. | Asks for another authentication factor, then follows the takeover or sharing path below. |
| `user.fraud.sharing`, `user.fraud.compromised`, or `user.fraud.mocked` is `true` | Screen sharing or remote control, a compromised device or app, or a spoofed location on this check. | Holds sensitive changes and asks for another factor. |
| `user.fraud.devicesForThisUser` and `user.fraud.usersForThisDevice` | How many devices this user ID has been seen on, and how many user IDs this device has been seen with. | Records them as context. People replace phones, and households share devices, so neither count is a reason to block alone. |

To recognize a device the user has signed in from before, compare `user.deviceId` from the verified token with the device IDs you stored for that user on earlier checks. A device ID you haven't stored for the user is a new device for that user. It is context, not proof.

## Detect account takeover

The hypothesis is that someone other than the account owner has signed in.

Takeover shows up as a break from the account's own pattern, usually followed quickly by an attempt to change or extract something.

| Observation | Where it comes from |
| --- | --- |
| A device the account hasn't used before | A `user.deviceId` you haven't stored for this user. In the dashboard, the user's device list. |
| A VPN, proxy, or hosting network on that device | `risk.reasons` and `network.privacy` on the risk assessment, or `user.fraud.proxy` |
| Screen sharing or remote control during the session | `user.fraud.sharing`, or a `fraud_sharing_` reason. Remote control of the real owner's device is a takeover method that keeps the device and location unchanged. |
| A country or state that differs from the account's recent checks | `user.country` and `user.state` on the verified location check, or the location history in the dashboard |
| The same account active on two devices in inconsistent places | `fraud_jumped_multiple_devices` in `failureReasons` |
| A sensitive account action soon after any of the above | Your own event sequence |

Respond in a way the real owner can recover from: ask for another authentication factor, hold changes to credentials and payout details, notify the owner, and revoke other sessions once the owner confirms. Reserve blocking for confirmed cases.

## Detect account sharing

The hypothesis is that the account owner has given their credentials to other people.

Sharing shows up as a stable, repeating pattern, without the urgency of a takeover.

| Observation | Where it comes from |
| --- | --- |
| The same small set of devices returning over weeks | `user.fraud.devicesForThisUser` on the verified location check, and the user's device list in the dashboard |
| Those devices checking from different places, repeatedly | Location history in the dashboard. Repeated `fraud_jumped_multiple_devices` over time. |
| Overlapping sessions on different devices | Your session store |
| No change to credentials or payout details | Your own event sequence |

Whether sharing is a problem, and how much of it, is defined by your terms of service. Respond in proportion: limit concurrent sessions, ask the user to sign in again, or message the account owner. A fraud rule on **Devices for this user** with a time window is a good way to surface candidates as cases without acting on them automatically.

## Tell the scenarios apart

The same signals appear in all three of these. What distinguishes them is what accompanies the signal and what happens next.

| Scenario | What you observe | What an app typically does | Why |
| --- | --- | --- | --- |
| Legitimate new-device session | A device ID you haven't seen for the user. A risk level of `none` or `low`. No fraud flags. The country and state match the account's recent checks. | Continues, and tells the account owner about the new sign-in through a channel the new device doesn't control. | A new device alone is context. People replace and add devices. |
| Suspicious login | A device ID you haven't seen for the user, together with a raised risk level or no valid assessment. Possibly a different country from recent checks. | Asks for another authentication factor before continuing. | A new device with a second independent signal breaks the account's pattern. The owner can pass the extra factor. Someone else usually can't. |
| Inconsistent activity across devices | `fraud_jumped_multiple_devices`: this device's location is inconsistent with another device using the same user ID. | Asks for another factor at the checkpoint. Then follows the takeover path if the other device is new and sensitive actions follow, or the sharing path if the same devices recur. | Two devices in inconsistent places means two people or a spoofed location. It doesn't say which person is the owner. |

### Keep one user's history out of another's decision

Shared and handed-down devices are common. These rules keep one person's history from affecting another person:

- Call `Radar.setUserId()` for the signed-in user before any verified location check. Radar keeps a separate user record for each combination of install, device, and user ID.
- On your backend, reject a geolocation token whose `user.userId` isn't the session user, as the `/api/location` route does.
- Store device IDs under your own user ID. When `user-456` signs in on a device that `user-123` used, the device is new for `user-456`.
- Treat `user.fraud.usersForThisDevice` greater than 1 as context. A family tablet has several users.
- Remember that Radar's risk score for a user can reflect signals from devices and users associated with them. A raised score on a shared device isn't evidence about the person signed in now. Look at the reasons.
- A risk assessment has no user ID. Never store its result against a user except through the authenticated request that delivered it.

## Investigate a suspected takeover or shared account

When a session needs a closer look, when a customer reports a takeover, or when a fraud rule opens a case, an analyst follows the same path in the dashboard. For this use case, look in particular for a device that appears for the first time shortly before a sensitive change, and for whether the account's devices form a stable set or keep changing.

<FraudInvestigation />

Rules that suit this use case, each starting with **Open case** as the only action:

| Goal | Criteria |
| --- | --- |
| Surface possible sharing | **Devices for this user** above a number you choose, within a time window in days |
| Surface inconsistent use | **Failure reasons** includes `fraud_jumped_multiple_devices` |
| Surface risky logins | **Location check reason** is `login`, and **Country change** or **State change** |

A blocking action on any of these rules affects every associated user or device, including legitimate members of a household. Add it only after reviewing what the rule opens. See [Configure rules and actions](/fraud/overview#configure-rules-and-actions).

## Handle results and errors

Your backend reads these fields from each result:

| Result | Fields your backend reads | Use |
| --- | --- | --- |
| Risk assessment | `risk.level`, `risk.reasons`, `network.privacy`, `network.asn`, `device`, `_id` | Device and network signal at every checkpoint. See [Read the result](/fraud/overview#read-the-result). |
| Verified location check | `user.userId`, `user.deviceId`, `passed`, `failureReasons`, `warningReasons`, `user.fraud`, `user.country`, `user.state`, `_id` | User-level signals. See the [Geolocation token schema](/api/geolocation-tokens). |

Notes on reading the verified location check for this use case:

- `passed` set to `false` means a check failed according to your project configuration. It doesn't by itself say the session is a takeover. Read `failureReasons` to see which check failed.
- `user.fraud.devicesForThisUser` and `user.fraud.usersForThisDevice` are counts. They tell you that relationships exist, not who the devices or users are. Use the dashboard to see them.
- `user.fraud.risk` is present when risk scores are enabled for your project. Record it for analysts, and don't build logic on specific values. See [Understand risk scores and decisions](/fraud/overview#understand-risk-scores-and-decisions).
- `warningReasons` lists signals that didn't fail the check. Record them with the session.
- Reasons can include values that aren't documented. Record them without failing.

### Recover from errors and degraded paths

Each situation in this table ends in a defined result:

| Situation | What your backend receives | Result |
| --- | --- | --- |
| Location permission not granted | A risk token and no geolocation token | Only the risk assessment is available. User-level signals, including the device ID, aren't available for this checkpoint. |
| Risk assessment failed in your app | No risk token | The risk is unknown. The example records a level of `null`. |
| Risk token invalid or expired | A token that fails verification | Same as no risk token. |
| Risk token sent twice | A `jti` your backend already recorded | `409` with `risk_token_reused`. Your app runs a new assessment. |
| Verified check returned a technical error | No geolocation token | Same as no permission. A technical error isn't a failed check and not a pass. |
| Geolocation token expired before it arrived | A token that fails verification | `400` with `token_invalid`. Don't ask the user to act. Run the check again at the next checkpoint. |
| Geolocation token for a different user | `user.userId` doesn't match the session | `400` with `token_mismatch`. In your app, call `Radar.setUserId()` with the session user and check again. This usually means the identity wasn't updated after a user switch. |
| Failed check | A valid token with `passed` set to `false` | Read `failureReasons`. Don't loop on the check. |
| User blocked in Radar | `user.fraud.blocked` is `true`, with a `fraud_blocked_` failure reason | Refuse the action. To reverse it, an analyst removes the block rule. |

For the client status values for technical errors, see [Handle a technical error](/fraud/risky-transactions#handle-a-technical-error).

Handle each point in the session lifecycle:

- **Login**: Set the user ID, then assess.
- **App returns to the foreground**: Assess again if the last assessment is older than the interval you chose for the `session` checkpoint.
- **User switch**: Call `Radar.setUserId()` with the new user before the next verified location check.

## Test the integration

Use the Test environment and dedicated test accounts. Test your backend with tokens signed by a test-only secret.

| Test | How | Expected result |

| Inconsistent devices | Backend test with a signed geolocation token whose `failureReasons` contains `fraud_jumped_multiple_devices` | `passed` is `false`, and the reason is recorded |
| Blocked user | Create a block rule for the test user in the dashboard, then sign in with permission granted | `passed` is `false`, and `user.fraud.blocked` is `true` |
| Shared device | Sign in as `test-user-123`, then sign in as `test-user-456` on the same device | The second user's token carries `test-user-456` |
| Token for another user | Send `test-user-123`'s geolocation token in `test-user-456`'s session | `400` with `token_mismatch` |

To create and remove the block rule, see [Produce a failed check on demand](/fraud/risky-transactions#produce-a-failed-check-on-demand). Remove every test rule when you finish.

After each test, open the [Users](https://dashboard.radar.com/geofencing/users) page and confirm that the test user shows the devices you used.

## Production checklist

- [ ] `Radar.setUserId()` is called with the authenticated user before any verified location check.
- [ ] Both tokens are verified on your backend with the JWT secret key and an explicit `HS256` allowlist.
- [ ] The risk token is accepted only on an authenticated request, and each `jti` is recorded once.
- [ ] Your backend rejects a geolocation token whose `user.userId` isn't the session user.
- [ ] No rule or code path blocks on a new device, a device count, or a user count alone.
- [ ] What your product does at each risk level was chosen for each checkpoint and has an owner who reviews it against recorded outcomes.
- [ ] A missing or invalid risk token is treated as unknown risk, not as no risk.
- [ ] Account takeover and account sharing have separate follow-up actions.
- [ ] Each result is stored with the Radar assessment ID or check ID.
- [ ] Analysts have dashboard access and know how to record an outcome.
- [ ] New fraud rules start with **Open case** only.
- [ ] Production builds use a Live publishable key, and neither token is written to logs.
- [ ] Confirmed takeovers and cleared reviews are recorded as [labels](/fraud/overview#labels-and-feedback).
