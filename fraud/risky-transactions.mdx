By the end of this guide, a sensitive action in your app, such as a payment, a cashout, or revealing account details, goes through a risk assessment first. When Radar reports a risk level of `none` or `low`, the action continues without interruption. When the level is `medium` or `high`, or no assessment is available, the user must pass a verified location check before your backend authorizes the action.

Your backend reads two results from Radar. From the risk assessment:

```json
{
  "risk": {
    "level": "high",
    "reasons": ["fraud_proxy_known_proxy_ip"]
  }
}
```

From the verified location check that follows, bound to the user and the transaction:

```json
{
  "passed": true,
  "failureReasons": [],
  "transactionId": "txn-789",
  "user": {
    "userId": "user-123"
  }
}
```

Payments, cashouts, and account details are examples of where you might place this flow in your own product. They aren't Radar features.

If the action always requires the user to be in a particular place, regardless of risk, you don't need the risk step. See [Verify location for non-gaming use cases](/geo-compliance/non-gaming), which runs the same verified location check and backend validation as a fixed condition.

## Complete example

This is the whole client flow for one withdrawal, and the sections below explain each part. `api` is your own backend client, which calls back on the main thread, and the `show` functions are your UI.

<CodeGroup>

```swift Swift
import CoreLocation
import RadarSDK

// At app launch
Radar.initialize(publishableKey: "prj_test_pk_...")

final class WithdrawalFlow: NSObject, CLLocationManagerDelegate {
  private var locationManager: CLLocationManager?
  private var transactionId = ""

  func withdraw(userId: String, amount: Int) {
    Radar.setUserId(userId)
    api.createWithdrawal(amount: amount) { transactionId in
      self.transactionId = transactionId

      Radar.revealRisk { status, risk in
        // A nil token tells your backend that the risk is unknown.
        let riskToken = status == .success ? risk?.token : nil
        api.sendRiskToken(riskToken, transactionId: transactionId) { result in
          if result.authorized { showDone() } else { self.requestLocation() }
        }
      }
    }
  }

  // Elevated or unknown risk: your backend asks for a verified location check.
  private func requestLocation() {
    // A new manager reports the current status to locationManagerDidChangeAuthorization.
    locationManager = CLLocationManager()
    locationManager?.delegate = self
  }

  func locationManagerDidChangeAuthorization(_ manager: CLLocationManager) {
    switch manager.authorizationStatus {
    case .notDetermined: manager.requestWhenInUseAuthorization()
    case .authorizedWhenInUse, .authorizedAlways: verifyLocation()
    default: showLocationNeeded()
    }
  }

  private func verifyLocation() {
    locationManager = nil
    Radar.trackVerified(
      beacons: false,
      desiredAccuracy: .medium,
      reason: "withdrawal",
      transactionId: transactionId
    ) { status, token in
      guard status == .success, let jwt = token?.token else {
        // The check didn't complete. No token was issued.
        showTryAgain(status)
        return
      }
      api.sendGeolocationToken(jwt, transactionId: self.transactionId) { result in
        if result.authorized { showDone() } else { showFailed(result.failureReasons) }
      }
    }
  }
}
```

```kotlin Kotlin
import android.Manifest
import androidx.activity.result.contract.ActivityResultContracts
import androidx.appcompat.app.AppCompatActivity
import io.radar.sdk.Radar
import io.radar.sdk.RadarInitializeOptions
import io.radar.sdk.RadarTrackingOptions

// In Application.onCreate()
Radar.initialize(
  context = this,
  publishableKey = "prj_test_pk_...",
  options = RadarInitializeOptions(fraud = true)
)

class WithdrawalActivity : AppCompatActivity() {
  private var transactionId = ""

  private val locationPermission = registerForActivityResult(
    ActivityResultContracts.RequestMultiplePermissions()
  ) { grants ->
    if (grants.values.any { it }) verifyLocation() else showLocationNeeded()
  }

  fun withdraw(userId: String, amount: Int) {
    Radar.setUserId(userId)
    api.createWithdrawal(amount) { id ->
      transactionId = id

      Radar.revealRisk { status, risk ->
        // A null token tells your backend that the risk is unknown.
        val riskToken = if (status == Radar.RadarStatus.SUCCESS) risk?.token else null
        api.sendRiskToken(id, riskToken) { result ->
          if (result.authorized) showDone() else requestLocation()
        }
      }
    }
  }

  // Elevated or unknown risk: your backend asks for a verified location check.
  private fun requestLocation() {
    locationPermission.launch(
      arrayOf(
        Manifest.permission.ACCESS_FINE_LOCATION,
        Manifest.permission.ACCESS_COARSE_LOCATION
      )
    )
  }

  private fun verifyLocation() {
    Radar.trackVerified(
      beacons = false,
      desiredAccuracy = RadarTrackingOptions.RadarTrackingOptionsDesiredAccuracy.MEDIUM,
      reason = "withdrawal",
      transactionId = transactionId
    ) { status, token ->
      if (status != Radar.RadarStatus.SUCCESS || token == null) {
        // The check didn't complete. No token was issued.
        showTryAgain(status)
        return@trackVerified
      }
      api.sendGeolocationToken(transactionId, token.token) { result ->
        if (result.authorized) showDone() else showFailed(result.failureReasons)
      }
    }
  }
}
```

```javascript JavaScript
import Radar from 'radar-sdk-js';
import { createFraudPlugin } from '@radarlabs/plugin-fraud';

// When the page loads
Radar.registerPlugin(createFraudPlugin());
Radar.initialize('prj_test_pk_...');

export async function withdraw(userId, amount) {
  Radar.setUserId(userId);
  const { transactionId } = await api.createWithdrawal(amount);

  let riskToken = null;
  try {
    riskToken = (await Radar.fraud.revealRisk()).token ?? null;
  } catch (err) {
    // The assessment didn't complete. Your backend treats the risk as unknown.
  }

  let result = await api.sendRiskToken(transactionId, riskToken);
  if (result.authorized) return showDone();

  // Elevated or unknown risk: your backend asks for a verified location check.
  // The browser shows its location prompt when the check runs.
  let geolocationToken;
  try {
    const check = await Radar.fraud.trackVerified({
      skipVerifyApp: true,
      reason: 'withdrawal',
      transactionId,
    });
    geolocationToken = check.token;
  } catch (err) {
    // The check didn't complete. No token was issued.
    return err.status === 'ERROR_PERMISSIONS' ? showLocationNeeded() : showTryAgain(err.status);
  }

  result = await api.sendGeolocationToken(transactionId, geolocationToken);
  return result.authorized ? showDone() : showFailed(result.failureReasons);
```

Your backend creates the transaction, verifies both tokens with your project's JWT secret key, and authorizes the withdrawal. `requireSession`, `transactions`, and `releaseWithdrawal` are your own session middleware, store, and downstream call.

<CodeGroup>

```javascript Node.js
import { randomUUID } from 'node:crypto';
import express from 'express';
import { jwtVerify } from 'jose';

const app = express();
app.use(express.json());

const secret = new TextEncoder().encode(process.env.RADAR_JWT_SECRET_KEY);

// Checks the signature and the expiry, and accepts HS256 only.
async function verifyRadarToken(token) {
  const { payload } = await jwtVerify(token ?? '', secret, { algorithms: ['HS256'] });
  return payload;
}

app.post('/api/withdrawals', requireSession, async (req, res) => {
  const transaction = await transactions.create({
    id: `txn-${randomUUID()}`,
    userId: req.session.userId,
    amount: req.body.amount,
    status: 'awaiting_risk',
    expiresAt: Date.now() + 10 * 60 * 1000,
  });
  res.status(201).json({ transactionId: transaction.id });
});

app.post('/api/withdrawals/:id/risk', requireSession, async (req, res) => {
  const transaction = await transactions.getOpen(req.params.id, req.session.userId, 'awaiting_risk');
  if (!transaction) return res.status(409).json({ authorized: false });

  let risk = null;
  try {
    const assessment = await verifyRadarToken(req.body.riskToken);
    // The token has no user ID. Record its jti against this transaction, once.
    if (await transactions.recordRiskAssessment(transaction.id, assessment.jti)) {
      risk = assessment.risk;
    }
  } catch (err) {
    // Missing, changed, or expired. The risk stays unknown.
  }

  if (risk?.level === 'none' || risk?.level === 'low') {
    if (await transactions.transition(transaction.id, 'awaiting_risk', 'authorized')) {
      await releaseWithdrawal(transaction.id);
    }
    return res.json({ authorized: true });
  }

  // Medium, high, or unknown risk: ask for a verified location check.
  await transactions.transition(transaction.id, 'awaiting_risk', 'awaiting_location');
  res.json({ authorized: false, locationRequired: true });
});

app.post('/api/withdrawals/:id/location', requireSession, async (req, res) => {
  const transaction = await transactions.getOpen(req.params.id, req.session.userId, 'awaiting_location');
  if (!transaction) return res.status(409).json({ authorized: false });

  let check;
  try {
    check = await verifyRadarToken(req.body.geolocationToken);
  } catch (err) {
    return res.status(400).json({ authorized: false, error: 'token_invalid' });
  }

  // The check must be for this user, this transaction, and this environment.
  const live = process.env.NODE_ENV !== 'production' || check.user?.live === true;
  if (check.user?.userId !== req.session.userId || check.transactionId !== transaction.id || !live) {
    return res.status(400).json({ authorized: false, error: 'token_mismatch' });
  }

  if (check.passed !== true) {
    return res.status(403).json({
      authorized: false,
      passed: false,
      failureReasons: check.failureReasons ?? [],
    });
  }

  if (await transactions.transition(transaction.id, 'awaiting_location', 'authorized')) {
    await releaseWithdrawal(transaction.id);
  }
  res.json({ authorized: true });
});
```

## Prerequisites

- **Access**: A Radar project with Fraud enabled. The device and network risk assessment must be enabled for your project. Contact your Radar account team.
- **SDK and plugin**: The Radar SDK and fraud plugin for your platform. See [Fraud plugin setup](/sdk/fraud). The examples use iOS SDK 3.46.0, Android SDK 4.3.0, and Web SDK 5.3.0 with `@radarlabs/plugin-fraud` 1.6.1. `Radar.revealRisk()` requires iOS SDK 3.38.0 or later, Android SDK 3.35.0 or later, `@radarlabs/plugin-fraud` 1.4.0 or later, or React Native SDK 4.36.0 or later. The verified location check with `reason` and `transactionId` is available on the clients listed in [Supported clients](#supported-clients).
- **Keys**: A publishable key in your app. The project's JWT secret key on your backend only. See [Set up organizations, projects, accounts, and authentication](/fundamentals/authentication-and-access).
- **Identity**: An authenticated user, with `Radar.setUserId()` called with that user's ID before the verified location check. The `userId` is nullable, so you can set it to `nil` or `null` when the user logs out. See [Handle login, logout, and user switching](/fundamentals/authentication-and-access#handle-login-logout-and-user-switching).
- **Permission**: Location permission is needed only for the verified location check. Foreground permission is enough. For the platform prompts, see [Understand foreground and background location permissions](/fundamentals/location-permissions).
- **Environment**: Build and test with Test keys. Switch to Live keys only in production builds.

## How it works

| Party | Responsibility |
| --- | --- |
| Your app | Starts the transaction, calls `Radar.revealRisk()`, sends the risk token to your backend, and, when asked, requests location permission, runs the verified location check, and sends the geolocation token. It displays the result. It never authorizes anything. |
| Radar | Collects device and network signals and returns a signed risk assessment. For the verified location check, collects the location with integrity signals, evaluates it, and returns a signed geolocation token. |
| Your backend | Creates the transaction, verifies both tokens, reads `risk.level` to choose whether the location check is needed, binds the check to the user and the transaction, and authorizes or refuses the action. |
| Your downstream systems | Your payment processor, ledger, or account service acts only after your backend has authorized the transaction. |

The transaction record on your backend has one of these statuses:

| Status | Meaning | Next statuses |
| --- | --- | --- |
| `awaiting_risk` | The transaction exists. No risk result yet. | `authorized`, `awaiting_location`, `expired` |
| `awaiting_location` | The risk level was `medium` or `high`, or no valid assessment arrived. | `authorized`, `expired` |
| `authorized` | Your backend approved the action. This status is final and is used once. | None |
| `expired` | The transaction's time limit passed before it was authorized. | None. The user starts a new transaction. |

A transaction in `awaiting_location` stays there through permission prompts, retries, failed checks, and technical errors. Only a verified geolocation token for the same user and the same transaction, with `passed` set to `true`, moves it to `authorized`.

## Create the transaction on your backend

Create the transaction before any Radar call, on an authenticated request, as the `POST /api/withdrawals` route in the [complete example](#complete-example) does. Generate the transaction ID on your backend so your app can't choose it. Give the transaction a time limit that fits the action. The example uses 10 minutes.

The `transactions` store is yours. The example relies on three of its operations:

| Operation | What it must do |
| --- | --- |
| `getOpen(id, userId, status)` | Return the transaction only if it belongs to that user, has that status, and hasn't passed `expiresAt`. |
| `recordRiskAssessment(id, jti)` | Store the assessment ID against the transaction, and return `false` if that `jti` was already used. |
| `transition(id, from, to)` | Change the status with a compare-and-set, and return `false` if the status was no longer `from`. |

## Assess risk for the transaction

In your app, call `Radar.revealRisk()` and send the token with the transaction ID. If the call fails or returns no token, still call your backend route without a token, so your backend can ask for the verified location check.

On your backend, verify the token before you read it, then read `risk.level`. The whole application decision in this guide is this branch from the `/risk` route:

```javascript Node.js
if (risk?.level === 'none' || risk?.level === 'low') {
  // Authorize now.
} else {
  // Medium, high, or unknown risk: ask for a verified location check.
}
```

Which levels go on which side is your choice for each action. Record `risk.level` and `risk.reasons` with the transaction so you can review that choice against real outcomes. Unknown risk, from a missing, invalid, expired, or reused token, takes the location path, because unknown risk isn't low risk.

The risk assessment has no user ID. It is tied to the user and the transaction only because your backend received it on that user's authenticated request for that transaction and recorded its `jti`.

## Ask for location permission

When your backend asks for the location check, explain to the user why you need their location for this action before the operating system prompt appears. Then request foreground location permission, as each tab of the complete example does. On the web, the browser shows its own prompt when the check runs. For the platform details, see [Understand foreground and background location permissions](/fundamentals/location-permissions).

Granting permission isn't verification. It only makes the check possible. The transaction stays in `awaiting_location` until a check passes and your backend verifies it.

If the user declines, don't run the check. Show what they can do instead, and leave the transaction in `awaiting_location` until it expires. See [Recover from errors and degraded paths](#recover-from-errors-and-degraded-paths).

## Request the verified location check

Run one verified location check for the transaction. Pass the transaction ID from your backend as `transactionId`, and a `reason` from your fixed set.

## Authorize the original action

The `/location` route in the [complete example](#complete-example) applies that procedure to the transaction, in this order:

1. Load the transaction for the session user, and continue only if its status is `awaiting_location` and it hasn't expired.
2. Verify the token's signature, algorithm, and expiry. A token that fails here verified nothing, so the transaction is unchanged and your app runs a new check.
3. Compare `user.userId` with the session user and `transactionId` with the transaction, and in production require `user.live` to be `true`.
4. Read `passed`. When it isn't `true`, respond with `failureReasons` and leave the transaction in `awaiting_location`.
5. Move the transaction to `authorized` with a compare-and-set, so two concurrent requests can't both release the action, and only then call your downstream system.

After a failed check, the example lets the user correct the cause, such as disconnecting a VPN, and run a new check with the same `transactionId` until the transaction expires. If your product ends the transaction on the first failed check instead, mark it so in your own record at step 4.

## Check proximity to an expected address

This step is optional. Some actions are less risky when the user is at an address you already hold for them, such as a billing address. You can add that comparison to the verified location check.

<Info>
  Address verification must be enabled for your project. Contact your Radar account team.
</Info>

Call `Radar.setExpectedAddress()` with the address before the verified location check. Radar geocodes the address and compares it with the location of the check. The method is available on iOS SDK 3.42.0 or later and Android SDK 3.38.0 or later. The web fraud plugin exposes it as `Radar.fraud.setExpectedAddress()`. Radar sends the address with each later check until you clear it by passing `nil` in Swift or `null` in Kotlin, or by calling `Radar.fraud.setExpectedAddress()` with no argument on web.

<CodeGroup>

```swift Swift
Radar.setExpectedAddress("123 Example St, New York, NY 10001")
// Then run the verified location check for the transaction.
```

```kotlin Kotlin
Radar.setExpectedAddress("123 Example St, New York, NY 10001")
// Then run the verified location check for the transaction.
```

```javascript JavaScript
Radar.fraud.setExpectedAddress('123 Example St, New York, NY 10001');
// Then run the verified location check for the transaction.
```

</CodeGroup>

The result is in `user.expectedAddress` in the validated token. Read `atAddress`, `distance`, and `confidence`. See [Expected address fields](/api/geolocation-tokens#expected-address-fields). When the user isn't at the address, the token includes the warning `address_not_expected`. A warning doesn't change `passed`.

Be precise about what this establishes:

| It tells you | It doesn't tell you |
| --- | --- |
| At the time of the check, the verified location was within the configured distance of the point Radar geocoded for the address, with the stated confidence. | That the user lives or works there, that the address is formatted correctly or deliverable, or that the user is who they claim to be. |

Read the result on your backend from the validated token, and treat it as one input:

```javascript Node.js
// payload is the verified geolocation token payload.
const address = payload.user.expectedAddress;
const atExpectedAddress =
  address?.atAddress === true && (address.confidence === 'high' || address.confidence === 'medium');
```

Which confidence values you accept is your choice. A `confidence` of `unknown` means the address couldn't be geocoded or the location accuracy wasn't available, so treat it as "not established".

## Handle results and errors

Your backend reads two results from Radar and responds to your app once for each request.

### Read the risk assessment

For the assessment fields, see [Read the result](/fraud/overview#read-the-result). In this flow, your backend reads `risk.level` to choose whether the verified location check is needed, and records it with `risk.reasons` on the transaction. Your app doesn't make that choice.

### Result for every branch

Each branch ends in exactly one result. No branch authorizes the action on the client.

| Branch | How you detect it | Transaction status | What the user sees |
| --- | --- | --- | --- |
| Risk level `none` or `low` | A valid risk token with that `risk.level` | `authorized` | The action completes. |
| Risk level `medium` or `high` | A valid risk token with that `risk.level` | `awaiting_location` | An explanation, then the location prompt. |
| Risk assessment unavailable | Your app sends no token, or the token is invalid, expired, or already used | `awaiting_location` | The same explanation and prompt. Unknown risk isn't low risk. |
| Permission denied | The user declines the prompt, or the check returns `ERROR_PERMISSIONS` | `awaiting_location` | Why location is needed, how to turn it on in settings, and your alternative, such as contacting support. |
| Location unavailable | The check returns `ERROR_LOCATION` | `awaiting_location` | A request to turn on location services and Wi-Fi, and a button to try again. |
| Technical error | The check returns `ERROR_NETWORK`, `ERROR_SERVER`, or another error status, and no token | `awaiting_location` | A request to check the connection and try again. |
| User cancelled | The user leaves before a check completes. Radar sends no signal for this. | `awaiting_location` until the time limit, then `expired` | The action isn't completed. They can start again. |
| Token expired | Your backend's verification fails because `exp` has passed | `awaiting_location` | Your app runs a new check with the same `transactionId` and resends. |
| Token for another user or transaction | `user.userId` or `transactionId` in the verified token doesn't match | `awaiting_location` | A general error. Your app sets the correct user ID and runs a new check. |
| Failed check | A verified token for this user and transaction with `passed` set to `false` | `awaiting_location` | A message based on `failureReasons`, for example to enable precise location for `fraud_inaccurate_exceeded_accuracy_threshold`. |
| Passed check | A verified token for this user and transaction with `passed` set to `true` | `authorized` | The action completes. Record any `warningReasons` with the transaction. |
| Transaction expired | Your own time limit passed | `expired` | The action timed out. They start a new transaction. |

### Recover from errors and degraded paths

Apply these rules to every retry and failure:

- **Keep one transaction ID through retries**: A retry after a technical error, an expired token, a failed check, or a permission change uses the same `transactionId`. A new transaction gets a new ID and starts again from the risk assessment.
- **Authorize once**: Move the transaction to `authorized` with a compare-and-set, as in the example, so a repeated or concurrent request can't release the action twice. Radar returns `transactionId` unchanged and doesn't enforce single use.
- **Permission approval isn't success**: After the user grants permission, the check can still fail or return an error. Read the check result, not the permission state.
- **Unknown risk isn't low risk**: When the risk assessment is unavailable, require the verified location check. When the check can't complete, the action stays unauthorized. Offer the user another route, such as support or a different verification method that you operate.
- **Don't loop on a failed check**: A failed check means Radar reached a conclusion. Let the user change something first, such as disconnecting a VPN, and then run a new check.
- **App backgrounded during the check**: When the app returns to the foreground, ask your backend for the transaction's current status before continuing. If the transaction expired, start again.
- **User changes during the flow**: If the signed-in user changes, discard the transaction in your app, call `Radar.setUserId()` with the new user, and start a new transaction. Your backend rejects a token whose `user.userId` doesn't match the session.
- **Unknown reasons**: `risk.reasons` and `failureReasons` can contain values that aren't documented. Record them and show a general message.

## Production checklist

- [ ] Your backend creates the transaction ID. Your app never chooses it.
- [ ] The risk token and the geolocation token are both validated on your backend with the JWT secret key and an explicit `HS256` allowlist.
- [ ] A missing, invalid, or expired risk token leads to the verified location check, not to direct authorization.
- [ ] The risk levels that need the verified location check were chosen for this action and have an owner who reviews them against recorded outcomes.
- [ ] The geolocation token is bound to the authenticated user and to the transaction ID.
- [ ] The transaction is authorized at most once, with an atomic state change.
- [ ] Every branch in [Result for every branch](#result-for-every-branch) has a tested client message and a tested transaction status.
- [ ] No code path authorizes the action from a client-side value.
- [ ] Production builds use a Live publishable key, and your backend rejects tokens with `user.live` set to `false`.
- [ ] The JWT secret key is in a secret manager, and neither token is written to logs.
- [ ] Each transaction record stores the Radar assessment ID and check ID, so an analyst can [inspect the check](/fraud/overview#inspect-a-check).
- [ ] No bypass rule exists in the Live environment for a real user.
- [ ] Confirmed outcomes, such as chargebacks, are sent back as [labels](/fraud/overview#labels-and-feedback).
