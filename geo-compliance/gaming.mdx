At the end of this guide, your app runs a verified location check for the signed-in player and the selected product, and your backend performs wagers, contest entries, deposits, and withdrawals only when the geolocation token it verified has `passed` set to `true`. The guide covers sportsbooks, casinos, daily fantasy sports, prediction markets, and sweepstakes.

After your backend verifies a token, the payload includes these fields:

```json
{
  "passed": true,
  "failureReasons": [],
  "product": "sportsbook",
  "reason": "login",
  "user": {
    "userId": "user-123",
    "state": {
      "code": "NJ",
      "allowed": true,
      "passed": true
    }
  }
}
```

## Complete example

This is the whole client side of one check on each platform. The sections below explain each part.

<CodeGroup>

```swift Swift
import CoreLocation
import RadarSDK

final class LocationCheck: NSObject, CLLocationManagerDelegate {
  private let locationManager = CLLocationManager()

  func start() {
    Radar.initialize(publishableKey: "prj_test_pk_...")
    Radar.setUserId("user-123")
    Radar.setProduct("sportsbook")

    locationManager.delegate = self
    locationManager.requestWhenInUseAuthorization()
  }

  func locationManagerDidChangeAuthorization(_ manager: CLLocationManager) {
    let status = manager.authorizationStatus
    if status == .authorizedWhenInUse || status == .authorizedAlways {
      check(reason: "login")
    }
  }

  func check(reason: String) {
    Radar.trackVerified(
      beacons: false,
      desiredAccuracy: .medium,
      reason: reason,
      transactionId: nil
    ) { (status, token) in
      guard status == .success, let token = token, let jwt = token.token else {
        showCheckError(status)
        return
      }

      if token.passed {
        sendTokenToBackend(jwt)
      } else {
        showFailure(token.failureReasons ?? [])
      }
    }
  }
}
```

The backend verifies the token and reads `passed`:

<CodeGroup>

```javascript Node.js
import express from 'express';
import { jwtVerify } from 'jose';
import { requireSession } from './auth.js';

const secret = new TextEncoder().encode(process.env.RADAR_JWT_SECRET_KEY);
const app = express();
app.use(express.json());

app.post('/api/wagers', requireSession, async (req, res) => {
  let payload;
  try {
    ({ payload } = await jwtVerify(req.body.geolocationToken, secret, {
      algorithms: ['HS256'],
    }));
  } catch (err) {
    return res.status(401).json({ error: 'invalid_geolocation_token' });
  }

  if (payload.user?.userId !== req.session.userId || payload.product !== 'sportsbook') {
    return res.status(401).json({ error: 'invalid_geolocation_token' });
  }

  if (payload.passed !== true) {
    return res.status(403).json({ passed: false, failureReasons: payload.failureReasons });
  }

  // Place the wager.
  res.status(201).json({ placed: true });
});
```

```python Python
import os

import jwt  # PyJWT
from flask import Flask, jsonify, request, session

app = Flask(__name__)
app.secret_key = os.environ["SESSION_SECRET_KEY"]
SECRET = os.environ["RADAR_JWT_SECRET_KEY"]


@app.post("/api/wagers")
def place_wager():
    if "user_id" not in session:
        return jsonify(error="not_signed_in"), 401

    body = request.get_json(silent=True) or {}
    try:
        payload = jwt.decode(body.get("geolocationToken", ""), SECRET, algorithms=["HS256"])
    except jwt.InvalidTokenError:
        return jsonify(error="invalid_geolocation_token"), 401

    user_id = (payload.get("user") or {}).get("userId")
    if user_id != session["user_id"] or payload.get("product") != "sportsbook":
        return jsonify(error="invalid_geolocation_token"), 401

    if payload.get("passed") is not True:
        return jsonify(passed=False, failureReasons=payload.get("failureReasons", [])), 403

    # Place the wager.
    return jsonify(placed=True), 201
```

## Prerequisites

- Fraud is enabled for your project under **Fraud** on the [Settings](https://dashboard.radar.com/settings#fraud-settings) page of the Radar dashboard.
- The Radar SDK and fraud plugin are installed, and device attestation is configured. See [Fraud plugin setup](/sdk/fraud).
- A Test publishable key for your app, and your project's JWT secret key for your backend. See [Choose the right API key](/fundamentals/authentication-and-access#choose-the-right-api-key).
- Foreground location permission on the device. A check can't succeed without it. See [Understand foreground and background location permissions](/fundamentals/location-permissions).
- A written list, per product, of the countries and states where the product is allowed.

## Select the product

Call `Radar.setUserId()` with the ID your backend uses for the signed-in player, so that your backend can compare the token to the session. See [Handle login, logout, and user switching](/fundamentals/authentication-and-access#handle-login-logout-and-user-switching).

A product is a named configuration inside a project, such as `sportsbook`, `casino`, or `fantasy`, with its own allowed countries and states. Call `Radar.setProduct()` before the check with the product the player is using. `passed` in the token is the result for that product, so when the player switches product, set the new product and run a new check.

If you have one offering with one set of allowed locations, you don't need products. Leave out `Radar.setProduct()`.

To narrow a check to the jurisdiction of the player's session, call `Radar.setExpectedJurisdiction()` with a country code and a state code before the check (`Radar.fraud.setExpectedJurisdiction()` on web).

## Configure allowed locations

Allowed countries and states are set in the **Fraud** section of the [Settings](https://dashboard.radar.com/settings#fraud-settings) page, once for the project and once for each product. Each list is an allowlist or a blocklist, and an empty list allows every country or state. A product setting overrides the project setting with the same name. Changes apply to checks made after you save, and tokens already issued keep their result until they expire.

If the controls are read-only for your account, ask your Radar account team to make the change.

## Choose manual or automatic checks

This guide uses manual checks: your app calls `Radar.trackVerified()` (`Radar.fraud.trackVerified()` on web) when it needs a token, and passes a `reason` on each call.

With automatic checks, the SDK keeps a current token for the session instead. Call `Radar.startTrackingVerified()` once, then `Radar.getVerifiedLocationToken()` before a restricted action. On web, both methods are on `Radar.fraud`. See the verified location section of the [iOS](/sdk/ios#verified-location) or [Android](/sdk/android#verified-location) SDK reference, or [Fraud plugin setup](/sdk/fraud#web) for web. Backend validation is the same for both.

## Choose the web path

On web, the `skipVerifyApp` option of `Radar.fraud.trackVerified()` selects how the check runs.

| Your product and market | Recommended path | `skipVerifyApp` |
| --- | --- | --- |
| A sportsbook or casino in the US or Canada | The Radar Verify companion app. The player installs Radar Verify for Mac or Windows once, and the check runs through the app. | `false`, which is the default |
| Any other product, such as daily fantasy sports, a prediction market, or sweepstakes, and any other market | Verify without the app. The check runs in the browser and the player installs nothing. | `true` |

With the companion app, the call fails with `ERROR_VERIFY_APP` (`RadarVerifyAppError`) when the app isn't installed or isn't running. Tell the player to open or install Radar Verify, then run the check again. For download links, see [Choose the companion app or the no-download path](/sdk/fraud#choose-the-companion-app-or-the-no-download-path).

## Verify from a native desktop app

A native macOS or Windows app runs the check itself with the Radar Verify SDK, as shown in the macOS and Windows tabs of [Complete example](#complete-example). The Mac and Windows SDKs are available on request. See [Desktop](/sdk/fraud#desktop).

## Run checks at the right time

Run the first check at login, before you show restricted features. After that, reuse the token until one of these happens:

- **The token expires.** Each token carries its own expiry in `expiresAt`, and tokens issued close to a border expire sooner. Compare the current time to `expiresAt` before each restricted action and when the app returns to the foreground. Don't hardcode an interval. See [Expiry](/api/geolocation-tokens#expiry).
- **The player changes product.** Call `Radar.setProduct()` with the new product, then run a check.
- **The SDK reports an IP change.** Implement `didChangeIP()` on your `RadarVerifiedDelegate` on iOS, override `onIpChanged()` on your `RadarVerifiedReceiver` on Android, or register a callback with `Radar.fraud.onIpChanged()` on web. In the callback, discard the last token and run a check.

Run one check at a time. If a check is in progress when another is triggered, wait for the first result.

For a single-use action such as a withdrawal, generate a `transactionId` on your backend, pass it to the check, and compare it to `transactionId` in the verified token.

## Record check reasons

Pass a `reason` on every check, such as `login`, `wager`, or `withdrawal`. Radar returns it in the token as `reason` and shows it on the [Locations](https://dashboard.radar.com/geofencing/locations) page and in reports, so choose a small fixed set of values and use the same spelling on every platform.

## Validate the response on the backend

Your backend decides, not your app. The `passed` value your app reads is for your UI, and a player can change anything the client sends, so never perform a restricted action because of a client-supplied `passed`.

The backend block in [Complete example](#complete-example) is the minimum: verify the `HS256` signature and expiry with your project's JWT secret key, compare `user.userId` to the session user and `product` to the product of the action, then read `passed`. In production, also require `user.live` to be `true`, so that a Test environment token isn't accepted.

For every validation step, a reusable Node.js and Python verifier, key changes, and the tests to write, see [Validate a token](/api/geolocation-tokens#validate-a-token).

## Handle results and errors

A failed check is a token with `passed` set to `false`. An error is a status other than success, with no token. Neither performs the action, and they need different messages.

| Result or error | What it means | What to do |
| --- | --- | --- |
| `passed` is `true` | The player passed the jurisdiction and fraud checks for the product. | Send the token to your backend. |
| `passed` is `false` with a jurisdiction reason, such as `state_not_allowed` | The product isn't allowed at this location. | Say the product isn't available here. Let the player check again after they move. |
| `passed` is `false` with a fraud reason, such as `fraud_proxy_known_proxy_ip` | A device or network signal failed. | Say what to change, such as disconnecting from a VPN, and offer a new check. |
| `ERROR_PERMISSIONS` | Location permission isn't granted. | Explain why location is needed and how to grant it. |
| `ERROR_LOCATION` | The device couldn't determine a location. | Ask the player to turn on location services and Wi-Fi, then run a new check. |
| `ERROR_NETWORK`, `ERROR_SERVER` | The check didn't complete. | Run a new check after a short delay. Don't say the player is ineligible. |
| `ERROR_VERIFY_APP` | Web only. Radar Verify isn't running or isn't installed. | Prompt the player to open or install the app. |
| Your backend rejects the token | The token is expired, or is for another user or product. | Set the right user and product, then run a new check. |

Handle a failure reason you don't recognize with a general message. For every reason and status, see [Failure reasons](/api/geolocation-tokens#failure-reasons) and [Handle a technical error](/api/geolocation-tokens#handle-a-technical-error).

## Test the integration

Use the Test environment with a Test publishable key, the matching JWT secret key on a staging backend, and a named test user.

- **Passing case**: Sign in as the test user from an allowed state. Confirm that a check runs at login, that the token has `passed` set to `true`, and that your backend performs the action.
- **Failing case**: On the **Block rules** page, create a rule that blocks the test user ID, then run a new check. Confirm that the token has `passed` set to `false` with `fraud_blocked_user_id`, and that your backend rejects the action, even when the request body also says `"passed": true`. Remove the rule when you finish.

Bypass rules are for internal testing only. Never apply one to a real player. See [Force a pass or a fail](/fundamentals/testing-and-launch#force-a-pass-or-a-fail), and for backend fixtures, [Negative tests](/api/geolocation-tokens#negative-tests).

## Production checklist

- [ ] Each product's country and state lists match your written list, and no list that is meant to restrict is empty.
- [ ] `Radar.setUserId()` and `Radar.setProduct()` are set before every check, and a product change triggers a new check.
- [ ] A token is reused only until its returned expiry, and one check runs at a time.
- [ ] On web, `skipVerifyApp` follows the recommendation for each product and market.
- [ ] Every restricted endpoint verifies the token's signature, expiry, user, product, and `user.live`, then reads `passed`. None reads a client-supplied `passed`.
- [ ] No JWT secret key in any client, and no bypass rule or test block rule in the Live environment.
