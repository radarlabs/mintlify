At the end of this guide, your app verifies a location condition as a step in a workflow, such as "the employee is at the workplace when they clock in" or "the customer is in the store when they redeem the offer", and your backend performs the action only when the geolocation token it verified has `passed` set to `true` and shows that the condition holds.

For a clock-in at `store-42`, the verified token payload shows a passed check inside the store geofence:

```json
{
  "passed": true,
  "failureReasons": [],
  "reason": "clock_in",
  "transactionId": "txn-789",
  "user": {
    "userId": "user-123",
    "geofences": [
      {
        "tag": "store",
        "externalId": "store-42"
      }
    ]
  }
}
```

```swift Swift
import CoreLocation
import RadarSDK

final class ClockIn: NSObject, CLLocationManagerDelegate {
  private let locationManager = CLLocationManager()
  private var transactionId: String?

  // transactionId comes from your backend for this clock-in.
  func start(transactionId: String) {
    self.transactionId = transactionId
    Radar.initialize(publishableKey: "prj_test_pk_...")
    Radar.setUserId("user-123")

    locationManager.delegate = self
    locationManager.requestWhenInUseAuthorization()
  }

  func locationManagerDidChangeAuthorization(_ manager: CLLocationManager) {
    let status = manager.authorizationStatus
    if status == .authorizedWhenInUse || status == .authorizedAlways {
      check()
    }
  }

  func check() {
    Radar.trackVerified(
      beacons: false,
      desiredAccuracy: .medium,
      reason: "clock_in",
      transactionId: transactionId
    ) { (status, token) in
      guard status == .success, let token = token, let jwt = token.token else {
        showCheckError(status)
        return
      }

      if token.passed {
        sendClockIn(jwt)
      } else {
        showFailure(token.failureReasons ?? [])
      }
    }
  }
}
```

The backend verifies the token, reads `passed`, and then checks the geofence:

<CodeGroup>

```javascript Node.js
import express from 'express';
import { jwtVerify } from 'jose';
import { requireSession } from './auth.js';
import { loadShift, recordClockIn } from './shifts.js';

const secret = new TextEncoder().encode(process.env.RADAR_JWT_SECRET_KEY);
const app = express();
app.use(express.json());

app.post('/api/shifts/:shiftId/clock-in', requireSession, async (req, res) => {
  const shift = await loadShift(req.params.shiftId, req.session.userId);

  let payload;
  try {
    ({ payload } = await jwtVerify(req.body.geolocationToken, secret, {
      algorithms: ['HS256'],
    }));
  } catch (err) {
    return res.status(401).json({ error: 'invalid_geolocation_token' });
  }

  if (
    payload.user?.userId !== req.session.userId ||
    payload.transactionId !== shift.clockInTransactionId
  ) {
    return res.status(401).json({ error: 'invalid_geolocation_token' });
  }

  if (payload.passed !== true) {
    return res.status(403).json({ passed: false, failureReasons: payload.failureReasons });
  }

  // passed doesn't say which store. Check the geofence your records require.
  const geofences = payload.user.geofences ?? [];
  if (!geofences.some((geofence) => geofence.externalId === shift.storeExternalId)) {
    return res.status(403).json({ error: 'not_at_required_location' });
  }

  await recordClockIn(shift, payload._id);
  res.status(201).json({ clockedIn: true });
});
```

```python Python
import os

import jwt  # PyJWT
from flask import Flask, jsonify, request, session

from shifts import load_shift, record_clock_in

app = Flask(__name__)
app.secret_key = os.environ["SESSION_SECRET_KEY"]
SECRET = os.environ["RADAR_JWT_SECRET_KEY"]


@app.post("/api/shifts/<shift_id>/clock-in")
def clock_in(shift_id):
    if "user_id" not in session:
        return jsonify(error="not_signed_in"), 401

    shift = load_shift(shift_id, session["user_id"])

    body = request.get_json(silent=True) or {}
    try:
        payload = jwt.decode(body.get("geolocationToken", ""), SECRET, algorithms=["HS256"])
    except jwt.InvalidTokenError:
        return jsonify(error="invalid_geolocation_token"), 401

    user = payload.get("user") or {}
    if (
        user.get("userId") != session["user_id"]
        or payload.get("transactionId") != shift.clock_in_transaction_id
    ):
        return jsonify(error="invalid_geolocation_token"), 401

    if payload.get("passed") is not True:
        return jsonify(passed=False, failureReasons=payload.get("failureReasons", [])), 403

    # passed doesn't say which store. Check the geofence your records require.
    geofences = user.get("geofences") or []
    if not any(g.get("externalId") == shift.store_external_id for g in geofences):
        return jsonify(error="not_at_required_location"), 403

    record_clock_in(shift, payload["_id"])
    return jsonify(clockedIn=True), 201
```

## Prerequisites

- **Access**: Fraud is enabled for your project under **Fraud** on the [Settings](https://dashboard.radar.com/settings#fraud-settings) page of the Radar dashboard.
- **Platform**: iOS, Android, React Native, web, or a native macOS or Windows app. Use a Radar SDK and fraud plugin pair from the [compatibility table](/sdk/fraud#compatibility).
- **SDK versions**: The examples use iOS SDK 3.46.0, Android SDK 4.3.0, and Web SDK 5.3.0 with `@radarlabs/plugin-fraud` 1.6.1.
- **Platform setup**: The fraud plugin is installed. See [Fraud plugin setup](/sdk/fraud).
- **Keys**: A Test publishable key for your app and your project's JWT secret key for your backend.
- **Backend**: An authenticated endpoint for the workflow step, a JWT library that supports `HS256`, and your own record of which location each action requires.
- **Permissions**: Foreground location permission on the device.
- **Place condition**: Geofences for your stores, workplaces, or service locations, each with a stable `externalId`. See [Detect geofence events and place visits](/geofencing/geofences-and-places).
- **Address condition**: Address verification for your project. See [Address condition](#address-condition).

## How it works

| Party | Responsibility |
| --- | --- |
| Your app | Identifies the user, requests location permission, runs one check at the workflow step, and sends the token with the action. |
| Radar | Collects location with device and network integrity signals, runs fraud and jurisdiction checks, and returns a signed token that includes the verified location, the custom geofences it is inside, and, when requested, the expected-address comparison. |
| Your backend | Verifies the token, reads `passed`, then checks the location condition against the location that your own records require for this action. It performs the action only when both hold. |
| Your downstream systems | Timekeeping, order, or account systems act only after your backend has verified the token and checked the condition. |

Use this page when the location condition is part of the workflow: every user who reaches the step is checked, and the step doesn't proceed without it.

Use [Detect risky transactions and verify precise location](/fraud/risky-transactions) when location is a step-up: you assess device and network risk first, and ask for precise location only when the risk result calls for it.

| | This guide | Risky transactions guide |
| --- | --- | --- |
| When the check runs | Always, at a defined step | Only when a risk assessment triggers it |
| What starts it | The workflow | A risk result |
| What your backend checks | Whether the location condition holds | Whether the original action can proceed after the step-up |

## Choose the location condition

Decide what the step needs to establish before you write code. The three conditions use the same check and read different fields.

| Condition | Example | What your backend reads | What it establishes |
| --- | --- | --- | --- |
| In an allowed region | A service offered only in certain states or countries | `passed`, with `user.country` and `user.state` | The device passed fraud checks, and its location was in a country and state your settings allow, at the time of the check. |
| Inside a specific place | Clock-in at a workplace, in-store redemption, a technician at a service location | `passed`, then `user.geofences` for the required `externalId` or `tag` | The device passed fraud checks, and its location was inside that geofence's boundary at the time of the check. |
| Near an expected address | A delivery handoff or a visit at an address on file | `passed`, then `user.expectedAddress.atAddress` and `user.expectedAddress.confidence` | The device passed fraud checks, and its location was within the distance threshold of the point Radar geocoded for that address. |

### What a check does not establish

Keep these apart in your product language, your logs, and your backend field names:

- **Address formatting or validity**: Whether an address is real and well formed is address validation. See [Autocomplete, geocode, and validate addresses](/maps/addresses).
- **Proximity to an address**: `atAddress` says the device was near the geocoded point for an address at one moment.
- **Residence**: A check near an address doesn't show that the user lives or works there. One check is one observation.
- **Fraud risk**: `passed` includes the fraud checks for this check. It isn't a risk score for the user. See [Understand risk scores and decisions](/fraud/overview#understand-risk-scores-and-decisions).
- **Identity**: The token carries the user ID your client set. Your backend's session establishes who the user is.
- **Regulatory acceptance**: Whether a verified location check satisfies a specific legal or contractual requirement is for your compliance team to determine.

A token with `passed` set to `true` doesn't say the user is at a particular store. Unless your backend checks the place or address condition, it has only verified a region.

## Configure the location condition

### Region condition

Set the country list and state list in the **Fraud** section of the [Settings](https://dashboard.radar.com/settings#fraud-settings) page. Each list is an allowlist or a blocklist, and an empty list allows every country or state. If your workflow has no region restriction, leave the lists empty so that `passed` reflects the fraud checks only. Whether you can edit the lists yourself is account-specific. See [Who can change jurisdiction settings and block or bypass rules](/fundamentals/authentication-and-access#who-can-change-jurisdiction-settings-and-block-or-bypass-rules).

### Place condition

<Steps>
  <Step title="Create the geofences">
    Create one geofence for each store, workplace, or service location, or import them in bulk. See [Detect geofence events and place visits](/geofencing/geofences-and-places).
  </Step>
  <Step title="Set an external ID and a tag">
    Give each geofence an `externalId` that matches the ID in your own system, such as `store-42`, and a `tag` for its type, such as `store`.
  </Step>
  <Step title="Draw the boundary">
    Draw the boundary to cover the area where the action is legitimate. Location accuracy indoors varies, so a boundary drawn tightly around a building can exclude users who are inside it.
  </Step>
  <Step title="Confirm the geofence in a token">
    Run a check from inside one geofence and confirm that it appears in `user.geofences` in the token.
  </Step>
</Steps>

A regular geofence doesn't change `passed`. It is reported in `user.geofences`, and your backend applies the rule.

### Address condition

<Info>
  Address verification must be enabled for your project. Contact your Radar account team.
</Info>

Call `Radar.setExpectedAddress()` with the address from your backend's records before the check (`Radar.fraud.setExpectedAddress()` on web). Radar geocodes the address and compares it to the verified location. This requires iOS SDK 3.42.0 or later, or Android SDK 3.38.0 or later.

<CodeGroup>

```swift Swift
Radar.setExpectedAddress("123 Example St, New York, NY 10001")
```

```kotlin Kotlin
Radar.setExpectedAddress("123 Example St, New York, NY 10001")
```

```javascript JavaScript
Radar.fraud.setExpectedAddress('123 Example St, New York, NY 10001');
```

</CodeGroup>

- The result is in `user.expectedAddress`. See [Expected address fields](/api/geolocation-tokens#expected-address-fields).
- `atAddress` is `true` when the location is within the distance threshold of the geocoded address. The threshold is 60 meters by default. Contact your Radar account team to change it.
- `confidence` is `high`, `medium`, `low`, or `unknown`. It accounts for the accuracy of the location and the uncertainty of the geocoded address. `unknown` means the address couldn't be geocoded or the location accuracy wasn't available.
- When the user isn't at the address, the token includes the warning `address_not_expected`. A warning doesn't fail the check, so `passed` can still be `true`. Your backend must read `atAddress`.
- The SDK sends the address with each later check until you clear it. Pass `nil` in Swift or `null` in Kotlin, or call `Radar.fraud.setExpectedAddress()` with no argument on web, when the workflow ends.

The address your app sends is client input. On your backend, compare `user.expectedAddress.expectedAddress` in the token to the address in your own records before you trust `atAddress`.

### Check the location condition

Token validation tells you the token is authentic, current, for this user, and that the check passed. The location condition is a separate step that you write against the verified payload, which `verifyGeolocationToken` returns in the Node.js example above. The required location comes from your own records, never from the request body.

```javascript Node.js
function isInsideGeofence(payload, externalId) {
  const geofences = payload.user.geofences ?? [];
  return geofences.some((geofence) => geofence.externalId === externalId);
}

function isAtExpectedAddress(payload, addressOnFile) {
  const result = payload.user.expectedAddress;
  // The check must have compared against the address in your records.
  if (!result || result.expectedAddress !== addressOnFile) return false;
  // Choose which confidence levels your workflow accepts.
  const confident = result.confidence === 'high' || result.confidence === 'medium';
  return result.atAddress === true && confident;
}

app.post('/api/shifts/:shiftId/clock-in', requireSession, async (req, res) => {
  const shift = await loadShift(req.params.shiftId, req.session.userId);

  let payload;
  try {
    payload = await verifyGeolocationToken(req.body.geolocationToken, {
      userId: req.session.userId,
      transactionId: shift.clockInTransactionId,
      requireLive: process.env.NODE_ENV === 'production',
    });
  } catch (err) {
    return res.status(401).json({ error: 'invalid_geolocation_token' });
  }

  if (payload.passed !== true) {
    return res.status(403).json({ passed: false, failureReasons: payload.failureReasons });
  }

  // For example 'store-42'
  if (!isInsideGeofence(payload, shift.storeExternalId)) {
    return res.status(403).json({ error: 'not_at_required_location' });
  }

  await recordClockIn(shift, payload._id);
  return res.status(201).json({ clockedIn: true });
});
```

`loadShift`, `recordClockIn`, and the `not_at_required_location` error belong to the example application. For an address condition, call `isAtExpectedAddress` with the address from your records in place of `isInsideGeofence`. Which `confidence` levels to accept is your choice. Start strict and review real results before you relax it.

### Decide every branch

| Outcome | How you detect it | Application action |
| --- | --- | --- |
| Condition met | The token is valid, `passed` is `true`, and the place or address condition holds | Perform the action. |
| Condition not met | The token is valid and `passed` is `true`, and the place or address condition fails | Reject the action. Tell the user where they need to be. Let them check again after they move. |
| Failed check | The token is valid and `passed` is `false` | Reject the action. Show a message based on `failureReasons`, such as disconnecting from a VPN. |
| Permission not granted | Client returns `ERROR_PERMISSIONS`, no token | Don't perform the action. Explain how to grant location access. Offer your manual alternative if you have one. |
| Location unavailable | Client returns `ERROR_LOCATION`, no token | Don't perform the action. Ask the user to turn on location services and Wi-Fi and run a new check. |
| Low-quality location | Token has `fraud_inaccurate_exceeded_accuracy_threshold`, or an address result with `confidence` of `low` or `unknown` | Reject the action or ask for a new check. Don't round up to a pass. |
| Other error | Client returns `ERROR_NETWORK` or `ERROR_SERVER`, no token | Don't perform the action. Run a new check after a short delay, a limited number of times. |
| Expired token | Your backend rejects the token because the current time is past `exp` | Run a new check. |

No branch treats a missing or unverifiable result as presence. If your business needs an exception path, such as a supervisor override for a clock-in, build it as an explicit, logged action in your own system and don't record it as a verified location.

## Test the integration

Use the Test environment with a Test publishable key and a dedicated test account.

1. **Inside**: Stand inside a test geofence, or set an address or coordinates override on the test user so that later checks return a location inside it. Run the step. Confirm that the geofence appears in `user.geofences` and that your backend performs the action. To set an override, open the user in the dashboard, open its menu, and select **Set override**. Remove it when you finish.
2. **Outside**: Move outside the geofence, or change the override to a location outside it. Run the step. Confirm `passed` is `true`, the geofence is absent, and your backend rejects the action.
3. **Wrong place**: Run the step inside a geofence for a different store. Confirm your backend rejects it.
4. **Failed check**: On the **Block rules** page, create a rule that blocks the test user ID, run the step, and confirm the token has `passed` set to `false` with `fraud_blocked_user_id` and your backend rejects it. Remove the rule afterward. Bypass rules are for internal testing only. Never apply them to real users.
5. **Permission not granted**: Deny location permission and run the step. Confirm that no token is sent and the action isn't performed.
6. **Location unavailable**: Turn off location services, or use airplane mode for the network case. Confirm the same.
7. **Backend only**: Send the request directly to your backend with a valid token for a different transaction, with a tampered token, and with `"passed": true` and no token. Confirm each is rejected. For the full list, see [Negative tests](#negative-tests).
8. **Inspect**: Open the check on the [Locations](https://dashboard.radar.com/geofencing/locations) page and confirm the user ID, reason, and transaction ID.

A fixture or an override confirms your code paths. It doesn't confirm how location behaves inside your buildings. Test the place condition on real devices at a real location before launch, at the edges of the boundary and indoors.

For the full block, bypass, and override procedure, see [Test the integration](/geo-compliance/gaming#test-the-integration).

## Production checklist

- [ ] Your backend checks the specific place or address condition, not only `passed`.
- [ ] The required location comes from backend records. An address or geofence ID in the request body is never trusted.
- [ ] Your backend checks signature, algorithm, expiry, user, `transactionId`, `user.live`, and `passed`, and rejects the action when any check fails.
- [ ] Every outcome in [Decide every branch](#decide-every-branch) has a tested path.
- [ ] Geofence boundaries were tested on real devices at real locations.
- [ ] For an address condition, the accepted `confidence` levels are a recorded decision.
- [ ] `Radar.setUserId()` is set at login, and the expected address is cleared when the workflow ends.
- [ ] Every check passes a `reason`.
- [ ] Live publishable key in production clients. JWT secret key only on your backend.
- [ ] No bypass rule or override exists in the Live environment for a real user.
- [ ] Product copy describes the check as what it is: a verified location at a moment in time.
- [ ] The [go-live checklist](/fundamentals/testing-and-launch#go-live-checklist) is complete.
