At the end of this guide, your app verifies a location condition as a step in a workflow, such as "the employee is at the workplace when they clock in" or "the customer is in the store when they redeem the offer", and your backend performs the action only when the geolocation token it verified has `passed` set to `true` and shows that the condition holds.

For a clock-in at `store-42`, the verified token payload shows a passed check inside the store geofence:

```json
{
  "passed": true,
  "failureReasons": [],
  "reason": "clock_in",
  "transactionId": "txn-789",
  "user": {
    "userId": "user-123",
    "geofences": [
      {
        "tag": "store",
        "externalId": "store-42"
      }
    ]
  }
}
```

## Complete example

This is the whole client side of a clock-in check on each platform. The sections below explain each part.

<CodeGroup>

```swift Swift
import CoreLocation
import RadarSDK

final class ClockIn: NSObject, CLLocationManagerDelegate {
  private let locationManager = CLLocationManager()
  private var transactionId: String?

  // transactionId comes from your backend for this clock-in.
  func start(transactionId: String) {
    self.transactionId = transactionId
    Radar.initialize(publishableKey: "prj_test_pk_...")
    Radar.setUserId("user-123")

    locationManager.delegate = self
    locationManager.requestWhenInUseAuthorization()
  }

  func locationManagerDidChangeAuthorization(_ manager: CLLocationManager) {
    let status = manager.authorizationStatus
    if status == .authorizedWhenInUse || status == .authorizedAlways {
      check()
    }
  }

  func check() {
    Radar.trackVerified(
      beacons: false,
      desiredAccuracy: .medium,
      reason: "clock_in",
      transactionId: transactionId
    ) { (status, token) in
      guard status == .success, let token = token, let jwt = token.token else {
        showCheckError(status)
        return
      }

      if token.passed {
        sendClockIn(jwt)
      } else {
        showFailure(token.failureReasons ?? [])
      }
    }
  }
}
```

The backend verifies the token, reads `passed`, and then checks the geofence:

<CodeGroup>

```javascript Node.js
import express from 'express';
import { jwtVerify } from 'jose';
import { requireSession } from './auth.js';
import { loadShift, recordClockIn } from './shifts.js';

const secret = new TextEncoder().encode(process.env.RADAR_JWT_SECRET_KEY);
const app = express();
app.use(express.json());

app.post('/api/shifts/:shiftId/clock-in', requireSession, async (req, res) => {
  const shift = await loadShift(req.params.shiftId, req.session.userId);

  let payload;
  try {
    ({ payload } = await jwtVerify(req.body.geolocationToken, secret, {
      algorithms: ['HS256'],
    }));
  } catch (err) {
    return res.status(401).json({ error: 'invalid_geolocation_token' });
  }

  if (
    payload.user?.userId !== req.session.userId ||
    payload.transactionId !== shift.clockInTransactionId
  ) {
    return res.status(401).json({ error: 'invalid_geolocation_token' });
  }

  if (payload.passed !== true) {
    return res.status(403).json({ passed: false, failureReasons: payload.failureReasons });
  }

  // passed doesn't say which store. Check the geofence your records require.
  const geofences = payload.user.geofences ?? [];
  if (!geofences.some((geofence) => geofence.externalId === shift.storeExternalId)) {
    return res.status(403).json({ error: 'not_at_required_location' });
  }

  await recordClockIn(shift, payload._id);
  res.status(201).json({ clockedIn: true });
});
```

```python Python
import os

import jwt  # PyJWT
from flask import Flask, jsonify, request, session

from shifts import load_shift, record_clock_in

app = Flask(__name__)
app.secret_key = os.environ["SESSION_SECRET_KEY"]
SECRET = os.environ["RADAR_JWT_SECRET_KEY"]


@app.post("/api/shifts/<shift_id>/clock-in")
def clock_in(shift_id):
    if "user_id" not in session:
        return jsonify(error="not_signed_in"), 401

    shift = load_shift(shift_id, session["user_id"])

    body = request.get_json(silent=True) or {}
    try:
        payload = jwt.decode(body.get("geolocationToken", ""), SECRET, algorithms=["HS256"])
    except jwt.InvalidTokenError:
        return jsonify(error="invalid_geolocation_token"), 401

    user = payload.get("user") or {}
    if (
        user.get("userId") != session["user_id"]
        or payload.get("transactionId") != shift.clock_in_transaction_id
    ):
        return jsonify(error="invalid_geolocation_token"), 401

    if payload.get("passed") is not True:
        return jsonify(passed=False, failureReasons=payload.get("failureReasons", [])), 403

    # passed doesn't say which store. Check the geofence your records require.
    geofences = user.get("geofences") or []
    if not any(g.get("externalId") == shift.store_external_id for g in geofences):
        return jsonify(error="not_at_required_location"), 403

    record_clock_in(shift, payload["_id"])
    return jsonify(clockedIn=True), 201
```

## Prerequisites

- Fraud is enabled for your project under **Fraud** on the [Settings](https://dashboard.radar.com/settings#fraud-settings) page of the Radar dashboard.
- The Radar SDK and fraud plugin are installed. See [Fraud plugin setup](/sdk/fraud).
- A Test publishable key for your app, and your project's JWT secret key for your backend. See [Choose the right API key](/fundamentals/authentication-and-access#choose-the-right-api-key).
- Foreground location permission on the device, requested at the workflow step. See [Understand foreground and background location permissions](/fundamentals/location-permissions).
- Your own backend record of which location each action requires.

## Choose this guide or the risky transactions guide

Use this guide when the location condition is part of the workflow: every user who reaches the step is checked, and the step doesn't proceed without it. Use [Detect risky transactions and verify precise location](/fraud/risky-transactions) when location is a step-up that you ask for only after a device and network risk assessment calls for it.

## Choose the location condition

The three conditions use the same check and read different fields.

| Condition | Example | What your backend reads |
| --- | --- | --- |
| In an allowed region | A service offered only in certain states or countries | `passed` |
| Inside a specific place | Clock-in at a workplace, in-store redemption, a technician at a service location | `passed`, then `user.geofences` for the required `externalId` |
| Near an expected address | A delivery handoff or a visit at an address on file | `passed`, then `user.expectedAddress.atAddress` and `user.expectedAddress.confidence` |

`passed` covers the fraud checks and your allowed countries and states. It doesn't say the user is at a particular store or address. Unless your backend checks the place or address condition itself, it has only verified a region.

A check is one observation of where a device was at one moment. It doesn't show that the user lives or works at an address.

## Configure the location condition

### Region condition

Set the country list and state list in the **Fraud** section of the [Settings](https://dashboard.radar.com/settings#fraud-settings) page. Each list is an allowlist or a blocklist, and an empty list allows every country or state. If your workflow has no region restriction, leave the lists empty so that `passed` reflects the fraud checks only.

### Place condition

Create one geofence for each store, workplace, or service location, each with an `externalId` that matches the ID in your own system, such as `store-42`. See [Detect geofence events and place visits](/geofencing/geofences-and-places). Location accuracy indoors varies, so a boundary drawn tightly around a building can exclude users who are inside it.

A geofence doesn't change `passed`. Radar reports it in `user.geofences`, and your backend applies the rule.

### Address condition

Address verification must be enabled for your project. Contact your Radar account team.

Call `Radar.setExpectedAddress()` with the address from your backend's records before the check (`Radar.fraud.setExpectedAddress()` on web):

<CodeGroup>

```swift Swift
Radar.setExpectedAddress("123 Example St, New York, NY 10001")
```

```kotlin Kotlin
Radar.setExpectedAddress("123 Example St, New York, NY 10001")
```

```javascript JavaScript
Radar.fraud.setExpectedAddress('123 Example St, New York, NY 10001');
```

</CodeGroup>

Radar geocodes the address and returns the comparison in `user.expectedAddress`. `atAddress` is `true` when the location is within the distance threshold of the geocoded address, 60 meters by default, and `confidence` is `high`, `medium`, `low`, or `unknown`. When the user isn't at the address, the token carries the warning `address_not_expected`, and `passed` can still be `true`. See [Expected address fields](/api/geolocation-tokens#expected-address-fields).

The SDK sends the address with each later check until you clear it. Pass `nil` in Swift or `null` in Kotlin, or call `Radar.fraud.setExpectedAddress()` with no argument on web, when the workflow ends.

## Run the check

Call `Radar.setUserId()` with the ID your backend uses for the signed-in user. See [Handle login, logout, and user switching](/fundamentals/authentication-and-access#handle-login-logout-and-user-switching). Then run one check at the workflow step, with a `reason` that names the step and a `transactionId` that your backend generated for this action.

## Choose the web path

On web, pass `skipVerifyApp: true` to `Radar.fraud.trackVerified()` to verify without the Radar Verify companion app. The check runs in the browser and the user installs nothing. We recommend the companion app only for sportsbooks and casinos in the US and Canada. See [Choose the web path](/geo-compliance/gaming#choose-the-web-path).

A native macOS or Windows app runs the check with the Radar Verify SDK. See [Verify from a native desktop app](/geo-compliance/gaming#verify-from-a-native-desktop-app).

## Validate the token and check the condition

Your backend decides, not your app. It verifies the token, compares `user.userId` to the session user and `transactionId` to the action, and reads `passed`, as the backend block in [Complete example](#complete-example) shows. Never perform the action because of a client-supplied `passed`. For every validation step and a reusable verifier, see [Validate a token](/api/geolocation-tokens#validate-a-token).

Then check the location condition against the verified payload. The required location comes from your own records, never from the request body:

```javascript Node.js
function isInsideGeofence(payload, externalId) {
  const geofences = payload.user.geofences ?? [];
  return geofences.some((geofence) => geofence.externalId === externalId);
}

function isAtExpectedAddress(payload, addressOnFile) {
  const result = payload.user.expectedAddress;
  // The check must have compared against the address in your records.
  if (!result || result.expectedAddress !== addressOnFile) return false;
  // Choose which confidence levels your workflow accepts.
  const confident = result.confidence === 'high' || result.confidence === 'medium';
  return result.atAddress === true && confident;
}
```

A user who is outside the store still gets a token with `passed` set to `true` when nothing is wrong with the device or the region. The geofence list is empty, so a backend that reads only `passed` would accept the clock-in.

## Handle results and errors

| Result or error | How you detect it | What to do |
| --- | --- | --- |
| Condition met | The token is valid, `passed` is `true`, and the place or address condition holds | Perform the action. |
| Condition not met | The token is valid and `passed` is `true`, and the place or address condition fails | Reject the action. Tell the user where they need to be. |
| Failed check | The token is valid and `passed` is `false` | Reject the action. Show a message based on `failureReasons`, such as disconnecting from a VPN. |
| Permission not granted | `ERROR_PERMISSIONS`, no token | Don't perform the action. Explain how to grant location access. |
| Location unavailable | `ERROR_LOCATION`, no token | Don't perform the action. Ask the user to turn on location services and Wi-Fi, then run a new check. |
| Low-quality location | `fraud_inaccurate_exceeded_accuracy_threshold`, or an address result with `confidence` of `low` or `unknown` | Reject the action or ask for a new check. |
| Other error | `ERROR_NETWORK` or `ERROR_SERVER`, no token | Don't perform the action. Run a new check after a short delay. |
| Expired token | Your backend rejects the token because the current time is past `exp` | Run a new check. |

No row treats a missing or unverifiable result as presence. For every reason and status, see [Failure reasons](/api/geolocation-tokens#failure-reasons) and [Handle a technical error](/api/geolocation-tokens#handle-a-technical-error).

## Test the integration

Use the Test environment with a Test publishable key and a named test user.

- **Passing case**: Run the step from inside a test geofence, or set a location override on the test user that is inside it. Confirm that the geofence appears in `user.geofences` and that your backend performs the action.
- **Failing case**: Run the step from outside the geofence. Confirm that `passed` is `true`, the geofence is absent, and your backend rejects the action.

To test a failed check, create a block rule for the test user ID and confirm that your backend rejects the token with `passed` set to `false`. Bypass rules are for internal testing only. For block rules, bypass rules, and location overrides, see [Force a pass or a fail](/fundamentals/testing-and-launch#force-a-pass-or-a-fail).

Test the place condition on real devices at a real location before launch, at the edges of the boundary and indoors.

## Production checklist

- [ ] Your backend checks the specific place or address condition, not only `passed`.
- [ ] The required location comes from backend records. An address or geofence ID in the request body is never trusted.
- [ ] Your backend checks signature, expiry, user, `transactionId`, and `user.live`, then reads `passed`.
- [ ] Geofence boundaries were tested on real devices at real locations.
- [ ] For an address condition, the accepted `confidence` levels are a recorded decision, and the expected address is cleared when the workflow ends.
- [ ] No JWT secret key in any client, and no bypass rule in the Live environment.
