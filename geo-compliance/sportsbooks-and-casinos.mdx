At the end of this guide, your iOS, Android, or web app runs a verified location check for the signed-in player and the selected product, and your backend allows or denies wagers, deposits, and withdrawals based on a geolocation token that it has validated itself.

A protected request ends in one of three decisions from your backend. The examples on this page use this response shape:

```json
{
  "decision": "deny",
  "reasons": ["state_not_allowed"]
}
```

`decision` is `allow`, `deny`, or `retry`. Your app never decides. It shows what your backend returned.

## Prerequisites

- **Access**: Fraud is enabled for your project under **Fraud** on the [Settings](https://dashboard.radar.com/settings#fraud-settings) page of the Radar dashboard.
- **Platform**: iOS, Android, React Native, or web. Use a Radar SDK and fraud plugin pair from the [compatibility table](/sdk/fraud#compatibility).
- **SDK versions**: The examples use iOS SDK 3.46.0, Android SDK 4.3.0, and Web SDK 5.3.0 with `@radarlabs/plugin-fraud` 1.6.1.
- **Platform setup**: The fraud plugin is installed and device attestation is configured. See [Fraud plugin setup](/sdk/fraud).
- **Keys**: A Test publishable key for your app and your project's JWT secret key for your backend.
- **Backend**: An authenticated endpoint for each protected action, and a JWT library that supports `HS256`.
- **Permissions**: Foreground location permission on the device. Background permission isn't needed for checks that run while the app is open.
- **Dashboard access**: An account that can view locations and create block rules in the Test environment. See [Roles and what each can do](/fundamentals/authentication-and-access#roles-and-what-each-can-do).

## How it works

| Party | Responsibility |
| --- | --- |
| Your app | Identifies the player and the product, requests location permission, runs a check at the right moments, sends the token to your backend, and shows your backend's decision. |
| Radar | Collects location with device and network integrity signals, evaluates your allowed locations and fraud checks for the product, and returns a signed geolocation token with `passed`, `failureReasons`, and an expiry. |
| Your backend | Verifies the token signature and expiry, binds the token to the session user, the product, and the action, reads `passed`, and allows, denies, or asks for a new check. |
| Your downstream systems | Receive the decision from your backend. Wagering, payments, and account systems never read a client result directly. |

The sequence for one protected action:

1. The player signs in. Your app calls `Radar.setUserId()` and `Radar.setProduct()`.
2. Your app runs a check and receives a token.
3. Your app sends the token to your backend on an authenticated request.
4. Your backend validates the token and returns `allow`, `deny`, or `retry`.
5. Your app schedules the next check from the returned expiry and repeats from step 2.

## Set up the project, identity, and products

### Choose projects and environments

<EnvironmentAndKeys />

Each project has its own keys, settings, users, devices, and location checks. Users with the same user ID inside one project share history, block rules, and risk signals. That makes the project boundary an identity decision:

| Situation | Project layout |
| --- | --- |
| Several brands share one player account system, so `user-123` is the same person in each brand | One project for those brands. Separate the offerings with products. |
| Brands have separate account systems, so the same ID can mean different people | One project per brand. |
| A brand must not share settings, keys, or data with another | One project per brand. |

Use the Test environment for development and the Live environment for production. The token carries `user.live`, and the validation steps on this page reject a Test environment token in production.

As an alternative to a publishable key, a project can initialize the SDK with short-lived auth tokens that your backend signs. This is account-specific. See [Use auth tokens instead of a publishable key](/fundamentals/authentication-and-access#use-auth-tokens-instead-of-a-publishable-key).

### Map the authenticated player to the SDK user ID

The token proves which user ID a check ran for. Your backend proves who is making the request. The two match only if your app sets the same ID your backend uses for the session.

<IdentifyUser />

For sportsbook and casino flows, clear the user ID and the cached token at logout. A check must never be attributed to the previous player on a shared device.

### Select the product

A product is a named configuration inside a project, such as `sportsbook` or `casino`. Each product can have its own allowed countries and states and its own check settings. A product setting overrides the project setting with the same name. Where a product doesn't set a value, the project value applies.

Call `Radar.setProduct()` before the check, with the product the player is using:

<CodeGroup>

```swift Swift
Radar.setProduct("casino")
```

```kotlin Kotlin
Radar.setProduct("casino")
```

```javascript JavaScript
Radar.setProduct('casino');
```

</CodeGroup>

How product selection affects the decision:

- `passed` and `failureReasons` in the token are the result for the product named in `product`.
- A token for `sportsbook` doesn't establish eligibility for `casino`. Your backend compares `product` to the product of the action it is authorizing.
- When the player switches product, set the new product and run a new check.
- If per-product results are enabled for your project, the token also carries a `products` object with one `passed` value per configured product from the same check. This is account-specific. See [Payload fields](/api/geolocation-tokens#payload-fields).

Product names are short identifiers made of letters, numbers, hyphens, and underscores. Use the same names in the dashboard, your app, and your backend. Contact your Radar account team for help configuring products.

To narrow a check to the jurisdiction of the player's session, call `Radar.setExpectedJurisdiction()` with a country code and a state code before the check (`Radar.fraud.setExpectedJurisdiction()` on web). A check outside that jurisdiction fails with `country_not_expected` or `state_not_expected`, even when the location is allowed in settings.

## Configure allowed locations

Your allowed locations are your footprint. Radar evaluates four things for the state or province the player is in, for the selected product:

| Setting | What it does | Result in the token |
| --- | --- | --- |
| Country list and state list | Each list is either an allowlist or a blocklist. An empty list allows every country or state. | `user.country.allowed`, `user.state.allowed`. Failure reasons `country_not_allowed`, `state_not_allowed`. |
| Buffer zones | Fails a check that is too close to a border, based on a jurisdiction threshold or the accuracy reported by the device. | `user.state.inBufferZone`, `user.state.distanceToBorder`. Failure reason `state_in_buffer_zone`. |
| Exclusion zones | Fails a check inside a zone within an otherwise allowed state. Can be turned on for all states or for specific states. | `user.state.inExclusionZone`. Failure reason `state_in_exclusion_zone`. |
| Custom geofence zones | A custom geofence can be marked as a state exclusion zone, which fails checks inside it, or a state inclusion zone, which lets a check inside it pass the allowed-state test. | `user.state.inExclusionZone`, `user.state.inInclusionZone`, and the geofence in `user.geofences`. |

A state check passes when the state matches the expected jurisdiction if you set one, the location isn't in an exclusion zone, the location isn't in a buffer zone, and the state is allowed or the location is in an inclusion zone.

### View or change the lists

The jurisdiction settings are in the **Fraud** section of the [Settings](https://dashboard.radar.com/settings#fraud-settings) page, once for the project and once for each product. The controls are a list type (allowlist or blocklist) and a list for countries, the same pair for states, and a setting that turns state exclusion zones on for all states, for specific states, or off.

- Changes apply to checks made after you save. Tokens already issued keep their result until they expire, so a player who passed before the change can hold a passing token until its expiry.
- Changing a list changes where your product is offered. Treat it as a controlled change with a named approver.
- Whether your organization can edit these settings itself is account-specific. On some accounts they are read-only and Radar makes the change for you. See [Who can change jurisdiction settings and block or bypass rules](/fundamentals/authentication-and-access#who-can-change-jurisdiction-settings-and-block-or-bypass-rules).
- Access to buffer zones and exclusion zones is account-specific. Contact your Radar account team to use them.

Verify a change in the Test environment: run a check from a location in the state you changed, or use a location override on a test user, and confirm `user.state.allowed` and `passed` in the token.

### Add custom geofences and beacons

To fail or pass checks inside a property, create a custom geofence on the [Geofences](https://dashboard.radar.com/geofencing/geofences) page and set its fraud zone type to a state exclusion zone or a state inclusion zone. The geofence takes effect for checks made after you save it. Geofences without a zone type don't change `passed`. They appear in `user.geofences` for your own rules and investigations.

On iOS and Android, a check can also range nearby beacons. Pass `beacons: true` to `Radar.trackVerified()`. When beacons are enabled for your project, the beacons in range are returned with the user in the verified payload. A beacon doesn't change `passed` on its own in the behavior documented here, so if your eligibility rule depends on being near a beacon, apply that rule on your backend after token validation. For beacon setup, ranging behavior, and hardware guidance, see [Track indoor location with beacons](/geofencing/beacons).

## Choose manual or automatic checks

There are two ways to run checks. This guide uses manual checks as the worked example, because your app decides when each check runs and can label each one with a reason.

| | Manual checks | Automatic checks with caching |
| --- | --- | --- |
| Method | `Radar.trackVerified()` | `Radar.startTrackingVerified()`, then `Radar.getVerifiedLocationToken()` |
| Who decides when a check runs | Your app | The SDK |
| When checks run | When you call the method | When tracking starts, then at your interval, sooner when the last token expires before the interval, and when the device IP address changes |
| Token delivery | The completion handler or promise of your call | `RadarVerifiedDelegate.didUpdateToken()` on iOS, `RadarVerifiedReceiver.onTokenUpdated()` on Android, `Radar.fraud.onTokenUpdated()` on web, and the result of `getVerifiedLocationToken()` |
| `reason` | You pass a reason on every check | The SDK sets the reason on the checks it starts on iOS and Android, such as `interval` and `ip_change` |
| `transactionId` | Supported | Not sent on checks the SDK starts |
| Cached result | You store the last accepted result | `getVerifiedLocationToken()` returns the last token if it is still valid, and requests a new one if not |
| Overlap and scheduling | You implement them. See [Run checks at the right time](#run-checks-at-the-right-time). | Handled by the SDK |

Selection criteria:

- Choose manual checks when checks must line up with specific application moments, when you want your own reason on every check, or when you bind checks to actions with `transactionId`.
- Choose automatic checks when you want the SDK to keep a current token available for the whole session and you don't need a reason or transaction on each check.
- You can combine them: run automatic checks for the session, and call `Radar.trackVerified()` with a `reason` and `transactionId` before a bound action.

Whichever you choose, the backend validation is the same.

### Use automatic checks

These examples start automatic checks, read the cached token before a protected action, and stop at logout. On web, `interval` defaults to 300 seconds and `ipChanges` defaults to `false`.

<CodeGroup>

```swift Swift
import RadarSDK

// Conform to RadarVerifiedDelegate to receive each new token.
Radar.setVerifiedDelegate(self)

// Check at least every 1200 seconds, sooner when a token expires earlier.
Radar.startTrackingVerified(interval: 1200, beacons: false)

// Before a protected action: cached token if still valid, new check if not.
Radar.getVerifiedLocationToken { (status, token) in
  guard status == .success, let jwt = token?.token else {
    handleCheckError(status)
    return
  }
  sendTokenToBackend(jwt)
}

// RadarVerifiedDelegate
func didUpdateToken(_ token: RadarVerifiedLocationToken) {
  sendTokenToBackend(token.token)
}

// At logout or when the protected session ends.
Radar.stopTrackingVerified()
```

With automatic checks, call `Radar.clearVerifiedLocationToken()` (`Radar.fraud.clearVerifiedLocationToken()` on web) when the player logs out or changes product, so that a cached token for the previous player or product isn't returned.

## Choose the web path

On web, a check runs through one of two paths. For install steps and the full comparison, see [Choose the companion app or the no-download path](/sdk/fraud#choose-the-companion-app-or-the-no-download-path).

| | Companion app | No-download |
| --- | --- | --- |
| Supported platforms | Desktop browsers on macOS and Windows, with Radar Verify running on the same computer | Browsers supported by the [Web SDK](/sdk/web) |
| Installation | The player installs Radar Verify for Mac or Windows once | None |
| Initialization | `skipVerifyApp: false`, which is the default | `skipVerifyApp: true` |
| Where the location comes from | The Radar Verify app | The browser's geolocation API |
| Permission the player grants | Location access for the Radar Verify app | Location access for your site in the browser |
| Signals | Adds remote desktop detection for the `sharing` flag, more advanced `mocked` and `proxy` detection, and more stable device IDs | Browser signals |
| Path-specific error | `ERROR_VERIFY_APP` (`RadarVerifyAppError`) when the app isn't installed or isn't running | None. Permission and location errors come from the browser. |

Selection criteria:

- If your requirements include detecting screen sharing or remote control on desktop, only the companion app path reports the `sharing` signal.
- If your players can't or won't install software, only the no-download path works.
- If your compliance requirements name specific signals or a specific client type, confirm them with your compliance team and your Radar account team before you build.

Decide once per product and pass the same `skipVerifyApp` value to `Radar.fraud.trackVerified()`, `Radar.fraud.startTrackingVerified()`, and `Radar.fraud.getVerifiedLocationToken()`.

On the companion app path, handle `RadarVerifyAppError` as its own state: tell the player to open Radar Verify, or to install it, then run the check again. Don't fall back to the no-download path automatically unless your compliance team has approved both paths for the product.

## Run checks at the right time

A check is needed whenever the last result your backend accepted no longer covers what the player is about to do.

| Moment | What to do | Example `reason` |
| --- | --- | --- |
| Session start or login | Set the user ID and product, then run a check before you show protected features. | `login` |
| Product change | Set the new product, then run a check. A token for one product doesn't cover another. | `product_change` |
| Before expiry | Schedule the next check from `expiresIn` or `expiresAt` on the token you received. | `interval` |
| A protected action | If the accepted result has expired, run a check first. To bind the check to one action, pass a `transactionId`. | `wager`, `withdrawal` |
| App returns to the foreground, or the page becomes visible | Compare the current time to the stored expiry. Run a check if it has passed. | `resume` |
| Device IP address changes | Run a check. See [Respond to network changes](#respond-to-network-changes). | `ip_change` |
| Logout or user switch | Clear the user ID, the cached token, and your stored result. | Not applicable |

The `reason` values are examples. Choose your own set and keep it stable.

### Schedule checks from the returned expiry

Radar sets the expiry on each token from your product and jurisdiction configuration and the distance to the border. Tokens issued close to a border expire sooner, which is how a player who is moving toward a border gets checked more often. Don't replace this with a fixed interval, and don't extend a result past its expiry. See [Expiry](/api/geolocation-tokens#expiry).

### Orchestrate manual checks

These coordinators run one check at a time, skip a check when the accepted result is still current, schedule the next check from the returned expiry, and recheck on resume. `postTokenToBackend` is a function you write. It sends the token on an authenticated request and returns your backend's decision. `refreshLeadSeconds` is a value you choose so that a new token arrives before the old one expires.

<CodeGroup>

```swift Swift
import UIKit
import RadarSDK

final class LocationCheckCoordinator {
  static let shared = LocationCheckCoordinator()

  private let refreshLeadSeconds: TimeInterval = 10
  private var inFlight = false
  private var acceptedUntil: Date?
  private var timer: Timer?

  /// Call from the main thread at session start, on product change,
  /// on foreground, and before a protected action.
  func check(reason: String, transactionId: String? = nil, force: Bool = false) {
    // Skip when the backend already accepted a result that is still current.
    // Always run a new check for a bound action.
    if !force, transactionId == nil, let acceptedUntil, acceptedUntil > Date() { return }

    // One check at a time.
    guard !inFlight else { return }
    inFlight = true

    Radar.trackVerified(
      beacons: false,
      desiredAccuracy: .medium,
      reason: reason,
      transactionId: transactionId
    ) { [weak self] (status, token) in
      DispatchQueue.main.async {
        guard let self = self else { return }

        guard status == .success, let token = token else {
          // Technical error. No token, no decision. Keep the action blocked.
          self.inFlight = false
          self.acceptedUntil = nil
          showCheckError(status)
          return
        }

        // Send the token whether or not token.passed is true.
        postTokenToBackend(token.token) { decision in
          DispatchQueue.main.async {
            self.inFlight = false
            if decision == "allow" {
              self.acceptedUntil = token.expiresAt
              self.scheduleNext(after: token.expiresIn)
              showAllowed()
            } else {
              self.acceptedUntil = nil
              showBlocked(decision)
            }
          }
        }
      }
    }
  }

  private func scheduleNext(after expiresIn: TimeInterval) {
    timer?.invalidate()
    let delay = max(expiresIn - refreshLeadSeconds, 1)
    timer = Timer.scheduledTimer(withTimeInterval: delay, repeats: false) { [weak self] _ in
      self?.check(reason: "interval", force: true)
    }
  }

  /// Call at logout.
  func reset() {
    timer?.invalidate()
    acceptedUntil = nil
    Radar.setUserId(nil)
    Radar.clearVerifiedLocationToken()
  }
}

// In your scene delegate. Timers do not fire while the app is suspended,
// so compare against the stored expiry when the app becomes active.
func sceneDidBecomeActive(_ scene: UIScene) {
  LocationCheckCoordinator.shared.check(reason: "resume")
}
```

```kotlin Kotlin
import android.os.Handler
import android.os.Looper
import io.radar.sdk.Radar
import io.radar.sdk.RadarTrackingOptions

object LocationCheckCoordinator {
  private const val REFRESH_LEAD_SECONDS = 10
  private val handler = Handler(Looper.getMainLooper())
  private var inFlight = false
  private var acceptedUntilMs: Long? = null

  private val scheduled = Runnable { check(reason = "interval", force = true) }

  /**
   * Call from the main thread at session start, on product change,
   * on foreground, and before a protected action.
   */
  fun check(reason: String, transactionId: String? = null, force: Boolean = false) {
    // Skip when the backend already accepted a result that is still current.
    // Always run a new check for a bound action.
    val until = acceptedUntilMs
    if (!force && transactionId == null && until != null && until > System.currentTimeMillis()) return

    // One check at a time.
    if (inFlight) return
    inFlight = true

    Radar.trackVerified(
      beacons = false,
      desiredAccuracy = RadarTrackingOptions.RadarTrackingOptionsDesiredAccuracy.MEDIUM,
      reason = reason,
      transactionId = transactionId
    ) { status, token ->
      handler.post {
        if (status != Radar.RadarStatus.SUCCESS || token == null) {
          // Technical error. No token, no decision. Keep the action blocked.
          inFlight = false
          acceptedUntilMs = null
          showCheckError(status)
          return@post
        }

        // Send the token whether or not token.passed is true.
        postTokenToBackend(token.token) { decision ->
          handler.post {
            inFlight = false
            if (decision == "allow") {
              acceptedUntilMs = token.expiresAt.time
              scheduleNext(token.expiresIn)
              showAllowed()
            } else {
              acceptedUntilMs = null
              showBlocked(decision)
            }
          }
        }
      }
    }
  }

  private fun scheduleNext(expiresIn: Int) {
    handler.removeCallbacks(scheduled)
    val delaySeconds = maxOf(expiresIn - REFRESH_LEAD_SECONDS, 1)
    handler.postDelayed(scheduled, delaySeconds * 1000L)
  }

  /** Call at logout. */
  fun reset() {
    handler.removeCallbacks(scheduled)
    acceptedUntilMs = null
    Radar.setUserId(null)
    Radar.clearVerifiedLocationToken()
  }
}

// In your activity. Compare against the stored expiry when the app resumes.
override fun onResume() {
  super.onResume()
  LocationCheckCoordinator.check(reason = "resume")
}
```

```javascript JavaScript
import Radar from 'radar-sdk-js';

const REFRESH_LEAD_SECONDS = 10;
const skipVerifyApp = false; // your chosen web path

let inFlight = null;
let acceptedUntil = 0;
let timer = null;

// Call at session start, on product change, when the page becomes visible,
// and before a protected action.
export function check({ reason, transactionId, force = false }) {
  // Skip when the backend already accepted a result that is still current.
  // Always run a new check for a bound action.
  if (!force && !transactionId && acceptedUntil > Date.now()) {
    return Promise.resolve('allow');
  }

  // One check at a time. Callers share the check that is in flight.
  if (inFlight) return inFlight;

  inFlight = (async () => {
    try {
      const result = await Radar.fraud.trackVerified({ skipVerifyApp, reason, transactionId });

      // Send the token whether or not result.passed is true.
      const decision = await postTokenToBackend(result.token);

      if (decision === 'allow') {
        acceptedUntil = result.expiresAt.getTime();
        scheduleNext(result.expiresIn);
      } else {
        acceptedUntil = 0;
      }
      return decision;
    } catch (err) {
      // Technical error. No token, no decision. Keep the action blocked.
      acceptedUntil = 0;
      throw err;
    } finally {
      inFlight = null;
    }
  })();

  return inFlight;
}

function scheduleNext(expiresIn) {
  clearTimeout(timer);
  const delaySeconds = Math.max(expiresIn - REFRESH_LEAD_SECONDS, 1);
  timer = setTimeout(() => {
    check({ reason: 'interval', force: true }).catch(showCheckError);
  }, delaySeconds * 1000);
}

// Timers are throttled in hidden tabs. Compare against the stored expiry
// when the page becomes visible again.
document.addEventListener('visibilitychange', () => {
  if (document.visibilityState === 'visible') {
    check({ reason: 'resume' }).catch(showCheckError);
  }
});

// Call at logout.
export function reset() {
  clearTimeout(timer);
  acceptedUntil = 0;
  Radar.setUserId();
  Radar.fraud.clearVerifiedLocationToken();
}
```

</CodeGroup>

The client-side `acceptedUntil` value avoids unnecessary checks. It doesn't authorize anything. Your backend enforces expiry on every protected request, as described in [Validate the response on your backend](#validate-the-response-on-the-backend).

### Respond to network changes

The SDK can tell you when the device IP address changes, so that a manual integration can run a new check.

| Platform | How to receive the change | Notes |
| --- | --- | --- |
| iOS | Set a `RadarVerifiedDelegate` with `Radar.setVerifiedDelegate()` and implement `didChangeIP()`. | The SDK monitors IP changes while a verified delegate is set or automatic checks are running. |
| Android | Set a `RadarVerifiedReceiver` with `Radar.setVerifiedReceiver()` and override `onIpChanged(context)`. | Same condition as iOS. |
| Web | Register a callback with `Radar.fraud.onIpChanged()`. Pass `null` to remove it. | The plugin monitors IP changes while a callback is registered. |

In the callback, call your coordinator with `force` set to true and a reason such as `ip_change`. With automatic checks, the SDK starts the check itself on iOS and Android, and on web when you pass `ipChanges: true`.

Manual checks have no separate callback for a location change. Movement toward a border is handled by the shorter expiry on the token.

## Record check reasons

Pass a `reason` on every check. It costs one argument and it is the main way to tell checks apart later.

- **Investigation**: The reason appears on the location check in the dashboard and can be used as a filter on the [Locations](https://dashboard.radar.com/geofencing/locations) page and as a column or grouping in reports. When a player disputes a blocked withdrawal, you can go straight to the checks with the `withdrawal` reason.
- **Rules**: Fraud rules can use the location check reason as a condition, so a rule can apply to `withdrawal` checks without firing on every `interval` check. See [Configure rules and actions](/fraud/overview#configure-rules-and-actions).
- **Backend**: The reason is returned in the token as `reason`. Your backend can require a specific reason for a specific action, for example a `withdrawal` check for a withdrawal.

`reason` and `transactionId` are free-form strings. Radar doesn't restrict them to a list. Define a small fixed set of reasons, such as `login`, `interval`, `resume`, `product_change`, `wager`, `deposit`, and `withdrawal`, and use the same spelling on every platform. Don't put personal data in either field.

## Validate the response on the backend

<TokenValidation />

### What the token format means for your verifier

| Topic | Behavior | What you implement |
| --- | --- | --- |
| Supported format | A signed token: JWS compact serialization with `HS256`. The token isn't encrypted. | Reject anything that isn't a three-segment JWS with `alg` set to `HS256`. Treat the payload as readable by the player. |
| Trusted key selection | One JWT secret key per project. The header has no `kid`. | Load the key from your own configuration for the project the request belongs to. Never choose a key from a value inside the token. |
| Allowed algorithms | `HS256` only. | Pass an explicit allowlist to the library. |
| Decryption | Not applicable. There is no encrypted envelope to open. | Nothing. |
| Signature verification | Required for every token. | Performed by the JWT library with your secret key. |
| Key rotation | No key identifier, so no per-token key selection. | The two-key overlap in [Change the secret key](#change-the-secret-key). |
| Authenticated-user binding | `user.userId` is the value your app set. | Compare it to the session user. |
| Freshness | `exp` on the token. | Enforced by the library. Don't accept a token after `exp`. |
| Selected product | `product`, and `products` when enabled. | Compare to the product of the action. |
| Failure and warning fields | `passed`, `failureReasons`, `warningReasons`. | Deny when `passed` isn't `true`. Warnings don't fail a check. See [failure reasons](/api/geolocation-tokens#failure-reasons) and [warning reasons](/api/geolocation-tokens#warning-reasons). |
| Replay and transaction binding | Radar doesn't track whether a token was already presented. `transactionId` is returned unchanged and isn't checked for uniqueness. | For single-use actions, generate the `transactionId` on your backend, compare it, and mark it used. |

### Apply the decision to a session

You can require a token on every protected request, or accept a token once and remember the result. If you remember it, store the validated values on the server, keyed by your session:

```json
{
  "userId": "user-123",
  "product": "sportsbook",
  "decision": "allow",
  "expiresAt": "2026-11-17T18:20:00.000Z",
  "locationCheckId": "66f1c2a9e4b0a1b2c3d4e5f6"
}
```

Then, for each protected request, deny unless a stored result exists for the session user and the product of the action, and the current time is before `expiresAt`. Take `expiresAt` from the token's `exp` claim, and keep `_id` from the token as `locationCheckId` so that support staff can find the check in the dashboard. Delete the stored result at logout, on a product change, and when a later token for the same session is denied.

For withdrawals and other single-use actions, require a token on the request itself, bound with `transactionId`.

## Evaluate and roll out

### Shadow test against a current provider

In a shadow test, your current provider keeps making the decision. Your app also runs a Radar check at the same moments, and your backend records the Radar result without enforcing it.

- **Mirror your current integration**: Run the Radar check where the current check runs, with a matching `reason`, so that you compare like with like.
- **Record both results**: On your backend, store the user ID, product, platform, reason, timestamp, decision, failure reasons, and latency.
- **Shadow traffic can create history and risk signals**: Shadow checks are real checks. They create user and device records and location history in Radar, and they can contribute to fraud flags, risk scores, and, if it is enabled for your project, automatic blocking. Agree with your Radar account team before the test how that history is handled when you start enforcing, and whether automatic blocking stays off during the test.
- **Confirm your data-sharing position first**: A shadow test sends player location data to Radar. Check with your legal and compliance team whether a jurisdiction requires approval before that happens.
- **Prompts**: A second SDK can mean a second permission prompt or a second companion app. Decide which platforms and web paths are in scope so that players aren't asked to install two apps.

### Run two SDKs side by side

Two location SDKs in one app or page share the same device location services and, on web, the same browser APIs. Before you trust shadow numbers, confirm on each platform that both SDKs return valid results when loaded together, in the load order you ship. If one platform doesn't produce valid results for both, leave that platform out of the shadow test instead of comparing skewed data.

### Compare metrics

| Metric | What to look at |
| --- | --- |
| Pass rate | By jurisdiction, product, and platform |
| Failure reasons | The mix of jurisdiction and fraud reasons, and how it differs from your current provider |
| Technical error rate | By status, such as `ERROR_LOCATION` and `ERROR_NETWORK`, separately from failed checks |
| Latency | Time from the check call to the token, by platform |
| Agreement | Checks where the two providers disagree. Review a sample of each direction. |
| Support contacts | Location-related contacts per active player, after you start enforcing |

### Roll out in stages

1. **Internal**: Enforce for staff accounts in the Live environment, in one jurisdiction.
2. **Limited**: Enforce for one jurisdiction or a percentage of players, behind a server-side flag that your backend reads on each protected request.
3. **Expand**: Add jurisdictions or raise the percentage when the metrics hold.
4. **Complete**: Remove the previous provider after every jurisdiction and platform is enforcing on Radar.

Keep the flag on your backend, so that the path that enforces is the path that was tested and a client build can't choose its own provider.

### Roll back

Rollback is the same flag turned off: your backend returns to the previous decision source for the affected jurisdiction or cohort. Keep the previous integration deployable until the final stage is complete. Rehearse the rollback once in a non-production environment, and decide in advance which signals trigger it, such as a technical error rate above your threshold. Subscribe to the [Radar status page](https://status.radar.com) for incident notices.

### Control access

- **Roles**: Give support staff read access to the Live environment, and keep the group that can create bypass rules or change settings small. See [Roles and what each can do](/fundamentals/authentication-and-access#roles-and-what-each-can-do).
- **Footprint changes**: Limit who can change allowed countries and states. See [Who can change jurisdiction settings and block or bypass rules](/fundamentals/authentication-and-access#who-can-change-jurisdiction-settings-and-block-or-bypass-rules).
- **Retention**: Location checks are kept for the retention period configured for your project. See [Find and change data retention](/fundamentals/authentication-and-access#find-and-change-data-retention).
- **Exports and reports**: See [Export data](/fundamentals/authentication-and-access#export-data) and [Find, export, and report on data](/fundamentals/testing-and-launch#find-export-and-report-on-data).
- **Your own records**: If you must keep evidence of each decision for longer than your Radar retention period, store the token or the validated fields on your backend at decision time.

## Handle results and errors

<CheckResults />

### Show the right message

Keep three client states apart, because the player's next step is different in each:

| State | How you detect it | What to show |
| --- | --- | --- |
| Not eligible here | Backend returns `deny` with a jurisdiction failure reason, such as `state_not_allowed` or `state_in_buffer_zone` | The product isn't available at this location. Offer a retry after the player moves. |
| Device or network problem the player can fix | Backend returns `deny` with a fraud failure reason, such as `fraud_proxy_known_proxy_ip` | What to change, for example disconnect from a VPN, then a retry button. |
| Check couldn't complete | Your app received an error status and no token, or your backend returned `retry` | A technical message and a retry button. Don't say the player is ineligible. |

Handle a failure reason you don't recognize with a general message, because the list can grow. Limit automatic retries after a technical error to a small number with a delay between them, then wait for the player.

## Production checklist

- [ ] Live publishable key in production client builds. No secret key or JWT secret key in any client.
- [ ] JWT secret key loaded from a secret manager on your backend.
- [ ] `Radar.setUserId()` is set at login with the session user ID, and cleared at logout together with the cached token.
- [ ] `Radar.setProduct()` is set before every check, and a product change triggers a new check.
- [ ] Every check passes a `reason` from your fixed list.
- [ ] One check in flight at a time. The next check is scheduled from the returned expiry. Resume compares against the stored expiry.
- [ ] Every protected endpoint validates a token, or reads a server-side result that came from a validated token. None reads a client-supplied `passed`.
- [ ] Your backend checks signature, algorithm, expiry, user, product, `transactionId` when used, `user.live`, and `passed`, and fails closed.
- [ ] Failed checks and technical errors show different messages.
- [ ] Your backend negative tests pass in CI.
- [ ] Allowed countries, states, and zones are reviewed for each product in the Live environment by the accountable owner.
- [ ] No bypass rule or override exists in the Live environment for a real player, and test block rules are removed.
- [ ] The rollout flag and rollback steps are tested.
- [ ] The [go-live checklist](/fundamentals/testing-and-launch#go-live-checklist) is complete.
