Use this page to pick one implementation guide before you write code. At the end, you know which SDK or API to call, whether you need to ask the user for location, what result your app or backend receives, and which guide to follow.

## Start with the kind of result you need

Radar returns three kinds of result. They come from different calls, ask different things of the user, and support different decisions.

| | Location tracking | Verified location | Device and network risk |
| --- | --- | --- | --- |
| Question it answers | Where is this device, and which of my geofences, places, or trips does that relate to? | Is this user in a location where the action is allowed, and can I trust the location? | Does this device or its network connection look risky? |
| Client call | `Radar.trackOnce()`, `Radar.startTracking()`, or `Radar.startTrip()` | `Radar.trackVerified()` | `Radar.revealRisk()` |
| What you install | The core SDK | The core SDK and the fraud plugin | The core SDK and the fraud plugin |
| Location permission | Required. Foreground for in-app use, background for events while the app is closed. | Required. Foreground is enough. | Not requested |
| Result | The user's current geofences, place, beacons, and trip, plus events such as `user.entered_geofence` | A signed geolocation token with `passed`, failure reasons, fraud signals, and an expiry | `risk.level`, `risk.reasons`, `network`, `device`, and a signed token |
| Who decides | Your app, or a system that receives the events | Your backend, after it validates the token | Your backend, after it validates the token |
| Product | [Geofencing](/geofencing/overview) | [Geo-compliance](/geo-compliance/overview) and [Fraud](/fraud/overview) | [Fraud](/fraud/overview) |

Location tracking is built for experiences: a location that is good enough to show the right screen or start an order. It isn't evidence for an access decision. Use a verified location check when the answer gates something of value. Use a risk assessment when you want a signal without a location prompt, and step up to a verified location check only when you need to know where the user is.

Maps is the fourth path. Displaying a map, searching for an address, and geocoding don't track a user and don't need location permission, unless you also show or use the user's current position.

## Check your platform

Feature support differs by SDK. Confirm it in the tables in [SDK overview and compatibility](/sdk/sdk) before you commit to a path. The summary below covers the questions that most often change the choice.

| Client | What to know | Reference |
| --- | --- | --- |
| Native iOS and Android | All four products. Verified location checks and risk assessments need the fraud plugin, which you install separately from the core SDK. | [iOS SDK](/sdk/ios), [Android SDK](/sdk/android), [Fraud plugin setup](/sdk/fraud) |
| Web | Tracks only while your page is open: no background tracking, no beacons, no silent push. Verified location checks and risk assessments come from `@radarlabs/plugin-fraud`. Maps and autocomplete UI are separate plugins. | [Web SDK](/sdk/web) |
| Desktop browser with a companion app | The web fraud plugin can work with Radar Verify for Mac and Windows, which adds remote desktop detection, more advanced detection of mocked locations and proxies, and more stable device IDs. Pass `skipVerifyApp: true` to run the check in the browser with no download. | React Native | Core tracking, trips, beacons, verified location checks and risk assessments with the fraud plugin, and `Map` and `Autocomplete` components. | [React Native SDK](/sdk/react-native) |
| Flutter, Capacitor, Cordova, .NET MAUI | Core tracking, trips, and beacons. | Your backend | Geocoding, search, and routing requests. Managing geofences, trips, beacons, and users with a secret key. Receiving events through webhooks. Validating tokens. | [REST API overview](/api) |

## What your backend can and cannot do

A backend can't manufacture a verified client-location result. A verified location check and a risk assessment both collect signals on the user's device or browser, through the SDK and the fraud plugin, and Radar signs the result. The check has to run on the device because that is where the location and integrity signals come from. A location that your client reports to your own API in a request body isn't verified.

Your backend's role in Geo-compliance and Fraud is to:

1. Receive the signed token from the client on an authenticated request.
2. Validate the signature and expiry, and check that the user, product, and result match the action. See [Geolocation token schema](/api/geolocation-tokens).
3. Decide, enforce the decision, and record it.

Reading `passed` in the app isn't validation. The app shows what the backend decided.

Calls from your backend do have a place in the other paths:

- **Maps**: The geocoding, search, and routing endpoints work from your backend as well as from a client. See [Geocoding API](/api/geocoding), [Search API](/api/search), and [Routing API](/api/routing).
- **IP geocoding**: It returns an estimate of where a network connection terminates. Use it to set a default region or search bias. It isn't a verified location.
- **Trips**: Your backend can create and update trips with the [Trips API](/api/trips). Creating a trip on your backend doesn't start tracking on a device. The app still has to be running the SDK and sending locations.
- **Events**: Your backend receives geofence, place, trip, and beacon events through [webhooks](/integrations/webhooks) or another [integration](/integrations/integrations).

## Set up a project, then identify users

These are two separate steps, done in different places by different people. Confusing them is a common early mistake.

| | Account and project setup | Identifying an end user |
| --- | --- | --- |
| What it is | Creating your organization and project, inviting teammates, and getting API keys | Telling Radar which of your app's users a device belongs to |
| Where it happens | The dashboard | Your app, through the SDK |
| Who does it | Your team, once per project | Your code, each time a user signs in or changes |
| What it uses | Dashboard accounts and roles, publishable keys (`prj_test_pk_...`, `prj_live_pk_...`), and secret keys (`prj_test_sk_...`) | `Radar.setUserId()` with a stable, opaque ID from your own system, such as `user-123` |
| Guide | [Set up a project and its environments](/fundamentals/authentication-and-access#set-up-a-project-and-its-environments) and [Choose the right API key](/fundamentals/authentication-and-access#choose-the-right-api-key) | [Identify the users in your app](/fundamentals/authentication-and-access#identify-the-users-in-your-app) |

A dashboard account is a teammate. A user is a person or device in your app. Users never sign in to the dashboard, and inviting a teammate doesn't create a user. An API key identifies your project and environment, not a person.

For Geo-compliance and Fraud, the user ID matters for the decision itself: your backend compares the user ID in the validated token to the user in the authenticated session. Set it before the check, and set it again when the signed-in user changes.
